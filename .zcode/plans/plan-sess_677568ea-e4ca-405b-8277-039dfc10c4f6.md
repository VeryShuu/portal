# План: prod-контур без клона репозитория (B + C в одной итерации)

## Цель
Запечь `backend/migrations/init.sql` в postgres-образ (B) и сделать так, чтобы на проде был **только** deploy-bundle (`docker-compose.yml` + `.env` + monitoring-overlay), без дерева исходников (C). Образы тянутся из GHCR (ADR-045). Dev/CI работают как раньше из полного клона.

Решения пользователя: bundle через **CI Release-artifact**, мониторинг **в bundle**, гейт по **`.portal-profile`**, **B+C в одной итерации**.

## Этап 2 — Разделение контуров через `.portal-profile` (C, ядро)

### Новый файл `.portal-profile`
Создаётся один раз при первичной настройке: `prod` или `dev`. Добавить в `.gitignore`.

### `setup.sh` — правки

**Новая функция `current_profile()`** (читает `.portal-profile`, default `dev`).

**`setup_env()` (строки 172-338):** в начале интерактивный вопрос «Контур: prod/dev»:
- `prod` → пишет в `.env` `IMAGE_PREFIX=ghcr.io/veryshuu/`, в `.portal-profile` `prod`.
- `dev` → пустой `IMAGE_PREFIX`, `.portal-profile` `dev`.

**`show_menu()` (строки 36-94):** ветвить по `current_profile`:
- **prod-профиль:** скрывать п.2 (dev), п.3 (staging), п.4-в-режиме-local-build. Подпись п.4 — всегда «pull свежих». Оставить: 1, 4, 5, 6, 7, 8, 9, 10.
- **dev-профиль:** скрывать п.6 (update_production). Оставить: 1 (если вручную проставили registry), 2, 3, 4, 5, 7, 8, 9, 10.

**`run_compose()` (строки 709-745):** добавить guard в начало:
```
if [[ "$(current_profile)" == "prod" && -z "$image_prefix" ]]; then
    err "prod-контур требует IMAGE_PREFIX (registry). Запустите пункт 5."
fi
```
Ветви build (`:737-743`) физически недостижимы в prod-профиле.

**`update_production()` (строки 1187-1255):**
- Заменить блок git-pull (`:1219-1233`): если `.git` есть — `git pull --ff-only` (как сейчас); если `.git` нет И `current_profile == prod` → тихо пропустить (без warn, только echo «пропускаю — deploy-bundle режим»).
- Эхо-превью (`:1199-1210`): фразы «git pull» заменить на «обновление конфигурации (git pull или новая версия bundle)».

**`preflight()` (строки 1094-1184):** добавить проверки:
- `[[ -f docker-compose.yml ]]` или явный err.
- Для prod-профиля: `IMAGE_PREFIX` непустой (иначе `fatal=1`).
- Для prod-профиля: если выбран пункт про monitoring-overlay, проверить `monitoring/docker-compose.monitoring.yml`.

**`start_monitoring()` (строки 1365-1369):** overlay-файл входит в bundle, оставить существующую проверку — она и так корректно сообщает «запускайте из корня» (bundle распаковывается в корень `/opt/portal/`).

**`gen-dev-files`/`generate_dev_files()` (строки 413-664):** оставить без изменений — это dev/CI-only. При запуске в prod-профиле — early `err "gen-dev-files только для dev-контура"`.

## Этап 3 — CI deploy-bundle (доставка на прод без git-clone)

### Новая job в `ci.yml`: `deploy-bundle`
- `needs: [publish-images]`, `if: startsWith(github.ref, 'refs/tags/v')` (только на релизном теге).
- Собирает tarball `portal-deploy-bundle-${{ github.ref_name }}.tar.gz`:
  ```
  docker-compose.yml
  .env.example
  monitoring/               # весь overlay, включая node-exporter-textfile/
  setup.sh                  # обновлённый, с profile-gate'ом
  ```
  (исключить `.git/`, `backend/`, `frontend/`, `nginx/`, `postgres/`, `screenshot-service/`, `*.md`, тесты — это не нужно на проде).
- `softprops/action-gh-release@v2` аттачит tarball к Release `v*` (права `contents: write`).

### Флоу на проде
1. `gh release download v1.2.3 -p 'portal-deploy-bundle-*.tar.gz'` (или `wget` со ссылочной вкладки Release).
2. `tar xzf portal-deploy-bundle-*.tar.gz -C /opt/portal`.
3. `./setup.sh` → 5 (первичная настройка .env, выбирает профиль prod) → 1 (запуск).

## Что НЕ меняется (гарантия несломанного dev/CI)
- Dev-контур: полный клон репо, `generate_dev_files()`, local-build, bind-mount'ы исходников — без изменений.
- CI-раннеры: `actions/checkout@v6`, `pytest`, `compose-smoke` — работают из полного чекаута; единственная правка — убран `-v init.sql` (init теперь в образе), всё остальное прежнее.

- monitoring-overlay — попадает в bundle как есть; `node-exporter-textfile/` собирается локально на проде при первом `up`.

## Риски и митигация
1. **`context: .` + корневой `.dockerignore`** — без whitelist образ не соберётся (init.sql и postgres/Dockerfile вне context). Митигация: whitelist в `.dockerignore`, проверить локальным `docker build`.
2. **`init.sql` уже применён к старым прод-кластерам** — `/docker-entrypoint-initdb.d/*` выполняется только при пустом `base_data/postgres/`. На существующих прод-инсталляциях baked init.sql **не перезапустит** FTS-конфиг (уже создан) — это безопасно, меняется только источник на новых стендах.
3. **Размер bundle** — ~десятки КБ (compose + .env.example + monitoring configs + setup.sh). Не артефакт-гигант.
4. **Пользователь забыл `.portal-profile`** — default `dev`, всё работает в local-build режиме (как сегодня). Без регрессии.
