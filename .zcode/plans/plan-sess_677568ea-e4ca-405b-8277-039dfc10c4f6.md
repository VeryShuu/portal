# План: Semver-lock прод-деплоя (ADR-047)

## Цель
Перевести продакшен с implicit deploy по `:latest` на **явный pin к релизному тегу** (`IMAGE_TAG=v1.x.x`). Прод больше не выкатывается автоматически на каждый merge в main — только когда оператор сознательно меняет `IMAGE_TAG` в `.env`. Стратегически вы выбрали «ручной деплой по тегу», этот план её реализует.

Решения (best judgment после пропуска вопросов):
- `:latest` остаётся пушиться в CI (не ломает существующий прод и dev), но **prod-профиль `setup.sh` отвергает `IMAGE_TAG=latest`**. Так implicit deploy невозможен, а миграция — мягкая.
- Postgres остаётся на `:16` rolling (не привязан к semver; схема БД ≠ версия приложения).
- Валидация тега: CI-job `validate-release-tag` (невозможно обойти) + `scripts/release.sh` (эргономика).
- Существующий прод — отдельный runbook в `deploy.md`.

## Этап 1 — CI: validate-release-tag job

**Новый job в `.github/workflows/ci.yml`**, ставится перед `publish-images` и `deploy-bundle` в графе зависимостей.

- `if: startsWith(github.ref, 'refs/tags/v')` — только на релизном теге.
- Шаг `Validate semver`: проверяет `GITHUB_REF_NAME` против `^v[0-9]+\.[0-9]+\.[0-9]+(-rc\.[0-9]+)?$`. Если не матчит — `exit 1` с понятным сообщением («допустимо: v1.2.3 или v1.2.3-rc1; используйте scripts/release.sh»).
- Дополнительно: проверяет, что тег находится на коммите из `main` (защита от тегирования случайной ветки) — `git branch --contains $SHA | grep -qw main`.

**Связывание с существующими job'ами:**
- `publish-images.needs` — добавить `validate-release-tag`. Поскольку у `publish-images` сейчас `if: ... && always() && success()`, а `validate-release-tag` скипается на main-push (не на теге), нужно скорректировать `if` так, чтобы скипавшийся dependency не блокировал main-push. Подход: `needs: [...существующие..., validate-release-tag]` + оставить `success()` — skipped job считается success в `always() && success()`-семантике.
- `deploy-bundle` уже имеет `needs: [publish-images]` и `if: startsWith(github.ref, 'refs/tags/v')` — транзитивно получит валидацию через publish-images.

**Результат:** любой тег `v*` проходит валидацию формата И привязки к main до того, как образы уедут в registry. Некорректный тег (`v1.5`, `v1.2.3-rc`, `release-1`) → CI красный, образы не пушатся.

## Этап 2 — setup.sh: gate против `IMAGE_TAG=latest` на проде + manifest-check

### 2.1. preflight() — конфигурационная проверка
В существующий блок prod-профиля (сразу после проверки `IMAGE_PREFIX`) добавить:
```bash
local _pf_tag
_pf_tag=$(load_env_var IMAGE_TAG latest)
if [[ "$(current_profile)" == "prod" && "$_pf_tag" == "latest" ]]; then
    warn "prod-контур с IMAGE_TAG=latest — это implicit-deploy (ADR-047 запрещает)."
    warn "  Укажите релизный тег: IMAGE_TAG=v1.x.x в .env (см. gh release list)."
    fatal=1
fi
```
Покрывает все точки входа (меню 1/4/6 — все зовут `preflight`).

### 2.2. run_compose() — runtime guard с понятной ошибкой
Перед `docker compose pull` в registry-ветке добавить проверку существования тега в registry:
```bash
# Проверка, что тег существует в registry, до pull — иначе docker compose pull
# выдаёт невнятное "manifest unknown". Даёт оператору сразу понятную ошибку.
if ! docker manifest inspect "${image_prefix}portal-backend:${image_tag}" >/dev/null 2>&1; then
    err "Образ ${image_prefix}portal-backend:${image_tag} не найден в registry." \
        "Проверьте IMAGE_TAG в .env (доступные теги: gh release list / вкладка Packages)."
fi
```
Только в registry-ветке (где `image_prefix` непустой). В local-build ветке (dev) — пропускается.

### 2.3. setup_env() — обновить комментарий про IMAGE_TAG
В heredoc `.env` заменить комментарий:
```
# IMAGE_TAG: latest = последний успешный билд main (ТОЛЬКО dev/experiments);
#   v1.x.x = релизный тег, обязательный для prod-контура (ADR-047). См. gh release list.
#   sha-XXXXXXX = точный коммит (для отката/диагностики).
```
Default оставить `latest` (для dev-контура это корректно — локальная сборка).

## Этап 3 — scripts/release.sh: helper для «ручной деплой по тегу»

Минимальный (~40 строк) скрипт для эргономики релизного процесса:
```
Usage: ./scripts/release.sh <version>    (например: 1.5.0 или v1.5.0, или 1.5.0-rc1)
```
Что делает:
1. Валидирует semver-формат локально (тот же regex, что в CI — `^[0-9]+\.[0-9]+\.[0-9]+(-rc\.[0-9]+)?$`).
2. Проверяет чистый `git status` (нет незакоммиченных изменений).
3. Проверяет, что HEAD синхронизирован с `origin/main` (`git rev-parse HEAD == origin/main`).
4. Проверяет, что тег не существует (`git rev-parse v1.5.0`).
5. Создаёт annotated tag (`git tag -a v1.5.0 -m "Release v1.5.0"`).
6. Пушит тег (`git push origin v1.5.0`) — это и запускает CI publish + deploy-bundle.
7. Выводит ссылку на Actions и подсказку «после зелёного CI: на проде `IMAGE_TAG=v1.5.0` → setup.sh п.6».

Защищает от: грязного дерева, рассинхрона с remote, повторного тега, некорректного формата. CI `validate-release-tag` остаётся вторым барьером (defense-in-depth — если кто-то тегнёт в обход скрипта).

`shellcheck --severity=warning` (CI-gate).

## Этап 4 — Документация

### 4.1. docs/adr.md — новый ADR-047 «Semver-lock prod-деплой»
- **Контекст:** ADR-045 определил `:latest` как «continuous deploy» — любой merge в main потенциально едет на прод. Это implicit-deploy без явного решения; откат = ручная смена тега (легко забыть); непонятно «какая версия на проде». Для интранет-портала с ручной моделью деплоя это неправильный дефолт.
- **Решение:** prod-контур обязан пиниться к релизному тегу `v*` (`IMAGE_TAG=v1.x.x` в `.env`). `:latest` продолжает пушиться в CI (для dev/experiments), но `setup.sh` отвергает его в prod-профиле. Релиз = `scripts/release.sh <ver>` → CI публикует образы + bundle под тегом → оператор ставит `IMAGE_TAG` на проде. Postgres остаётся `:16` rolling (schema ≠ app version).
- **Связь:** уточняет ADR-045 (п.2 тегирования — `latest` больше не прод-дефолт) и ADR-046 (триада bundle↔образы↔commit теперь обязательна, а не опциональна).
- **Альтернативы:** (a) вообще не пушить `:latest` — отвергнуто, ломает migration/dev; (b) GitOps deploy-repo — оверкилл для 1 сервера; (c) авто-deploy staging → прод — не соответствует выбранной ручной модели.
- **Грабли:** (1) существующий прод на `:latest` сломается на следующем pull, если не выставить `IMAGE_TAG=v*` ДО применения gate — см. миграционный runbook в `deploy.md`; (2) `docker manifest inspect` требует сети до registry — в air-gap не сработает, но air-gap и не предполагается (pull-деплой).

### 4.2. docs/deploy.md — обновление §10 + новый миграционный runbook
- **§10.1 (вводный блок):** добавить, что прод пинится к `v*` (semver-lock, ADR-047), `:latest` запрещён.
- **§10.1.a:** убрать «(Опционально) IMAGE_TAG=...» — сделать обязательным шаг: «поставить `IMAGE_TAG=v1.x.x` (см. `gh release list`)».
- **§10.3 (Откат):** добавить откат через `IMAGE_TAG=v1.x.y` (предыдущий релиз), не только `sha-*`.
- **Новый §12 «Миграция с :latest на semver-lock»** — пошаговый runbook:
  1. До мерджа ADR-047: затегать текущий main как `v1.0.0` через `scripts/release.sh` (или вручную) — опубликовать образы+bundle под тегом.
  2. На проде: `IMAGE_TAG=v1.0.0` в `.env` → `docker compose pull` → `up -d` → verify. Снять SHA образа для отката.
  3. Теперь можно мёрджить ADR-047. После мерджа CI продолжит пушить `:latest`, но прод уже на `v1.0.0` и больше `:latest` не возьмёт (gate).
  4. Дальнейшие релизы: `scripts/release.sh 1.1.0` → на проде `IMAGE_TAG=v1.1.0` → setup.sh п.6.
  - С откатом на каждом шаге.

## Что НЕ меняется (гарантия несломанности)
- **`:latest` продолжает пушиться** — существующий прод на `:latest` НЕ сломается моментально после мерджа ADR-047. Сломается только если на нём применят gate (новый setup.sh) — а это и есть момент миграции, описанный в runbook.
- **Dev-контур** — `IMAGE_TAG=latest` остаётся корректным дефолтом (локальная сборка, gate не срабатывает — profile=dev).
- **CI smoke/integration** — используют `IMAGE_TAG=ci` или локальные сборки, gate не трогает.
- **Postgres `:16`** — без изменений.
- **Миграции, migrate.sh, compose-сервис `migrations`** — без изменений.
- **ADR-045 / ADR-046** — не переписываются, только «уточнены ADR-047» в соответствующих пунктах.

## Риски и митигация
1. **Существующий прод на `:latest`** — после применения нового `setup.sh` (gate) следующий `update_production` упадёт в `preflight`, пока не выставлен `IMAGE_TAG=v*`. Это намеренно (явный сигнал «мигрируй»). Runbook описывает порядок: сначала затегать, потом мёрджить.
2. **`docker manifest inspect` нужен network** — если registry недоступен, даст ложный negative. Но registry-деплой сам требует сети, так что это не новая зависимость.
3. **Оператор тегирует в обход `release.sh`** — CI `validate-release-tag` ловит некорректный формат; но привязку к main тоже проверяет. Defense-in-depth.
4. **Забытый `IMAGE_TAG` при первом deploy-bundle** — `setup.sh` gate и `manifest inspect` дают понятные ошибки, не молчат.
