# План: панель «Ошибки инфра-контейнеров» + первые Loki-ruler алерты

## Контекст (что выяснено)

- **Логи-дашборд** `monitoring/grafana/portal-logs.json` (uid `portal-logs`, 7 панелей) не показывает ошибки postgres/redis — у них нет лейбла `level` (plain-text логи, `stage.json` в Alloy их не парсит). Существующая панель ошибок (`id 1`) фильтрует только `{service=~"portal-backend|portal-worker", level=~"error|critical"}`.
- **Loki ruler** сконфигурирован (`monitoring/loki/config.yml:72-82`: local storage `/loki/rules`, `alertmanager_url: http://alertmanager:9093`, `enable_api: true`), но **директория rules не смонтирована** в контейнер Loki (`docker-compose.monitoring.yml:143-145` — только `config.yml:ro` + volume `loki-data`). Rules просто негде хранить → ruler пустой.
- **Алерт-роутинг**: в `alertmanager.yml:47-51` уже есть sub-route `severity = critical → admins-email` (group_wait 0s, repeat 30m). **Менять `alertmanager.yml` не нужно** — оба новых алерта с `severity: critical` автоматически попадут в существующий роут. Добавлять отдельное правило по `alertname` было бы избыточным и рискованным (перекрыло бы наследование).
- **Селектор** для postgres/redis: `compose_service="postgres"` / `compose_service="redis"` (стабильный лейбл из Alloy relabel, без суффикса `-1`).
- **Тексты ошибок** подтверждены (PostgreSQL 16 §20.8, Redis 7): postgres использует литералы `FATAL:`/`PANIC:` (ERROR — шум от плохих запросов, **не** матчем); redis — фразы persistence-сбоев (голый `#` отметать — ловит косметический `overcommit_memory is set to 0` на каждом старте).
- **Ловушка ложных срабатываний**: `FATAL: the database system is starting up` и `... is in recovery mode` — это `FATAL:`-severity, но нормальны при рестарте PG (каждый рестарт даст всплеск). Исключаем их через `!~`.

## Решения (по умолчанию — мои рекомендации)

- **Severity: оба `critical`** (PG FATAL бьёт по доступности для ~300 юзеров; Redis persistence failure — риск потери данных при `--appendonly yes`).
- **Scope панели: 1:1 с алертом** — показываем ровно те строки postgres/redis, на которых стреляют алерты (согласованная пара «видишь строки → понимаешь alert»).

## Изменения (5 файлов)

### 1. `monitoring/loki/rules/fake/portal-loki-rules.yaml` (НОВЫЙ)

> ⚠️ **Критичный путь**: Loki с `auth_enabled: false` использует tenant-id `fake` (дефолт). Rules обязаны лежать в `<storage-dir>/<tenant>/<file>.yaml`, т.е. `fake/portal-loki-rules.yaml`. Файл прямо в `rules/` загружен **не будет** — это №1 причина «ruler молча не подхватил правила».

Содержимое — одна группа `portal-loki` с двумя правилами (конвенция как в Prometheus `portal.yml`: `summary` + `description` с docker-командами, severity+service labels):

```yaml
groups:
  - name: portal-loki
    interval: 1m
    rules:
      # PostgreSQL FATAL/PANIC — connection/system-level (ERROR не трогаем — это шум
      # от плохих запросов). Исключаем transient startup/recovery FATAL (норма при рестарте).
      - alert: PostgresFatalf
        expr: |
          sum by (container) (
            count_over_time(
              {compose_service="postgres"}
                |~ "FATAL:|PANIC:"
                !~ "the database system is starting up|the database system is in recovery mode"
              [5m]
            )
          ) > 2
        for: 2m
        labels:
          severity: critical
          service: postgres
        annotations:
          summary: "PostgreSQL: FATAL/PANIC в логах ({{ $value }} за 5 мин)"
          description: "Более 2 FATAL/PANIC-сообщений в логе postgres за 5 мин (pool exhaustion / auth storm / PANIC). Startup/recovery FATAL исключены. Смотреть: docker compose logs postgres, дашборд Portal — Logs (панель «Ошибки инфра-контейнеров»)."

      # Redis persistence/connection failures (AOF+RDB при --appendonly yes --maxmemory).
      # Фразы вместо голого '#' — маркер '#' ловит косметический overcommit_memory на старте.
      - alert: RedisPersistenceFailure
        expr: |
          sum by (container) (
            count_over_time(
              {compose_service="redis"}
                |~ "Background saving error|Write error saving DB on disk|Can't save in background|fork: Cannot allocate memory|Error accepting a client connection|Error moving cur APPEND ONLY FILE|Error removing APPEND ONLY FILE|OOM command not allowed when used memory"
              [5m]
            )
          ) > 1
        for: 2m
        labels:
          severity: critical
          service: redis
        annotations:
          summary: "Redis: сбой persistence/подключений ({{ $value }} за 5 мин)"
          description: "Ошибки RDB/AOF-сохранения или приёма соединений в логе redis за 5 мин. Проверить: docker compose logs redis, свободное место на volume redis-data, память контейнера (maxmemory 256mb)."
```

### 2. `monitoring/docker-compose.monitoring.yml` — Loki volumes (1 строка)

Добавить bind-mount директории rules в сервис `loki` (строка 144-145):

```yaml
    volumes:
      - ./monitoring/loki/config.yml:/etc/loki/config.yml:ro
      - ./monitoring/loki/rules:/loki/rules:ro   # ← НОВОЕ: rules для ruler (tenant fake/)
      - loki-data:/loki
```

`:ro` — ruler только читает (рабочая директория `/loki/rules-tmp` внутри volume). Bind-mount перекрывает путь внутри `loki-data` volume — это безопасно, в `/loki/rules` никто не пишет.

## Верификация (DoD)

1. **Lint/yaml**: `python -c "import yaml; yaml.safe_load(open('monitoring/loki/rules/fake/portal-loki-rules.yaml'))"` + `python -c "import json; json.load(open('monitoring/grafana/portal-logs.json'))"` — валидность файлов.
2. **Развёртывание**: `docker compose -f docker-compose.yml -f monitoring/docker-compose.monitoring.yml up -d loki` ( recreate подхватит новый mount; `--build` не нужен — образ не менялся).
3. **Ruler подхватил правила** (главная проверка — №1 причина тихих провалов):
   - `curl -s http://localhost:3100/loki/api/v1/rules` → должны увидеть группу `portal-loki` с обоими правилами.
   - `docker compose logs loki 2>&1 | grep -i ruler` → нет ошибок загрузки.
4. **Панель в Grafana**: открыть Portal — Logs → внизу панель «Ошибки инфра-контейнеров»; проверить, что селектор возвращает пустой поток (ошибок сейчас нет — это нормально) и не падает с parse error. Скомпилировать тестовую FATAL-строку: `docker compose exec postgres sh -c "echo 'FATAL: test alert probe' >&2"` (или `docker logs` подделать) — убедиться, что строка появляется в панели (затем убрать).
5. **Маршрут алерта**: в Alertmanager UI (`:9093` → Status → Routes) проверить, что `PostgresFatalf`/`RedisPersistenceFailure` с `severity=critical` резолвятся в `admins-email`.

## Грабли / контекст (для хэндоффа)

- **tenant `fake/`** — без этого поддиректория ruler молча проигнорирует файл. Подтвердить через `/loki/api/v1/rules`.
- **`:ro` mount перекрывает volume-путь** `/loki/rules` — безопасно (ruler оттуда только читает, рабочий путь `/loki/rules-tmp`).
- **Polling**: Loki опрашивает rules-директорию раз в минуту (`ruler.poll_interval` default) — после recreate правила появятся в течение ~1 мин, не мгновенно.
- **ERROR postgres не в алерте намеренно** — это шум от плохих SQL-запросов приложения (constraint violations). Если позже окажется, что и ERROR нужно ловить — завести отдельный `PostgresErrorRate` с rate-порогом, а не расширять текущий.
- **Изменения требуют recreate контейнера Loki** (новый volume mount), `restart` не подхватит.
