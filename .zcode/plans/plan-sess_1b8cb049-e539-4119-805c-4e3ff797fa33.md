## Блок 1 — [C1] `.env.example` дефолт-секреты + валидатор Settings

**Цель:** защитить новые деплои от «скопировал `.env.example` → забыл сменить секреты». Существующий прод не затрагивается.

### Изменения

**`.env.example`** — убрать опасные дефолты:
- `SECRET_KEY=` (пусто) + комментарий: «Сгенерируйте: `openssl rand -hex 48`. Обязателен в production (≥48 символов, не дефолт).»
- `LOCAL_AUTH_ENABLED=false` (backdoor закрыт по умолчанию; включается осознанно через setup.sh)
- `ADMIN_EMAIL=` (пусто)
- `ADMIN_PASSWORD=` (пусто)
- Комментарий: «При пустых ADMIN_* bootstrap пропускается. Запустите `./setup.sh` для интерактивной генерации.»

**`backend/app/core/config.py`** — добавить production-валидаторы в `Settings`:
- Новый `@field_validator("secret_key")` (mode after): при `environment == "production"`:
  - block-list известных дефолтов: `change_me_32_chars_minimum_secret_key_here`, `ci_*` (CI-фикстуры)
  - `len(secret_key) >= 48` (текущий `min_length=32` поднять нельзя — сломает dev/CI; ужесточаем только в prod)
- Новый `@field_validator("admin_password", mode="after")`: при `environment == "production"` reject `change_me_on_first_login`
- `is_production` уже есть — использовать его в валидаторах

**`setup.sh::preflight()`** — добавить prod-gate по аналогии с semver-lock (строки ~1233-1258). В блоке `if [[ "$(current_profile)" == "prod" ]]`:
- Проверка `SECRET_KEY` не равно дефолту `change_me_32_chars_minimum_secret_key_here` → иначе `warn` + `fatal=1`
- Проверка `len(SECRET_KEY) >= 48` → иначе `warn` + `fatal=1`
- Проверка `ADMIN_PASSWORD != "change_me_on_first_login"` → иначе `warn` + `fatal=1`

**`backend/tests/unit/test_config.py`** — расширить существующий файл:
- `test_production_rejects_default_secret_key` — ValidationError в prod с дефолтом
- `test_production_rejects_short_secret_key` — 32-символьный ключ отклонён в prod (но работает в dev)
- `test_production_rejects_default_admin_password` — `change_me_on_first_login` отклонён в prod
- `test_dev_accepts_short_secret_key` — 32 символа OK в dev (регресс: не сломали dev/CI)
- `test_dev_accepts_default_admin_password` — dev/staging не валидирует (обратная совместимость)

### Риск для прода
**Нулевой.** Валидаторы срабатывают только при `environment == "production"`. Существующий prod-`.env` имеет валидный SECRET_KEY (сгенерированный setup.sh) — пройдёт валидацию. Если вдруг чей-то prod использует дефолт — это именно то, что мы хотим выявить (fail-closed).

## Блок 2 — [C2] Redis от root в compose

**Цель:** запуск redis-server от unprivileged user вместо root.

### Изменения

**`docker-compose.yml`** сервис `redis` (строки 34-64) — добавить `user: "999:999"`.

**Предварительная верификация UID** (через bash, read-only):
```bash
docker run --rm redis:7-alpine@sha256:e7723ff73d963f5cc6d9c4643ea3d989527a402a319239054e9472a7fb9219a2 id redis
```
Ожидание: `uid=999(redis) gid=999(redis) groups=999(redis),1(bin),2(daemon)...`. Если UID отличается — подставить фактический.

**ACL-файл `/tmp/redis.acl`**: создаётся в entrypoint через `printf > /tmp/redis.acl && chmod 600`. После дропа прав redis-юзер — владелец root (т.к. printf работает от root до `exec redis-server`). Проверить: `redis-server` читает ACL-файл при старте ДО дропа прав? Нужна верификация — если redis-server дропает права через `user:` compose, он стартует уже от redis-юзера, и `printf` в entrypoint тоже выполнится от redis-юзера (entrypoint выполняется от `user:`). Значит ACL-файл будет redis-owned — OK.

### Верификация (read-only, через docker exec после деплоя — в код не идёт)
- `docker compose exec redis id` → `uid=999(redis)`
- `docker compose exec redis ps aux | head` → redis-server от uid≠0
- `redis-cli AUTH ... ping` → PONG

### Риск для прода
**Низкий.** `user:` compose-директива применяет UID к entrypoint. Стратегия blue-green: проверить `id redis` в образе → поднять второй redis-контейнер с `user:` → прогнать healthcheck → переключить. Runbook уже в аудите (`audit.md` §«[C2] Что нужно сделать на проде»).

## Блок 3 — [H3] audit metadata::text → jsonb GIN (вариант A: jsonpath)

**Цель:** использовать существующий GIN-индекс миграции 033 вместо Seq Scan.

**Выбранный подход:** jsonpath `metadata @? '$.** ? (@ like_regex "q" flag "i")'` — ищет подстроку во ВСЕХ строковых значениях JSON (рекурсивно). Использует GIN `jsonb_path_ops`.

### Семантическое отличие от текущего ILIKE (важно)
Текущий `metadata::text ILIKE '%q%'` ищет подстроку в **сериализации целиком** (ключи + значения + пунктуация). Jsonpath ищет только по **строковым значениям**. Практические следствия:
- ✅ Поиск `192.168.1.5` (значение) — найдётся
- ✅ Поиск `отчёт` в old_value/new_value — найдётся
- ❌ Поиск `ip_address` (имени ключа) — НЕ найдётся
- ❌ Поиск числовых значений (напр. `42`) — НЕ найдётся (jsonpath regex применяется к строкам; числа нужно приводить через `.type() == "string"`)

Это сознательное упрощение: админы ищут по содержимому событий (значения), а не по именам полей. По email/заголовку поиск остаётся ILIKE (btree+trgm).

### Изменения

**`backend/app/api/audit.py::_build_filters`** (строки 59-65) — заменить `metadata::text ILIKE` на jsonpath:
```python
if q:
    clauses.append(
        "(coalesce(user_email,'') ILIKE :q "
        "OR coalesce(resource_title,'') ILIKE :q "
        "OR coalesce(metadata::text,'') LIKE :q_md_text)")  # временно — см. ниже
```
**Финальная версия** — jsonpath через bind-параметр:
```python
if q:
    # metadata: jsonpath regex по строковым значениям (использует GIN jsonb_path_ops, миграция 033)
    # email/title: ILIKE (btree+trgm)
    clauses.append(
        "(coalesce(user_email,'') ILIKE :q "
        "OR coalesce(resource_title,'') ILIKE :q "
        "OR metadata @? :q_jsonpath)")
    params["q"] = f"%{q}%"
    # экранирование regex-спецсимволов в запросе пользователя
    escaped = re.escape(q)
    params["q_jsonpath"] = f'$.** ? (@ like_regex "{escaped}" flag "i")'
```

**Важно — bind-параметр для jsonpath:** PG не поддерживает `@? $1` с внешней переменной-путём напрямую, но `@? :q_jsonpath` работает, т.к. параметр — это строка-литерал jsonpath. Проверить в testcontainers-тесте (см. ниже).

**`re.escape`** — защита от regex-инъекции (пользователь вводит `.*` → найдёт всё; `re.escape` делает его литералом).

### Тесты

**`backend/tests/integration/test_audit_metadata_jsonpath.py`** (новый, testcontainers):
- Поднимает PG через testcontainers (паттерн из `tests/integration/conftest.py`)
- Применяет миграции (включая 033 — GIN-индекс)
- Вставляет ~50k строк audit_log с разнообразными metadata
- **Baseline-тест (DoD):** `EXPLAIN (FORMAT TEXT)` обоих вариантов:
  - Старый `metadata::text ILIKE '%q%'` → Seq Scan (документируем в тесте)
  - Новый `metadata @? '$.** ? (@ like_regex ...)'` → Bitmap Index Scan по `idx_audit_log_metadata_gin`
  - Assert: новый план содержит `"Index Scan using idx_audit_log_metadata_gin"` или `"Bitmap Index Scan on idx_audit_log_metadata_gin"`
- **Корректность:**
  - Поиск по значению в metadata (`{"ip": "192.168.1.5"}`, q=`192.168`) → найдено
  - Поиск по old_value (`{"old_value": "draft", "new_value": "published"}`, q=`publish`) → найдено
  - Regex-инъекция: q=`.*` → не находит «всё» (re.escape), ведёт себя как литерал `.*` (ничего или конкретные значения с точкой-звездой)
  - Case-insensitive: q=`PUBLISH` находит `published` (flag "i")
  - Числа НЕ ищутся: q=`42` не находит `{"count": 42}` (документированное ограничение)
  - email/title ILIKE продолжает работать (q по user_email)

**`backend/tests/unit/test_audit.py`** — обновить `_build_filters` тесты под новый params-ключ `q_jsonpath`.

### Риск для прода
**Низкий-средний.** Семантика поиска по metadata чуть меняется (см. выше). Миграция не нужна — GIN-индекс миграции 033 уже на проде. Откат: вернуть `metadata::text ILIKE` одной правкой. Стратегия: testcontainers-тест верифицирует план локально; после деплоя оператор проверяет `EXPLAIN ANALYZE` на проде (runbook).
