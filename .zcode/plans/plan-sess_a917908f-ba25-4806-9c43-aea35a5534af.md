# Этап 15: Фикс CI-джобов compose-smoke + integration (ранее skip'ались)

## Контекст (не моя регрессия)

После этапа 14 (mypy cleanup → `ruff+mypy` зелёный) разблокировались два CI-джоба, которые **раньше skip'ались**: `compose-smoke` и `backend-integration`. Они падали в **каждом** из последних ~10 коммитов (с 17 июля), но это было невидимо, потому что `ruff+mypy` падал раньше и весь downstream-skip'ался. Моя работа по mypy-очистке «подняла завесу» — теперь видны реальные старые проблемы.

**Симптомы (из CI run 29748720284):**
1. `compose-smoke` → `lstat /certs: no such file or directory` на `COPY certs/*.crt`
2. `backend-integration` → 3 класса ошибок: `cannot insert non-DEFAULT into number`, `duplicate key email`, `ck_users_role violation (role='user')`

## План (4 правки + верификация)

### 1. Корневой сертификат Минцифры → в git (фикс compose-smoke)

- **`.gitignore`**: после `*.crt` добавить исключение `!backend/certs/russian_trusted_root_ca.crt`
- **`git add -f backend/certs/russian_trusted_root_ca.crt`** — закоммитить публичный сертификат (выложен на gu-st.ru, не секрет)
- **`backend/certs/README.md`**: rename `.pem`→`.crt` в упоминаниях (сейчас README говорит про `russian_trusted_root_ca.pem`, а файл `.crt`)
- Обоснование: README в `backend/certs/` явно описывает, что сертификат должен быть в этой папке и используется на этапе сборки образа. CI получает чистый checkout — без сертификата Docker build падает.

### 2. `role="user"` → `role="reader"` в хелпере (фикс ck_users_role violation)

**Файл:** `backend/tests/integration/test_helpdesk_media_integration.py`

- Строка 35: `async def _create_db_user(db, role: str = "user"):` → `role: str = "reader"`
- Обоснование: валидные роли в `ck_users_role` — `reader|editor|admin` (`app/models/user.py:25`). Роли `user` не существует; "обычный пользователь" = `reader` (дефолт модели). Затронуто 11 тест-кейсов.

### 3. Убрать явный `number=` из тестов (фикс cannot insert non-DEFAULT)

#### 3a. `backend/tests/integration/test_helpdesk_media_integration.py` (8 вызовов)

- Строка 58: `async def _create_db_ticket(db, requester_id, number: int = 1)` → убрать параметр `number`
- Строки 61-65: `HelpdeskTicket(number=number, ...)` → `HelpdeskTicket(...)` (без `number`)
- Удалить все явные `number=100001/100002/...` из 8 вызовов (строки 142, 164, 175, 186, 206, 222, 232, 243)
- Тесты используют `number` только для путей к файлам (`TKT-{number}/inline/`) — это `ticket.number` после INSERT, IDENTITY сгенерирует автоматически.

#### 3b. `backend/tests/integration/test_helpdesk_fts.py` (14 кейсов, 22 invocation'а)

- Строки 32-50: `def _make_ticket(*, subject, ..., number: int | None = None)` → убрать параметр `number`
- Убрать `number=number or abs(hash(subject)) % 1000000` из тела — IDENTITY сгенерирует сам
- В тестах assertions переключить с `number` на `id`: вместо `assert {t.number for t in res} == {400001}` → `assert {t.id for t in res} == {t1.id}`. FTS ищет по тексту (subject/description), предсказуемый number не нужен — достаточно сослаться на конкретные id созданных тикетов.
- Удалить явные `number=400001/400002/...` из всех вызовов `_make_ticket(...)`.

### 4. duplicate key email — побочный эффект, отпадёт

В `test_admin_users_db.py:217` (`test_email_unique_constraint_on_create`) логика корректна: создаёт дубликат, ловит `IntegrityError`, делает `rollback()`. Предположительно ошибка в логе — побочный эффект того, что **предыдущий тест** (например, `test_helpdesk_media_integration`) оставил сессию в невалидном состоянии из-за `IntegrityError` от `role="user"` без корректного rollback. После фиксов #2 и #3 этот тест должен пройти. Если всё же упадёт — следующий заход починит точечно.
