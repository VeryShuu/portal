# План: Full observability upgrade — exporters + ARQ-метрики + новые дашборды/алерты

## Контекст проблемы
Сейчас Prometheus скрейпит **только backend `/metrics`**. Главные узкие места интранет-портала (БД, Redis, диск) — слепая зона. Плюс 2 панели на Overview-дашборде мёртвые (ссылаются на удалённые ARQ-метрики). Цель: добавить 4 exporter'а (PostgreSQL, Redis, Host, Nginx), оживить ARQ-счётчики, расширить дашборды и алерты — одним заходом, по best practices.

## Часть 1. Exporter'ы (infra-метрики)

### 1.1. `monitoring/docker-compose.monitoring.yml` — 4 новых сервиса
Все по образцу существующих overlay-сервисов: `networks: [internal, external]`, `security_opt: [no-new-privileges:true]`, `restart: unless-stopped`, `logging: *default-logging`. Образы зафиксированы по версиям (проверены на Docker Hub/GitHub):

| Сервис | Образ | Ключевые env /Volumes |
|---|---|---|
| `postgres-exporter` | `prometheuscommunity/postgres-exporter:v0.20.1` | `DATA_SOURCE_NAME: postgresql://${POSTGRES_USER:-portal}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB:-portal}?sslmode=disable`; порт контейнера 9187 |
| `redis-exporter` | `oliver006/redis_exporter:v1.77.0` | `REDIS_ADDR: redis://redis:6379`, `REDIS_PASSWORD: ${REDIS_PASSWORD}`; порт 9121 |
| `node-exporter` | `prom/node-exporter:v1.12.1` | volumes `/proc:/host/proc:ro`, `/sys:/host/sys:ro`, `/:/rootfs:ro`; command `--path.procfs=/host/proc --path.sysfs=/host/sys --path.rootfs=/rootfs --collector.filesystem.mount-points-exclude='^/(dev\|proc\|sys\|var/lib/docker/.+)($\|/)'`; порт 9100 |
| `nginx-exporter` | `nginxinc/nginx-prometheus-exporter:v1.4.0` | `ARGS: -nginx.scrape-uri=http://nginx:8080/stub_status`; порт 9113 |

Никаких новых секретов в `.env` — `POSTGRES_PASSWORD`/`REDIS_PASSWORD` уже там, compose интерполирует автоматически.

### 1.2. Nginx: добавить `stub_status` — `nginx/templates/proxy_locations.conf.tmpl`
Добавить location-блок (доступный только внутри `internal`-сети, не светится наружу):
```nginx
location = /stub_status {
    stub_status;
    allow 172.16.0.0/12;   # portal_internal bridge
    allow 127.0.0.1;
    deny all;
    access_log off;
}
```
stub_status слушает на том же порту 80 — exporter будет скрейпить `http://nginx:80/stub_status`. Но `proxy_locations.conf.tmpl` подключается в server-блоки, которые слушают 80/443 — stub_status будет доступен на 80 (http) внутри сети. ✅

## Часть 2. ARQ-счётчики (оживить панели 13-14)

**Архитектурное ограничение**: worker — отдельный процесс; метрики экспортирует только API через `/metrics`. arq 0.26 **не передаёт** результат/исключение в `on_job_end`. Решение — повторить существующий cross-process паттерн через Redis snapshot:

**Backend-изменения:**
1. **`backend/app/core/metrics.py`** — новые метрики:
   - `Counter("portal_arq_jobs_total", labelnames=("function", "status"))` — status ∈ {started, succeeded, failed}
   - `Histogram("portal_arq_job_duration_seconds", labelnames=("function",))`
2. **`backend/app/worker/tasks/metrics.py`** — декоратор `@track_arq_job` + helper. Декоратор ставится на task-функции (покрывает и `functions`, и `cron_jobs`, т.к. обе ссылаются на сами функции). В finally: атомарно `HINCRBY arq:metrics:jobs {function}:{status} 1` + `HINCRBY arq:metrics:job_ms {function} <elapsed>`. Используется Redis-py `hincrby` (атомарно, безопасно при concurrency).
3. **`backend/app/worker/main.py`** — обернуть в `@track_arq_job` все 26 функций в `functions` и cron-задачи (применяется через регистрацию: либо декоратор на самих функциях в их модулях, либо `func(track_arq_job(fn))` wrapper в WorkerSettings). Выбираю **декоратор на уровне WorkerSettings** — минимальная правка в одном файле, не трогает 15+ модулей задач.
4. **`refresh_custom_metrics`** — добавить чтение `HGETALL arq:metrics:jobs` / `arq:metrics:job_ms` в snapshot dict (формат `{"arq_jobs": {"process_photo_upload:succeeded": 42, ...}, "arq_job_ms_count": {...}, "arq_job_ms_sum": {...}}`).
5. **`backend/app/middleware/metrics.py`** — в `hydrate_custom_metrics` гидрировать Counter/Histogram из snapshot. Counter-гидратация: `counter.labels(...).inc(value - current)` через отслеживание последнего значения в кэше middleware (Prometheus counter не имеет `.set()`, поэтому дельта-инкремент от последнего snapshot — стандартный приём для cross-process counter).

**Тесты:** `backend/tests/unit/test_worker_metrics.py` — проверка декоратора (success → started+succeeded инкремент), failure → failed,Redis hincrby моки; `test_metrics_hydration` — гидратация из snapshot.

> ⚠️ **Альтернатива учтена**: prometheus_client multiproc mode (`PROMETHEUS_MULTIPROC_DIR`) сложнее для overlay, т.к. требует shared volume + reset-логики. Redis-snapshot-паттерн уже работает в проекте — держу единый механизм.

### 3.2. Новый дашборд `monitoring/grafana/portal-infrastructure.json` (uid: `portal-infra`)
Структура — 4 секции по образцу Overview (rows + panels), datasource `{"type":"prometheus","uid":"prometheus"}`:

**PostgreSQL** (postgres-exporter метрики `pg_*`):
- Connections: `pg_stat_activity_count` / `pg_settings_max_connections{setting="max_connections"}` (использование пула)
- Cache hit ratio: `pg_stat_database_blks_hit / (blks_hit + blks_read)` по БД
- Transaction ID wraparound: `pg_database_xid_age` (топ БД)
- DB size: `pg_database_size_bytes`
- Slow queries: `pg_stat_activity_max_tx_duration` (long-running transactions)
- Temp files / deadlocks: `rate(pg_stat_database_deadlocks[5m])`

**Redis** (`redis_*`):
- Memory used / max: `redis_memory_used_bytes / redis_memory_max_bytes`
- Connected clients / evicted keys: `redis_connected_clients`, `rate(redis_evicted_keys_total[5m])`
- Keyspace hit rate: `redis_keyspace_hits_total / (hits + misses)`
- Persistence: `redis_rdb_last_save_timestamp_seconds`

**Host** (`node_*`):
- Disk space: `node_filesystem_avail_bytes{mountpoint="/data"}` / `node_filesystem_size_bytes` (критично — /data/photos)
- Disk I/O: `rate(node_disk_io_time_seconds_total[5m])`
- CPU: `sum(rate(node_cpu_seconds_total{mode!="idle"}[5m])) by (instance)`
- RAM: `node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes`
- Load: `node_load1`, `node_load5`

**Nginx** (`nginx_*` из stub_status):
- Active connections: `nginx_connections_active`
- Requests rate: `rate(nginx_http_requests_total[5m])`
- Reading/Writing/Waiting: `nginx_connections_reading/writing/waiting`

## Часть 4. Алерты — расширить `monitoring/alerts/portal.yml`

Новые правила (все с `for:` ≥ 2-5m, по существующей философии):

**Инфраструктура:**
- `PortalPGConnectionsHigh` — `pg_stat_activity_count / pg_settings_max_connections > 0.8` for 5m (warning)
- `PortalPGCacheHitLow` — cache ratio < 0.9 for 10m (warning)
- `PortalPGWraparound` — xid_age > 1.5e9 (warning) — на случай autovacuum-проблем
- `PortalRedisMemoryHigh` — memory_used/max > 0.9 for 5m (warning)
- `PortalRedisEvictions` — `rate(redis_evicted_keys_total[5m]) > 10` for 5m (warning)
- `PortalDiskSpaceLow` — `node_filesystem_avail_bytes / size < 0.15` for 5m (critical, mountpoint=/data)
- `PortalNginxConnectionsHigh` — active connections > 1000 for 5m (warning)

## Замечания
- **node_exporter в WSL2**: метрики хоста (disk/CPU) читаются через bind-mount `/proc`/`/sys`/`/` — это покажет хост-статистику WSL2-машины, где живут `/data/photos` и Docker volumes. Достаточно для disk-full-алерта.
- **nginx-exporter + stub_status**: stub_status даёт базовые connection-метрики (active/accepts/requests/reading/writing/waiting). RED через backend уже покрыт; для request_time-перцентилей останется Loki (как сейчас).
- **Пересборка образов**: backend-код (ARQ-метрики) требует `docker compose build backend` (образ вкомпилирован). nginx stub_status требует `docker compose build nginx`. Exporter'ы — готовые образы, без сборки.
- **Commit**: пользователем. Готовое сообщение в конце сессии.
