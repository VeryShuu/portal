# План: Мониторинг бизнес-процессов и интеграций

## Контекст
Текущий мониторинг силён по инфраструктуре (БД/Redis/диск/CPU) и backend RED, но почти слеп по бизнес-процессам. Email/Messenger outbox полностью невидимы в Prometheus (письма копятся/DLQ-ятся молча). Интеграции (Keycloak/SMTP/Collabora) не имеют continuous-probes. Synthetic-проверок нет совсем. Цель: заполнить все 4 пробела.

---

## Часть 1. Outbox-метрики (email + messenger)

**Архитектура:** тот же cross-process паттерн (worker → Redis snapshot → API hydrate), что уже работает для audit/SSE/ARQ.

**`backend/app/core/metrics.py`** — 6 новых gauge:
```
portal_email_outbox_pending        (дублей email_outbox WHERE status='PENDING')
portal_email_outbox_dlq            (WHERE status='DLQ')
portal_email_outbox_sending_stale  (WHERE status='SENDING' AND updated_at < NOW()-10min)
portal_messenger_outbox_pending
portal_messenger_outbox_dlq
portal_messenger_outbox_sending_stale
```

**`backend/app/worker/tasks/metrics.py`** — расширить `refresh_custom_metrics` (блок DB): один SQL с `count(*) ... GROUP BY status` для каждой таблицы. Лёгкие запросы (partial-index `idx_email_outbox_status_created` покрывает). Запись в snapshot: `{"email_outbox": {"pending": N, "dlq": N, ...}, "messenger_outbox": {...}}`.

**`backend/app/middleware/metrics.py`** — добавить hydration-блок: `for kind, val in snap.get("email_outbox", {}).items(): gauge.set(val)`. Зеркало для messenger.

**Тесты** — расширить `test_worker_metrics_tasks.py` (mock hgetall + новый DB-запрос) и `test_hydrate_custom_metrics.py` (hydratция outbox-гauges).

## Часть 2. Integration health-probes (ARQ cron)

**Новая задача** `backend/app/worker/tasks/integration_health.py` — `probe_integrations(ctx)`:
- Запускается по cron каждые 60с (`second={0}`).
- Проверяет каждую интеграцию через httpx с коротким timeout (3-5с), ловит все исключения (probe сам никогда не должен ронять worker).
- Результат → Redis hash `integration:health` (как snapshot): `{"keycloak": "1", "nextcloud": "1", "smtp": "0", "collabora": "1"}` (1=ок, 0=упал) + `integration:health:age` (last-check timestamp).

**Проверки:**
| Интеграция | Как проверяем | Timeout |
|---|---|---|
| Keycloak | `GET {keycloak_url}/realms/{realm}/.well-known/openid-configuration` (public endpoint, без auth) | 5с |
| Nextcloud | `GET {nc_url}/status.php` (существует `health_check()`) — reuse существующий метод | 3с |
| SMTP | TCP connect к `host:port` через `asyncio.open_connection` (без отправки письма) | 3с |
| Collabora | `GET {nc_url}/index.php/apps/richdocuments/` или через NC proxy — если модуль richdocuments активен | 3с |

Каждая проверка gated за своим флагом (Keycloak — за `keycloak-settings.json` presence; NC — за `modules.nextcloud.enabled`; SMTP — за `email-settings.json` host не пустой; Collabora — за `modules.nextcloud.enabled`).

**`backend/app/core/metrics.py`** — 4 gauge:
```
portal_integration_up{integration="keycloak|nextcloud|smtp|collabora"}  (1/0)
```

**`refresh_custom_metrics`** — дополнительно читает `integration:health` hash и кладёт в snapshot. `middleware/metrics.py` — hydrate gauge по label.

**Обёртка `track_arq_job`** НЕ применяется к `probe_integrations` (это periodic-probe, не user-triggered job) — ставится в `cron_jobs` напрямую, как `refresh_custom_metrics`.

**Тесты** — `test_integration_health.py`: моки httpx для up/down случаев, gating-логика (пропуск если модуль выключен).

## Часть 3. Расширение `/ready`

**`backend/app/api/health.py`** — добавить опциональные проверки (gated, non-fatal-by-default):
- Keycloak: reuse probe-логику, но **non-fatal** — если Keycloak unreachable, `/ready` возвращает 200 с warning-полем (логин через local-auth ещё работает). Обоснование: Keycloak-down ≠ portal-down (local-auth fallback).
- SMTP: проверка только если `email-settings.json` host не пустой; **non-fatal** (письма могут подождать, портал работает).
- Collabora: gated за `modules.nextcloud.enabled`; **non-fatal**.

Все новые проверки возвращают **status per-component** в JSON-body, но не делают `/ready` красным (только DB/Redis — fatal, как сейчас). Это даёт Kubernetes/Docker healthcheck видимость без капризности.

**Тесты** — расширить `test_health.py`: проверка что `/ready` 200 при упавшем Keycloak, и что body содержит per-component статус.

## Часть 4. Synthetic-проверки (user-flow через Playwright)

**Архитектура:** расширить `screenshot-service/main.py` новым endpoint `/probe` (reuse Chromium + Playwright, который уже запущен). Запускается ARQ cron из backend каждые 5 мин → вызывает screenshot-service → результат → Redis → metrics.

**`screenshot-service/main.py`** — новый `POST /probe`:
- Auth через `X-Screenshot-Secret` (как `/screenshot`, `/pdf`).
- Тело: `{flow: "login_and_load"}` — именованный flow (не arbitrary steps, безопасность).
- Flow `login_and_load`: navigate → `http://frontend:80/login` (internal) → local-auth login через `E2E_ADMIN_EMAIL`/`E2E_ADMIN_PASSWORD` env → wait `#app` → assert URL не `/login` → return `{ok: true/false, elapsed_ms, step_failed?}`.
- Использует local-auth (`POST /api/v1/auth/local/login`) — **не** OIDC redirect dance (избегаем хрупкости Keycloak-form + MFA).
- Chromium на internal-сети, target `frontend:80`/`backend:8000` — исключение из SSRF-allowlist (service-to-service).

**`backend/app/worker/tasks/synthetic_probe.py`** — `run_synthetic_probe(ctx)`:
- Cron каждые 5 мин (`minute={0,5,10,...}` или `minute=set(range(0,60,5))`).
- `httpx.post(screenshot_service_url + "/probe", json={flow}, headers={secret})`, timeout 30с.
- Результат → Redis hash `synthetic:probe` → snapshot → gauge `portal_synthetic_probe_ok{flow}` (1/0) + `portal_synthetic_probe_duration_seconds{flow}`.

**Env:** `E2E_ADMIN_EMAIL`/`E2E_ADMIN_PASSWORD` нужны в worker-окружении. Добавить в `.env.example` (с пометкой "для synthetic-проверок, можно переиспользовать тестовый аккаунт"). Если не заданы — probe skip-ается (gated).

**Тесты:**
- screenshot-service: unit-test `/probe` handler (mock browser, success/fail).
- backend: `test_synthetic_probe.py` — mock httpx, проверка записи в Redis, gating при отсутствии кредов.

## Порядок реализации
1. **Часть 1** (outbox-метрики) — простая, наибольшая ценность, pure-backend. Сначала.
2. **Часть 2** (integration probes) — worker task + httpx probes. Зависит от тех же metrics-pattern'ов.
3. **Часть 5a** (alerts + dashboard-панели для Части 1-2) — после того как метрики подтвердятся на live-стеке.
4. **Часть 3** (/ready расширение) — аккуратный, non-fatal подход.
5. **Часть 4** (synthetic probes) — самая сложная (screenshot-service endpoint + Playwright flow + env). Последняя.
6. **Часть 6** (документация) — финал.
7. Тесты пишутся синхронно с каждой частью (по AGENTS.md convention).

## Замечания
- **No new secrets required** для Части 1-3 (outbox-данные уже в БД; probes используют существующие system.json/secrets). Для Части 4 нужен тестовый аккаунт (E2E_ADMIN_*).
- **Zero-downtime**: все изменения — новые gauge/endpoint/cron, не трогают существующие миграции/схемы.
- **Cross-process**: все worker-side metrics идут через Redis snapshot (единый механизм, не multiproc).
- **Сложность synthetic (Часть 4)**: screenshot-service endpoint + Playwright flow — самая объёмная часть. Если времени мало — можно отложить её отдельно, Части 1-3 дают основной coverage.
- **Пересборка образов**: backend (worker cron + metrics) + screenshot-service (/probe endpoint).
