# План: Метрики пула соединений backend'а (П.3)

## Контекст

Сейчас `PortalPGConnectionsHigh` смотрит только на сторону БД (`pg_stat_activity`). Но connection leak в коде (незакрытая SQLAlchemy-сессия) проявится в **пуле приложения раньше**, чем в PG, — а мы об этом не узнаем. Добавляем прямую метрику пула и алерт на насыщение.

Разведка подтвердила: engine — module-level singleton (`app/core/database.py:16`), пул `AsyncAdaptedQueuePool`, методы `checkedout()`/`checkedin()` синхронные. Пул — состояние API-процесса, **не в Redis** → обновлять напрямую из engine при scrape.

**П.8 пропускается:** разведка показала отсутствие cardinality-бага (nginx=1 стрим, лейбл `level` отсутствует, а не пустой). Текущий фильтр `{container=portal-nginx-1} | json | status>=500` рабочий. Это лишь UX-косметика, не стоящая сейчас работы.

## Реализация П.3

### 1. `backend/app/core/metrics.py` — новый gauge
```python
db_pool_size = Gauge(
    "portal_db_pool_size",
    "SQLAlchemy AsyncAdaptedQueuePool connections in the API process "
    "(in_use = checked out; idle = checked in). Compare in_use to "
    "portal_db_pool_limit for saturation.",
    labelnames=("state",),
)
db_pool_limit = Gauge(
    "portal_db_pool_limit",
    "Max connections the API pool will open (db_pool_size + db_max_overflow).",
)
```
Два gauge'а: `portal_db_pool_size{state}` (in_use/idle) и `portal_db_pool_limit` (фиксированный capacity). Separately exposing limit позволяет PromQL считать долю насыщения (`portal_db_pool_size{state="in_use"} / portal_db_pool_limit`).

### 2. `backend/app/middleware/metrics.py` — обновление при scrape
В `hydrate_custom_metrics`, внутри блока `if request.url.path == "/metrics":`, **до** Redis-read (т.к. не зависит от snapshot), в общем try/except:
```python
# Пул — состояние API-процесса, не из Redis. Читаем напрямую из engine.
from app.core.database import engine
from app.core.config import get_settings
_settings = get_settings()
_metrics_mod.db_pool_limit.set(_settings.db_pool_size + _settings.db_max_overflow)
_metrics_mod.db_pool_size.labels(state="in_use").set(engine.pool.checkedout())
_metrics_mod.db_pool_size.labels(state="idle").set(engine.pool.checkedin())
```
Ленивый импорт `engine` внутри функции (как `load_system_settings` в `_require_metrics_metrics`), чтобы не плодить import-time coupling. Обёрнуто в существующий `except Exception → metrics.hydrate_failed` (никогда не ломает `/metrics`).

**Smoke-test первым делом** при реализации: проверить `type(engine.pool).__name__` и вызовы `checkedout()`/`checkedin()` в контейнере (subagent отметил, что поведение `AsyncAdaptedQueuePool` стоит проверить на реальном runtime).

### 3. `monitoring/alerts/portal.yml` — новый алерт
В группе `portal-postgresql` (рядом с `PortalPGConnectionsHigh`):
```yaml
- alert: PortalDBPoolHigh
  expr: |
    portal_db_pool_size{state="in_use"}
    / clamp_min(portal_db_pool_limit, 1) > 0.8
  for: 5m
  labels:
    severity: warning
    service: portal-backend
  annotations:
    summary: "Backend: пул соединений насыщен"
    description: "in_use > 80% от (pool_size + max_overflow) уже 5 мин — connection leak (незакрытая SQLAlchemy-сессия) или нехватка пула под нагрузкой. Проверить pg_stat_activity (что держит), логи на 'pool timeout'. Поднять DB_POOL_SIZE/DB_MAX_OVERFLOW."
```
Порог 80% = симметрично с `PortalPGConnectionsHigh`. `for: 5m` — дать settle (как у других saturation-алертов).

Дополнительно исправлю устаревший комментарий к `PortalPGConnectionsHigh` («Backend использует asyncpg pool» → на самом деле API использует SQLAlchemy, asyncpg только в воркере).
