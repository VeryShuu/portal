# Согласование документов (интеграция с 1С ERP)

> Модуль переноса стороннего PHP-приложения «Согласование документов»
> (исходники `/home/snow/order`, вне git портала) в портал. Backend — прокси
> к HTTP-сервисам 1С (адреса настраиваются в Admin UI: документы —
> `…/hs/Auth`, выдача токенов — `…/hs/PortalAuth`, миграции **115/116**);
> данные (документы, этапы, вложения) в БД портала **не хранятся** —
> источник истины 1С.
>
> **Статус: РАБОТАЕТ в тест-контуре (2026-09-06)** — сквозной прогон на
> живых документах пройден: заказы 1С видны в портале, согласование,
> вложения, токен по PortalAuth — всё проверено. Код в main (PR
> #214/#215/#216/#218/#219/#223/#226). Осталось перед продом — §8.
> Сервис 1С обновлён до **v2.1.0.0** (2026-09-06, §7.1): все вызовы —
> на корне PortalAuth, методы данных всегда отвечают 200 (токен —
> детект по телу), новые поля ТребуетсяОтветственный/Получатель/
> СсылкаНаЗадачуСЭД.

## 1. Что делает

Сотрудник видит в портале список документов 1С, ожидающих его согласования
(заказы поставщикам, заказы на внутреннее потребление), открывает карточку
(реквизиты, товары, история согласования, вложения) и **согласует** или
**отклоняет** (с обязательным комментарием) документ. Поддерживается массовое
согласование выбранных документов и назначение «ответственного» на этапе,
где это требует процесс.

```
Vue /approvals (список + карточка-Drawer)
        │  JSON (snake_case, кириллица 1С нормализована в схемах)
        ▼
FastAPI /api/v1/approvals/*  (module-gate modules.approvals.enabled)
        │  httpx, Basic = служебная учётка Portal
        ▼
1С HTTP-сервисы (v2.1.0.0: всё на erp.mage.ru/Test/hs/PortalAuth/)
  …/GETTokenByLogin?Login=<email> → {"Result":true,"Token":…}
      (TTL 30 мин; данные тоже на этом корне — старый …/hs/Auth/* только PHP)
  …/DocumentsForApproval?Profile=  → список документов (HTTP 200 всегда!)
  …/GETDocumentAttachments?Document= → вложения (#base64 в JSON)
  …/GETAgreed / GETNotAgreed        → согласовать / отклонить
```

Токен пользователя кэшируется в Redis (TTL 25 мин, ключ
`approvals:token:<email>`); на 401 от 1С тихо перезапрашивается — при
длинной массовой партии токен может протухнуть на середине (в 1С срок
захардкожен 1799 с и не продлевается).

Вход — SSO портала; **второй пароль не нужен**: 1С выдаёт токен по email
сотрудника через `GETTokenByLogin` под служебной учёткой Portal (решение
1С-разработчика от 2026-09-04, «вариант 2»).

## 2. Зафиксированные решения

| Решение | Значение |
|---|---|
| Форма | Нативный модуль портала (Vue + FastAPI-прокси); PHP-приложение после стабилизации выключается |
| Вход | SSO портала, без пароля ERP (`GETTokenByLogin`, маппинг — регистр на стороне 1С) |
| Кто пользуется | Все авторизованные сотрудники; реальную видимость определяет 1С (кому нечего согласовывать — пустой список). Отдельного гейта «согласующих» в портале нет |
| Владение документом | Карточка и действия ищут документ **только в списке текущего пользователя** (чужой GUID → 404 ещё на портале); после пакета доработок 1С дополнительно проверяет токен на своей стороне — двойной барьер |
| Вложения | base64 из 1С декодируется и отдаётся стримом, на диск **не пишется** (анти-паттерн PHP: `files/` c 0777); MIME — python-magic; Content-Disposition — RFC 5987 |
| Массовое согласование | Строго последовательно с паузой 0.5 с (каждый `GETAgreed` проводит документ + фоновое задание в 1С; параллелить нельзя). Лимит партии — **20** (`BULK_APPROVE_MAX` в схеме, зеркало на фронте): при 50 партия не укладывалась в таймаут интерфейса (ревью 2026-09-05). Транспортный сбой останавливает партию: хвост помечается «не обрабатывался», частичный отчёт возвращается; после таймаута проведение в 1С могло пройти — отчёт об этом предупреждает. Ответ — по-документные результаты (part success) |
| `requires_manager` | Вычисляемое поле «ТребуетсяОтветственный» из 1С (новый пакет); fallback — легаси-сверка текста этапа «Руководитель ЦЗ Заказа на внутреннее потребление» (константа `LEGACY_MANAGER_STAGE`). Такие документы исключены из bulk; «Согласовать» активно только после выбора ответственного из `Пользователи[]` |
| Внутренние заказы | **Согласуются** (v2.1.0.0, решение владельца 2026-09-06; до этого были «информационно» с 409): общий поток `requires_manager` — 1С флагом требует выбрать ответственного из `Пользователи[]`, портал шлёт `Employee`, 1С сама записывает его ответственным и завершает этап. Если в `GETAgreed` ушёл сотрудник не из группы — согласование пройдёт, но ответственный не запишется (1С предупредит текстом «Ответственный не записан…» — портал показывает его как есть), документ вернётся с `ТребуетсяОтветственный=true`. Из **bulk** внутренние по-прежнему исключены (свой ответственный на каждый документ) — элемент отчёта «согласуется по одному» |
| Отклонение | Только с непустым комментарием (валидация на фронте и на бэке) |
| История согласования | Пост-обработка на портале: показывается только текущий запуск — всё до последнего события «Процесс запущен» обрезается (остатки остановленного прогона при перезапуске; решение владельца 2026-09-05). Фолбэк `requires_manager` читает сырую историю 1С до обрезки |
| Числа из 1С | Суммы приходят строками с разделителями разрядов, причём пробел — неразрывный (`10\xa0108,7`): `_to_float` чистит все unicode-пробелы, иначе сумма документа и цены товаров молча терялись (прод-кейс 2026-09-05) |
| Цены | Только у «ЗаказПоставщику» (`has_prices`); для внутренних заказов 1С отдаёт нули намеренно (скрытие цен) — UI скрывает колонки. `СуммаСНДС` = «сумма с НДС» (не сам налог) |
| Сортировка очереди | Клиентская, по сумме документа **по убыванию** (решение владельца 2026-09-06): 1С порядок списка не гарантирует (живой ответ 2026-09-06 — без сортировки по сумме). Документы без суммы — в хвосте; исходный порядок данных query-кэша не мутируется |
| Ссылка на СЭД | Поле `СсылкаНаЗадачуСЭД` в `DocumentsForApproval` (гиперссылка на задачу в sed.mage.ru, есть не у всех документов): пустая строка/отсутствие поля → `sed_url: null`, строка в карточке скрыта; заполненная — кликабельная ссылка «Открыть в СЭД» в drawer (target=_blank) |
| Подразделение-получатель | Ожидавшиеся «Подразделения» пришли в v2.1.0.0 как **`Получатель` в строках `Товары`** (у внутренних заказов — шапочное подразделение, одинаковое во всех строках; у поставщика — построчное). Портал: `recipient` в `ApprovalProduct`; для внутренних — шапочный реквизит «Подразделение» карточки (первая строка), для поставщика — колонка в таблице товаров |
| Ошибки токена (v2.1.0.0) | Методы данных отвечают **HTTP 200 всегда** (как легаси-PHP): протухший/чужой токен — текст в теле («Пользователь по токену не найден»; в переписке 1С — «Профиль не найден»), честные коды остались только у `GETTokenByLogin`. Клиент детектит тело (подстрока «не найден» + «токен/профиль», массив данных отпадает сразу) и обрабатывает как 401: тихий re-login + один повтор; при повторном отказе — 502, НЕ пустой список и НЕ «успех» с текстом отказа (регресс-тесты `TestTokenInvalidBody`) |
| Секреты | `approvals_settings` (singleton, миграция 115): base_url, `auth_username` (default `Portal`), пароль Fernet (`auth_password_enc`), write-only в API |
| Ошибки 1С | Новый контракт `{"Result","Code","Message"}` + честные HTTP-коды; клиент терпит легаси (200 + сырой текст). Проброс на портал: 403/404 — как есть («не ваш документ» / «не найден»), остальное — 502 с текстом; не настроено → 503. Транспортные сбои (таймаут/DNS/TLS) оборачиваются в `ErpTransportError` → тоже 502; сырой httpx-эксепшн наружу не выходит (ревью 2026-09-05) |
| Таймауты | Клиент 1С: read 30 с (вложения — 120 с), connect 5 с, пул 5 соединений. Bulk-запрос фронта — 120 с (партия с паузами длиннее общего таймаута интерфейса 30 с). Ловушка httpx: явный `timeout=None` отключает **все четыре** таймаута, перекрывая настройки клиента, — дефолт передаётся только через `USE_CLIENT_DEFAULT` (ревью 2026-09-05) |
| TLS | Системный trust store (`ssl.create_default_context()`) — в образе уже есть Russian Trusted Root CA |

## 3. Схема БД (миграция 115)

| Таблица | Назначение |

## 4. Гейтинг

1. `modules.approvals.enabled` (modules.json) — мастер-переключатель:
   `/api/v1/approvals/*` → 404 при выключении, пункт меню скрыт, роут
   `/approvals` редиректит на главную, админ-вкладка скрыта.
2. «Настроено» = base_url + учётка + пароль (Admin → «Согласование 1С»);
   не настроено → 503 с человекочитаемым текстом.

## 5. API (префикс `/api/v1`)

| Метод и путь | Кто | Что |
|---|---|---|
| `GET /approvals` | все авторизованные | Список документов на согласование (`{items, total}`; пагинации нет — 1С отдаёт всё) |
| `GET /approvals/{uuid}` | все | Карточка + метаданные вложений (без байтов) |
| `GET /approvals/{uuid}/attachments/{index}` | все | Файл вложения (streaming download) |
| `POST /approvals/{uuid}/approve` | все | `{comment?, manager_guid?}`; `manager_guid` обязателен и должен быть из списка документа, если `requires_manager` (в т.ч. внутренние заказы — v2.1.0.0: `manager_guid` уходит в 1С параметром `Employee`) |
| `POST /approvals/{uuid}/reject` | все | `{comment}` — непустой |
| `POST /approvals/bulk-approve` | все | `{uuids[] ≤ 20}` → по-документные результаты |
| `GET/PUT /approvals/settings` | admin | Singleton настроек; пароль write-only (`password_set`) |
| `POST /approvals/test` | admin | Проверка подключения (`GETTokenByLogin`, email админа). Успех — только ответ по контракту: 200 с токеном в теле / честный 404 (не HTML); HTML или 200 без токена — отказ |

Аудит: `approvals.settings_updated` (PUT настроек), `modules.toggled`
(тумблер модуля), **`approvals.approved` / `approvals.rejected` /
`approvals.bulk_approved`** (согласования; с 2026-09-07 — решение владельца
о сборе статистики на портале; в metadata — doc_type/number, для bulk —
счётчики и uuids партии). История согласования по-прежнему источник истины
в 1С (`ИсторияВыполненияПроцессов`, туда 1С подставляет фактического
сотрудника по токену); портал-аудит — журнал «кто/когда/какой документ»
(Admin → Журнал аудита). Вложения в аудит не пишутся (шум) — только логи.

## 7. Что должно быть сделано на стороне 1С (пакет доработок)

По разбору кода расширения 1С-разработчиком (2026-09-04, журнал см. в
истории PR #214/#216/#219):

1. **`GETTokenByLogin`** — новый метод: токен по логину портала (без пароля),
   доступен **только учётке Portal** (проверка внутри метода, 403 иначе).
2. **Регистр соответствия** «логин портала → Пользователь 1С»
   (полуавтозаполнение: email-совпадения — автоматом, остальное руками;
   прямого совпадения логинов нет: из 499 активных пользователей email-вид
   у 276, домен в `ПользовательОС` у 188).
3. **Безопасность (обязательно, иначе учётка Portal расширит существующие
   дыры на всех сотрудников):**
   - `GETAgreed`/`GETNotAgreed` — проверять, что согласующий = владелец
     токена (сейчас согласуются все незавершённые этапы документа любого
     ответственного);
   - `GETDocumentAttachments` — проверять токен (сейчас не проверяется вовсе).
4. **Контракт ошибок**: `{"Result": "OK"|"Error", "Code", "Message"}` +
   честные HTTP-коды (401/403/404/500); прекратить отдавать наружу
   `ОписаниеОшибки()`.
5. **Поле «ТребуетсяОтветственный»** в ответе `DocumentsForApproval`
   (вычисляемое: внутренний заказ + пустой ответственный + активный этап) —
   **внедрено в v2.1.0.0** (2026-09-06): приходит у обоих типов, портал
   берёт его с приоритетом над легаси-фолбэком.
6. *(Опционально)* регистр аудита «сотрудник по токену + учётка вызова».
7. **«Подразделения»** — закрыто в v2.1.0.0: поле пришло как `Получатель`
   в строках `Товары` (см. §2). Формулировка «в ответе отсутствует» была
   верна для предыдущей версии сервиса (проверено 2026-09-06 утром).

### 7.1. Сервис согласования v2.1.0.0 (2026-09-06)

Письмо 1С-разработчика + живая проверка тест-контура:

1. **Корень API — всё на `…/hs/PortalAuth/…`** (токен, очередь, вложения,
   согласование). Старый `…/hs/Auth/*` остаётся только PHP-сайту. Порталу
   достаточно `base_url = …/hs/PortalAuth` в настройках (token_base_url
   совпадает; в тест-контуре так уже настроено).
2. **Новые поля**: `ТребуетсяОтветственный` (шапка), `Получатель`
   (строки `Товары`), `СсылкаНаЗадачуСЭД` (шапка поставщика) — все
   обработаны (§2). Также в ответе `Склад` и `ДокументПроцесса` (история) —
   парсером игнорируются.
3. **Назначение ответственного**: `GETAgreed` с `Employee` (GUID из
   `Пользователи[]`) — 1С записывает ответственного сама. Сотрудник не из
   группы → согласование проходит, ответственный НЕ записывается (текст
   «Ответственный не записан…» в ответе), документ вернётся с флагом.
4. **Семантика ошибок данных**: HTTP 200 всегда, ошибки — текстом в теле
   (см. §2 «Ошибки токена»). Карта ошибок — в приложении к письму 1С
   (в портал не передавалась; при получении — сверить тексты детекта).

Нюансы живого контракта (учтены в клиенте, PR #216):

- **WAF веб-сервера банит «подозрительные» User-Agent** (Python-urllib и
  т.п.). Портал шлёт `User-Agent: portal-approvals/1.0` — ок. Не-JSON ответ
  на ошибке (бан-страница/текст платформы «Недостаточно прав») трактуется
  как **инфраструктурная ошибка** (502-семантика), а не «документ чужой».
- **400 пробрасывается как есть**: карта ошибок 1С — «нет обязательного
  параметра / Employee не в группе „Ответственные за закупку“» —
  пользователь должен увидеть текст 1С, а не «ошибку портала».
- 403 «не в очереди» = в т.ч. дабл-клик «Согласовать» — показываем текст 1С
  как есть (кнопки дизейблятся на время запроса).
- Списки — «голые» массивы; пустая очередь = `[]` (легаси-текст
  «{Документов нет}» больше не приходит, но парсер терпит его по-прежнему).

**Выдача токенов — на отдельном RootURL** (изменение 1С, 2026-09-05):
`…/hs/PortalAuth/GETTokenByLogin`, документы остаются на `…/hs/Auth`.
Настройка `token_base_url` (миграция 116): пусто = как base_url.

Сверка логинов: `./scripts/export-portal-logins.sh` на сервере портала →
CSV (email,full_name; UTF-8; действующие; email в нижнем регистре) → 1С
сверяет покрытие регистра и добивает несопоставленных вручную. Периодическая
сверка при приёмах/увольнениях — та же команда. Примечание: «499» в переписке
1С — это число **активных пользователей ИБ 1С** (включая техучётки и
юнити-пользователей), не сотрудников портала; CSV портала будет меньше.

Контрактные договорённости (уточняющие вопросы 1С, 2026-09-04): логин —
email в нижнем регистре с доменом (`strip().lower()` на портале; регистр
соответствия заполняется так же); токен-ответ принимается как
`{"Токен": …}`, так и `{"Result": true, "Token": …}`; список документов и
вложений остаются JSON-массивами; параметр комментария — `Comment` в обоих
методах; замещение (`Замещение=Истина`) сохраняется как в PHP; 1С добавляет
проверку Employee ∈ «Ответственные за закупку».

## 8.1. Регрессии, пойманные при живой стыковке (учитывать при правках)

- **`Depends(<Annotated-алиас>)` в router-level dependencies** (FastAPI
  0.140) генерирует фантомные обязательные query-параметры `args`/`kwargs`
  → любой запрос 422. Гейт модуля оборачивать только сырой функцией
  (регресс-тест `TestRouting`).
- **GET `/approvals/settings` перекрывался** `GET /approvals/{document_uuid}`
  при неверном порядке включения роутеров — settings_router включается
  ПЕРВЫМ (регресс-тест `test_settings_route_not_shadowed_by_document_uuid`).
- **Реактивность query-опций**: `useApprovalDetailQuery` — `queryKey`/`enabled`
  через `computed` (статичное значение фиксируется при закрытом drawer и
  запрос никогда не уходит; регрессия в `approvals-queries.spec`).
- **1С отдаёт JSON-ошибки без Content-Type** — эвристика контракт/инфра по
  телу (первый символ `{`/`[`), не по заголовку.
- **Токен-щуп «Проверить подключения»** — только `GETTokenByLogin`: под
  честным контрактом фиктивный Profile неотличим от отказа кредов (оба 401).
- **`timeout=None` в httpx — это «без таймаутов»** (ревью 2026-09-05): явный
  `None` в per-request вызове перекрывает клиентские настройки и отключает
  все четыре таймаута. Дефолт — только через `USE_CLIENT_DEFAULT`
  (регресс-тест `TestTimeouts`).
- **Партия vs таймаут интерфейса** (ревью 2026-09-05): последовательные
  вызовы с паузами при лимите 50 не укладывались в 30 с фронта. Решение:
  лимит 20 + bulk-таймаут фронта 120 с + аборт хвоста партии на
  транспортной ошибке (регресс-тест `test_bulk_transport_error_keeps_partial_report`).
- **ping без проверки тела давал ложный успех** (ревью 2026-09-05): любой
  200/404 считался зелёным — HTML-страница чужого адреса проходила как
  «ERP доступна». Теперь 200 обязан нести токен, 404 с HTML-телом — отказ
  (регресс-тесты в `TestPing`).
