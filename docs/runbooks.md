# Runbook — что делать при тревогах

> **Когда читать:** пришёл алерт из Grafana/Alertmanager (или пропали уведомления целиком) и нужно понять, что случилось и что делать.
> **Связано:** [мониторинг приложения](./monitoring.md), [дашборды](../monitoring/README.md), [развёртывание](./deploy.md).

Дата: 2026-09-10. Статус: живой документ; дополняется вместе с алертами (`monitoring/alerts/portal.yml`).

## Как пользоваться

- **Critical (красное)** — сотрудникам что-то недоступно или данные под угрозой. Реакция немедленно.
- **Warning (жёлтое)** — деградация или отставание; разобрать в течение рабочего дня.
- **Info (синее)** — заметка на будущее (ёмкость и т.п.), будить никого не нужно.
- **«Нет данных»** на панели — само наблюдение не отвечает (источник умер, метрика исчезла). Это не «всё хорошо»: сначала проверить здоровье наблюдения (дашборд Overview → секция «Здоровье наблюдения»), потом причину.
- **«Данные устарели»** — источник жив, но перестал обновлять метрики >2 мин. Цифры ниже по экрану могут быть неполными.
- **«Отключено»** — модуль выключен настройками; это норма, не авария.
- **«Ещё не проверено»** — проверка ещё ни разу не завершалась после старта.

Команды в диагностических разделах ниже **только читающие** — их можно безопасно выполнять на работающей системе. Действия с эффектом (рестарты, чистки, отправка тестов) встречаются в двух местах — «Внешний dead-man контроль» и «Проверка доставки» — и там помечены знаком ⚠️: выполнять осознанно, не как первый шаг.

Быстрые переходы — Grafana (адрес: `.env::GRAFANA_ROOT_URL`, по умолчанию `<хост>:3001`), дашборды папки **Portal**: «Overview» — общий статус, «Logs» — поиск по логам, «Infrastructure» — контейнеры/ресурсы, «Storage» — диски и размеры. Каждая секция ниже указывает, какой дашборд и какие панели открыть.

Логи сервиса: `docker compose logs --since 30m backend` (аналогично `worker`, `nginx`, `postgres`). Поиск по request_id — Grafana → Logs.

## 1. Здоровье наблюдения (portal-meta)

**Что произошло:** наблюдение само частично ослепло — умер Prometheus/Alertmanager/Loki/Alloy/экспортер, устарел metrics-snapshot или пропали уведомления.

**Что не работает у сотрудников:** как правило ничего (это мета-уровень). Но если не чинить — следующая авария пройдёт молча.

**Что посмотреть сначала:**

```bash
docker compose -f docker-compose.monitoring.yml ps        # кто упал
docker compose -f docker-compose.monitoring.yml logs --since 30m prometheus
docker compose -f docker-compose.monitoring.yml logs --since 30m alertmanager
```

- `PortalMetricsSnapshotStale` — worker перестал публиковать снапшот метрик: смотреть `docker compose logs --since 30m worker`, доступность Redis. Цифры на Overview помечены «Данные устарели».
- `AlertmanagerNotificationsFailed` — Alertmanager жив, но письма не уходят: SMTP-relay, логи alertmanager. **Важно: пока это не починено, остальные письма-алерты не доставляются.**
- `Watchdog` сам по себе не алерт-событие: он **всегда** горит. Его ПРОПАЖА на внешнем dead-man приёмнике означает отказ Prometheus/Alertmanager (см. «Внешний dead-man контроль» ниже).

**Как проверить восстановление:** панель «Здоровье наблюдения» на Overview вся зелёная; «Свежесть метрик» — «Свежие».

**Когда звать специалиста:** если два компонента наблюдения не поднимаются после рестарта — есть риск каскадной проблемы (диск, сеть).

## 2. Доступность портала (portal-availability)

**Что произошло:** `PortalBackendDown` — API не отвечает; `PortalBackendUnhealthy` — процесс жив, но зависимости (БД/Redis) не готовы; `PortalHighErrorRate` — много 5xx.

**Что не работает у сотрудников:** весь портал или часть операций — ошибки в браузере, невозможность войти.

**Что посмотреть сначала:**

```bash
docker compose ps backend
docker compose logs --since 30m backend | tail -50
docker compose exec postgres pg_isready        # читающая проверка БД
docker compose exec redis redis-cli ping       # читающая проверка Redis
```

- Overview → «Готовность API (зависимости)»: «Не готов» = смотрим БД/Redis, «Работает» при 5xx = ошибка в коде/конкретном эндпоинте.
- Overview → «Доля успешных HTTP-ответов» и топ хендлеров по ошибкам — какой endpoint деградировал.

**Как проверить восстановление:** «API портала» зелёный, доля 5xx падает до нормы, алерт ушёл (в Grafana → Alerting или письмо resolved).

**Когда звать специалиста:** рестарт backend не помог, или ошибка повторяется в одном и том же эндпоинте (это уже баг — заводить задачу).

## 3. Конвейер аудита (portal-audit-pipeline)

**Что произошло:** события аудита копятся в Redis, но не попадают в PostgreSQL (`PortalAuditQueueBacklog`), застрял флаш (`PortalAuditFlushStuck`) или push-поток встал (`PortalAuditPushRateZero`).

**Что не работает у сотрудников:** обычно ничего заметного; НО журнал действий (кто что сделал) не пишется — это требование безопасности, тянуть нельзя.

**Что посмотреть сначала:**

```bash
docker compose logs --since 30m worker | grep -i audit
docker compose exec redis redis-cli LLEN audit:queue      # глубина очереди (чтение)
```

Overview → секция «Audit pipeline»: глубина очереди растёт = воркер не успевает или флаш упал.

**Как проверить восстановление:** очередь опускается к нулю после спайка; `PortalAuditPushRateZero` — сравнить с ожидаемой активностью (ночью ноль событий — норма, алерт это учитывает окном).

**Когда звать специалиста:** очередь растёт часами или в логах повторяются ошибки записи в PostgreSQL.

## 4. Фоновые задачи (portal-worker)

**Что произошло:** `PortalWorkerDown` — ARQ-воркер мёртв (heartbeat >4 мин); `PortalWorkerStale` — жив, но не шевелится; `PortalArqQueueBacklog` — очередь задач растёт; `PortalArqJobFailures` — конкретная задача падает ≥3 раза за 10 мин (в т.ч. «неуспешный результат» без исключения).

**Что не работает у сотрудников:** рассылки, обработка фото, хелпдеск-почта, синхронизации — всё фоновое. Вход/чтение работают.

**Что посмотреть сначала:**

```bash
docker compose ps worker
docker compose logs --since 30m worker | tail -50
```

Overview → «ARQ job failures rate» и «ARQ: таймауты и прерывания»: какая функция падает. Если задача связана с интеграцией — смотреть её секцию ниже.

**Как проверить восстановление:** heartbeat обновился, глубина очереди снижается, ошибки конкретной функции прекратились.

**Когда звать специалиста:** воркер падает в цикле (restart-loop) или одна и та же задача падает после деплоя — откат релиза, если причиной был он.

## 5. Насыщенность (portal-saturation)

**Что произошло:** `PortalHighLatencyP99` — p99 задержек высокий; `PortalSSEConnectionsHigh` — аномально много стримов уведомлений (утечка EventSource); `PortalPhotoStorageHigh` — фото-хранилище >100 ГБ (info, планировать ёмкость).

**Что не работает у сотрудников:** тормоза портала; SSE — лишний трафик, возможные «вечные» вкладки.

**Что посмотреть сначала:** Overview → «p99 latency по endpoints» (какой endpoint), Infrastructure → CPU/RAM контейнеров. SSE: ZSET `sse:global` в Redis (чтение: `docker compose exec redis redis-cli ZCARD sse:global`).

**Как проверить восстановление:** p99 вернулся в зелёную зону; число SSE-соединений упало после закрытия «висящих» вкладок.

**Когда звать специалиста:** латентность растёт при обычной нагрузке неделями — узкое место в коде/БД, нужна задача.

## 6. PostgreSQL (portal-postgresql)

**Что произошло:** `PortalDBPoolHigh` — пул соединений приложения насыщен (утечка сессии или мало пула) **в конкретном процессе** (pid в алерте); `PortalDBPoolTelemetryStale` — этот процесс не отдаёт метрики пула (завис event loop или умер некрасиво); `PortalPGConnectionsHigh` — соединений к PG близко к лимиту; `PortalPGCacheHitLow` — БД читает с диска; `PortalPGWraparound` — XID близко к автовакуумной защите; `PortalPGDeadlocks` — дедлоки.

**Что не работает у сотрудников:** замедление/ошибки всех операций с БД при насыщении; wraparound — угроза перехода БД в read-only.

**Что посмотреть сначала:**

```bash
docker compose exec postgres psql -U portal -c "SELECT count(*), state FROM pg_stat_activity GROUP BY state;"   # чтение
docker compose logs --since 30m backend | grep -i "pool timeout"
```

Storage → «Топ-10 таблиц по размеру» — кто раздувает БД (текущий срез).

**Как проверить восстановление:** алерт исчез; доля in_use пула < 80%; соединения к PG < 80% лимита.

**Когда звать специалиста:** wraparound — сразу; дедлоки — это баг в коде, заводить задачу с текстом ошибки из логов.

## 7. Redis (portal-redis)

**Что произошло:** `PortalRedisMemoryHigh` — память >90% (близко к eviction); `PortalRedisEvictions` — ключи начали выбрасываться (теряются сессии/аудит); `PortalRedisKeyspaceLow` — подозрительно мало обращений (потеря трафика).

**Что не работает у сотрудников:** при eviction — разлогины, потеря событий аудита, сбои очередей.

**Что посмотреть сначала:**

```bash
docker compose exec redis redis-cli INFO memory | head -20   # чтение
```

**Как проверить восстановление:** память < порога, evictions = 0. Долгосрочно — увеличить `REDIS_MAXMEMORY` в .env (рестарт Redis — согласовать: это разлогин всех).

**Когда звать специалиста:** eviction после увеличения лимита — аномальный рост данных (утечка ключей).

## 8. Хост и диски (portal-host)

**Что произошло:** `PortalDiskSpaceLow` — диск заполняется; `PortalLokiStorageHigh` — volume логов; `PortalStorageCollectorStale` — сборщик размеров не обновляет метрики; `PortalCPUHigh`/`PortalRAMLow` — ресурсы хоста.

**Что не работает у сотрудников:** при полном диске падает запись БД/логов — фактически остановка всего портала.

**Что посмотреть сначала:**

```bash
df -h
docker system df        # сколько занимает Docker (читающая команда)
```

Storage-дашборд: какие папки/логи растут. Логи: `docker compose logs --since 1h storage-collector`.

**Как проверить восстановление:** диск стабилизировался ниже порога. Чистку не делать автоматически — ручной осмотр (это не read-only действие).

**Когда звать специалиста:** неизвестный источник роста; чистка Docker/логов — отдельное согласованное действие.

## 9. Контейнеры (portal-containers)

**Что произошло:** `PortalContainerRestartLoop` — контейнер перезапускается чаще 3 раз за 10 мин.

**Что не работает у сотрудников:** зависит от контейнера (backend/worker — заметно; exporters — слепые зоны мониторинга).

**Что посмотреть сначала:** `docker compose ps` (колонка Restart), логи упавшего контейнера с начала последнего старта: `docker compose logs backend | tail -100`.

**Как проверить восстановление:** uptime контейнера растёт, причина в логах устранена.

**Когда звать специалиста:** цикл после деплоя — откат релиза (`IMAGE_TAG` на предыдущий в .env).

## 10. Внешний периметр (portal-blackbox)

**Что произошло:** `PortalExternalProbeFailed` — портал недоступен снаружи (через настоящий адрес/TLS); `PortalCertExpirySoon/Critical` — сертификат истекает (<14 / <3 дней).

**Что не работает у сотрудников:** снаружи офиса/VPN портал не открывается.

**Что посмотреть сначала:** Overview → «Внешние пробы», «TLS-сертификаты (дней)». Изнутри: `docker compose logs --since 30m nginx`; сертификаты: `openssl s_client -connect <host>:443 </dev/null 2>/dev/null | openssl x509 -noout -dates` (чтение).

**Как проверить восстановление:** проба снаружи зелёная; после продления сертификата дни до истечения растут.

**Когда звать специалиста:** сертификат critical (<3 дней) и продление не настроено автоматически — звать немедленно.

## 11. Nginx (portal-nginx)

**Что произошло:** `PortalNginxConnectionsHigh` — аномально много активных соединений (сканер, бот или всплеск).

**Что посмотреть сначала:** `docker compose logs --since 30m nginx | tail -30`; Overview/Infrastructure → rate запросов.

**Когда звать специалиста:** признаки внешней атаки — блокировать на уровне сети/прокси.

## 12. Исходящая почта и мессенджеры (portal-outbox)

**Что произошло:** очередь писем/PMAX-сообщений растёт (`...OutboxBacklog`), письма попали в DLQ (`...OutboxDLQ`), или застряли в статусе SENDING >10 мин (`...OutboxStuck` — воркер умер при отправке).

**Что не работает у сотрудников:** не приходят уведомления о заявках/встречах/новостях. Число PENDING само по себе — не авария (нормальная очередь), тревога — рост и DLQ.

**Что посмотреть сначала:**

```bash
docker compose logs --since 30m worker | grep -iE "outbox|smtp"
```

Overview → «Очереди и synthetic»: PENDING/DLQ/SENDING. Внимание: «SMTP» в статусах интеграций — это **сетевая проверка relay'я, не доставка писем**; доставку показывает именно этот раздел.

**Как проверить восстановление:** очередь опустела, DLQ не растёт. Разбор DLQ — вручную (не read-only, согласовать).

**Когда звать специалиста:** письма не уходят при живом SMTP — проблема у провайдера relay или в шаблонах.

## 13. Интеграции (portal-integrations)

**Что произошло:** `PortalIntegrationDown` — интеграция (Keycloak, Nextcloud, SMTP, Collabora, ERP 1С…) не отвечает на пробу; `PortalIntegrationProbeStale` — проба не завершалась вовремя (наблюдение устарело).

**Что не работает у сотрудников:** Keycloak — SSO-вход (локальный вход работает); Nextcloud — файлы; Collabora — совместное редактирование; ERP — согласование документов.

**Состояния на Overview:** «Работает» — свежая успешная проверка; «Недоступна» — свежая неудачная; «Данные устарели» — проба перестала выполняться; «Отключено» — модуль выключен (норма); «Нет данных» — проверка ещё не завершалась после старта.

**Что посмотреть сначала:**

```bash
docker compose logs --since 30m worker | grep -i "integration"
```

Collabora смотрит глубже страницы: конфигурацию Nextcloud Office (WOPI-URL) и capabilities самого Collabora — ложных «зелёных» на redirect/404 больше нет.

**Как проверить восстановление:** статус интеграции «Работает» с новой временной меткой проверки.

**Когда звать специалиста:** интеграция недоступна дольше часа при живом её сервере — сетевая/DNS проблема, эскалация сисадмину инфраструктуры.

## 14. Synthetic-проверка пользовательского пути (portal-synthetic)

**Что произошло:** `PortalSyntheticProbeFailed` — автопроверка «войти на портал и открыть главную» не проходит; `PortalSyntheticProbeStale` — проверка не выполнялась 15 мин; `PortalScreenshotServiceMetricsDown` — метрики проверяльщика недоступны.

**Что не работает у сотрудников:** сам проверяльщик — невидим; НО эта проверка — датчик реального пользовательского пути (браузер + вход + главная страница). Красная = путь сломан, даже если метрики API зелёные.

**Что посмотреть сначала:** `docker compose logs --since 30m screenshot-service` (в логах безопасные причины `step_failed` — без паролей/персональных данных); Overview → «Вход сотрудников (проверка)».

**Граница:** это проверка **локального входа**. Keycloak/SSO и внешний TLS — отдельные пробы (MON-14, pending).

**Как проверить восстановление:** свежий успешный прогон, длительность в норме.

**Когда звать специалиста:** проба красная при зелёном API и живом nginx — проблема на стыке (браузерная логика/JS) — заводить задачу с временем прогона.

## Внешний dead-man контроль пропажи мониторинга

Если **все уведомления пропали разом** (или внешний сервис сообщил о пропаже пингов Watchdog) — умер Prometheus, Alertmanager или хост. Порядок:

1. `docker compose -f docker-compose.monitoring.yml ps` — что живо.
2. Свободное место: `df -h` (частая причина смерти Prometheus — диск).
3. ⚠️ **Действие с эффектом:** поднять упавшее — `docker compose -f docker-compose.monitoring.yml up -d <сервис>`. Выполнять после осмотра пунктов 1–2, не вслепую.

Статус настройки: приёмник задаётся в `.env` → `ALERT_DEADMAN_WEBHOOK_URL` (пинги каждые ~5 мин, grace-окно внешнего сервиса ≥30 мин). Пока переменная пуста — внешний контроль не настроен (pending, ТЗ §14): пропажу уведомлений замечает только человек.

## Проверка доставки уведомлений

1. Открой Grafana → Alerting → Alert rules → любая группа (или Alertmanager UI `:3001/api/…` через интерфейс).
2. Контрольный канал без副作用: в Alertmanager UI видно историю отправок (`Notifications`), ошибки доставки — там же.
3. Явный тест с письмом — только согласованному получателю, вручную (не из этого runbook автоматически): Alertmanager UI → Create silence не подходит; используйте тестовый алерт через `amtool` на своём контуре.

Частота проверки: **раз в месяц** — и после любых правок SMTP/dead-man конфигурации.

## Ежедневный чек-лист владельца (2 минуты)

1. Overview → «Всего тревог»: 0? Если нет — таблица «Что не работает»: есть critical? → раздел этого runbook.
2. Overview → «Свежесть метрик» = «Свежие», «Здоровье наблюдения» всё зелёное.
3. «Вход сотрудников (проверка)» и «API портала» зелёные.
4. Внешний периметр: пробы зелёные, до истечения сертификата >14 дней.
