# План реализации M2: расширения файлового модуля

> Источник задачи: `file.md` § 11 (M2 backlog). Цель — закрыть UX-провалы M1
> и перевести bulk-операции с «достаточно» на «production-grade».
>
> Версия документа: **v3 (утверждённый, май 2026)**. Версия v2 закрыла
> open questions §11; v3 добавляет результаты cross-review (тех-замечания
> по streaming ZIP, атомарному WebDAV MOVE, разделению in-flight/async
> ключей, CSRF для XHR, точный SQL для recursive UPDATE) и фиксирует
> Sprint 0 — подготовительный этап перед основными спринтами.
>
> **Решения, утверждённые до начала работы:**
> - Скоуп: все 8 задач M2.1–M2.8 + Sprint 0 (см. §0.1).
> - DnD папок (M2.1): полный flow — создание подпапок и в БД портала, и в NC.
>   **Пустые папки создаются** (Google Drive / Dropbox-style). Раздельные
>   лимиты: `MAX_UPLOAD_BATCH_FILES=500` (файлы), `MAX_FOLDER_UPLOAD_DIRS=200`
>   (пустые папки), `MAX_FOLDER_DEPTH=10`.
> - ZIP-bundle (M2.2): локальный volume `/data/file_zips/`, retention 24 ч.
>   Имя архива `{folder_name}-{YYYY-MM-DD}.zip`. Исчезнувшие файлы → skip +
>   `error_files` в job + статус `done_with_errors`. **Streaming через
>   `tempfile.SpooledTemporaryFile` + `zf.write()` + `force_zip64=True`**
>   (не `writestr` — буферизует RAM). `filenames` в endpoint **опционален**
>   — `null` означает «вся папка» (Google Drive «Download folder»-паттерн).
> - Конфликт-резолвер (M2.5): default `skip` (backward-compat с M1).
>   `split_extension` — последний `.ext` (`os.path.splitext`-семантика).
>   **Атомарный `nc.move(src, dst, overwrite=True)`** через WebDAV header
>   `Overwrite: T` (не двухступенчатый delete+move — race-free).
> - Корзина (M2.6): NC-папка `_trash/{user_id}/{job_id}/`, retention 30 дней,
>   cron-очистка. Все trashed-файлы в одном плоском списке. При restore без
>   живой `original_folder` → обязательная модалка выбора целевой папки.
>   Restore-коллизия с `conflict_strategy` (по умолчанию `rename` — не теряем
>   данные). **Использует существующий `idx_file_items_nc_path_active`**
>   (миграция 038) — новых уникальных индексов добавлять не нужно. Retention
>   считается от `trashed_at`; restore сбрасывает счётчик. Admin endpoint
>   `GET /files/trash?user_id=...` (API only, без UI в M2).
> - Cycle при move папок (M2.7): 422 + frontend-превентив (disabled
>   потомков в move-modal). **Recursive UPDATE `nc_path` через
>   `WITH RECURSIVE ... UPDATE ... FROM cte`** (см. §7.2.3).
> - Byte-progress (M2.4): EMA-сглаженный speed (alpha=0.3, 500ms) + ETA.
>   **Через `apiUploadWithProgress` (XHR) + общий `utils/csrf.ts`** — XHR
>   не наследует ofetch-интерсепторы, выносим CSRF в shared-утилиту.
> - In-flight ключи **разделены**: `bulk:inflight:{user_id}` (sync ops,
>   TTL 60s) vs `async:job:{user_id}:{type}:{job_id}` (TTL до `expires_at`).
>   Async-jobs снимают `bulk:inflight` сразу после `enqueue_job()`.
> - Все лимиты M2 — константы в `core/constants.py` с env-override.
> - DELETE-семантика M2.6: behavior-change (soft по умолчанию), `?hard=true`
>   для admin сохраняется. Audit-event получает `metadata.action ∈
>   {"trashed","purged"}`. Bump в `api-contracts.md`.
>
> **Очерёдность работ:** Sprint 0 (инфраструктура) → Sprint 1 (M2.4 + M2.8)
> → Sprint 2 (M2.5) → Sprint 3 (M2.6) → Sprint 4 (M2.1 + M2.2)
> → Sprint 5 (M2.3) → Sprint 6 (M2.7). M2.5 идёт **до** M2.6, чтобы restore
> сразу использовал стратегии. См. §9.
>
> Ответственные модули backend: `backend/app/api/files.py`,
> `backend/app/services/nextcloud/`, `backend/app/worker/tasks/files.py`.
> Frontend: `frontend/src/pages/FilesPage.vue`,
> `frontend/src/api/files.ts`, новые страницы `FilesTrashPage.vue`.

## 0. Глоссарий и инварианты M1, которые нельзя ломать

| Термин | Значение |
|---|---|
| **Natural idempotency** | Сохраняется во всех M2-операциях: NC 404→success, Overwrite=F, SETNX in-flight. |
| **In-flight key (sync)** | `bulk:inflight:{user_id}` (TTL 60s) — для **синхронных** bulk-ops (delete/move/rename). Один на пользователя. |
| **Async-job key** | `async:job:{user_id}:{type}:{job_id}` (`type ∈ {zip}`, `TTL = expires_at - now`) — для асинхронных ARQ-jobs. Не блокирует sync-ops. |
| **MAX_BULK_FILES** | 100 для M1 endpoints (bulk-операции). |
| **MAX_UPLOAD_BATCH_FILES** | 500 — для **upload** (включая DnD папок). |
| **MAX_FOLDER_UPLOAD_DIRS** | 200 — отдельный лимит на пустые папки в одном upload-batch. |
| **MAX_FOLDER_DEPTH** | 10 уровней — защита от рекурсии при DnD папок. |
| **MAX_ZIP_FILES** | 500 файлов в архиве. |
| **MAX_ZIP_SIZE_BYTES** | 2 GB суммарно. |
| **ZIP_RETENTION_HOURS** | 24 — TTL ZIP-файлов в `/data/file_zips/`. |
| **TRASH_RETENTION_DAYS** | 30 — auto-purge, считается от `trashed_at`. |
| **MAX_RECURSIVE_FOLDERS** | 20 папок в одной recursive-bulk операции (M2.7). |
| **uploaded_by** | Никогда не подменяется при move/restore (см. M1 §3.2). |
| **Audit-event-on-bulk** | Один event на операцию + counters в metadata. M2 продолжает паттерн. |

**Правила, которые сохраняются:**
- Все NC-операции через `portal-svc` (Basic Auth, App Password).
- Права проверяются только в БД портала (`files_acl.py`).
- Streaming uploads/downloads (без `await stream.read()` целиком).
- Rate-limit `fastapi-limiter` (per-user, Redis), новые эндпоинты подбирают
  лимит по характеру операции.
- i18n: ключи добавляются одновременно в `ru.json` + `en.json`.
- Backward compatibility M1 endpoints: только расширение body
  опциональными полями.

### 0.1.2. `frontend/src/utils/csrf.ts` — общая CSRF-утилита

**Текущее состояние** (`api/index.ts`): константы `CSRF_COOKIE = 'XSRF-TOKEN'`,
`CSRF_HEADER = 'X-XSRF-TOKEN'` и приватная `readCookie(name)` объявлены
inline. Не экспортируются — XHR в M2.4 не сможет переиспользовать.

**Refactor:**
```ts
// frontend/src/utils/csrf.ts
export const CSRF_COOKIE = 'XSRF-TOKEN'
export const CSRF_HEADER = 'X-XSRF-TOKEN'

export function getCsrfToken(): string | null {
  const prefix = CSRF_COOKIE + '='
  for (const part of document.cookie.split(';')) {
    const c = part.trim()
    if (c.startsWith(prefix)) return decodeURIComponent(c.slice(prefix.length))
  }
  return null
}
```

`api/index.ts` импортирует `getCsrfToken` + константы, удаляет
inline-`readCookie`. Backward-compat: поведение для `api()` и `apiUpload()`
не меняется.

### 0.1.4. `WebDAVClient.move(overwrite=...)` — расширение сигнатуры

**Текущее состояние** (`backend/app/services/nextcloud/webdav.py:300`):
```python
async def move(self, nc_path_src: str, nc_path_dst: str) -> None:
    headers = self._headers({"Destination": url_dst, "Overwrite": "F"})
    ...
    if r.status_code not in (201, 204):
        raise NextcloudError(r.status_code, f"MOVE failed: {r.status_code}")
```

`Overwrite: F` жёстко прибит. Нет специальной обработки 412
(precondition failed = name conflict).

**Refactor:**
```python
async def move(
    self, nc_path_src: str, nc_path_dst: str, overwrite: bool = False
) -> None:
    overwrite_header = "T" if overwrite else "F"
    headers = self._headers({"Destination": url_dst, "Overwrite": overwrite_header})
    ...
    if r.status_code not in (201, 204):
        raise NextcloudError(r.status_code, f"MOVE failed: {r.status_code}")
```

- Backward-compat: `overwrite` имеет default `False` → все текущие
  вызовы остаются с `Overwrite: F`.
- 412 (existing target при `overwrite=False`) уже сейчас попадает в
  `NextcloudError(412, ...)` — апстрим (M2.5/restore) ловит и применяет
  `conflict_strategy`.
- Используется в M2.5 (overwrite-strategy) и M2.6 (restore-rename).

## 1. M2.1. Загрузка папок через DnD (рекурсивный обход) — S

### 1.1. Скоуп
- Drop одной или нескольких папок (с любой глубиной вложенности) → backend
  создаёт промежуточные `file_folders` записи и NC-коллекции, грузит файлы
  в соответствующие подпапки.
- ACL: достаточно `editor` на корневой drop-target папке, новые подпапки
  наследуют permissions через `file_folder_permissions.inherit_permissions`
  (механизм уже есть в `files_acl.py`).

### 1.2. Backend

#### 1.2.1. Расширение `POST /files/folders/{id}/upload`
- Добавить опциональное поле `relative_paths` (form-data) — массив строк
  параллельно `files[]`. Каждое значение — относительный путь файла
  относительно корня drop'а (без ведущего `/`, разделитель `/`,
  Windows-backslashes нормализуются на frontend).
- Если `relative_paths[i]` пуст или равен basename — поведение M1.
- Если содержит `/` — backend разбивает на segments, для каждого segment
  upsert `file_folders` (parent_id = предыдущий folder.id), вызывает
  `nc.mkdir` идемпотентно (NC 405 на «уже существует» = success).
- **Пустые папки:** создаются. Frontend дополнительно отправляет поле
  `empty_dirs` (form-data, массив относительных путей) для папок без файлов
  внутри. Backend для каждого такого пути вызывает `ensure_subfolder_path`
  без последующего PUT.
- Все promotions подпапок логируются единым audit-event `files.folders_created`
  с `metadata = { count, root_folder_id }`.

#### 1.2.2. Новый сервис-метод
```python
# backend/app/services/files_subfolder.py
async def ensure_subfolder_path(
    db, redis, parent_folder, segments: list[str], user_id
) -> FileFolder:
    """Идемпотентно создаёт цепочку подпапок parent → seg1 → seg2 → ...
    Возвращает листовую папку. Каждая создаваемая папка наследует ACL.
    """
```

#### 1.2.3. NC-операция
- `WebDAV.mkdir(path)` уже есть; нужно убедиться, что 405/409 (existing
  collection) трактуется как success. Если нет — добавить.

#### 1.2.4. Лимиты
- **`MAX_UPLOAD_BATCH_FILES = 500`** — максимум файлов в одном upload-batch
  (расширяем с 100 для DnD папок и обычного multi-select).
- **`MAX_FOLDER_UPLOAD_DIRS = 200`** — отдельный лимит на пустые папки
  (`empty_dirs[]`). Папки и файлы считаются раздельно — 500 файлов + 200
  пустых папок одновременно валидно. Превышение → 422
  `too_many_dirs`/`too_many_files`.
- **`MAX_FOLDER_DEPTH = 10`** — защита от рекурсии при обходе.
- Все три константы из `core/constants.py` (см. §0.1.1), env-overridable.
- Rate-limit upload не меняется (20/min).

### 1.3. Frontend
- В `FilesPage.vue::extractDroppedFiles` заменить `if (entry?.isDirectory) {
  hadFolders = true; continue; }` на рекурсию:
  ```ts
  async function walkDirectory(
    dirEntry: FileSystemDirectoryEntry,
    prefix: string,
  ): Promise<{file: File, relativePath: string}[]> {
    const reader = dirEntry.createReader()
    const entries = await readAllEntries(reader)  // pagination!
    const result: {file: File, relativePath: string}[] = []
    for (const e of entries) {
      const rel = `${prefix}${e.name}`
      if (e.isFile) result.push({file: await fileFromEntry(e), relativePath: rel})
      else if (e.isDirectory) result.push(...await walkDirectory(e, `${rel}/`))
    }
    return result
  }
  ```
  > `readAllEntries` обязательна — `readEntries()` в Chrome возвращает по 100
  > за раз, нужен цикл до пустого массива.
- `uploadFiles` API расширяется: вторым параметром принимает
  `Array<{file, relativePath?}>` + опциональный `emptyDirs: string[]`.
  Внутри собирает FormData с парой `files[]` + `relative_paths[]` и
  отдельный `empty_dirs[]` (порядок files гарантирован).
- При обходе `walkDirectory` собираем директории, в которых не оказалось
  файлов — складываем в `emptyDirs`.
- Прогресс upload показывает текущий путь (`uploadProgress.currentPath`).

## 2. M2.2. ZIP-bundle для bulk-download — M

### 2.1. Скоуп
- Замена клиентского цикла `<a download>` на серверную сборку ZIP через ARQ.
- Снимает лимит «20 файлов» из M1.
- Новый лимит: **500 файлов** или **2 GB** (sum of `size_bytes`).

### 2.2. БД-миграция

| Метод | URL | ACL | Описание |
|---|---|---|---|
| POST | `/files/folders/{id}/zip` | viewer + per-file | Body `{filenames?: string[]}`. Если `filenames` отсутствует/пуст → backend берёт все non-trashed файлы папки (Google Drive «Download folder»-паттерн). Возвращает `{job_id, status}` |
| GET | `/files/zip/{job_id}` | owner | Статус (`status`, `progress`, `download_url?`, `error?`) |
| GET | `/files/zip/{job_id}/download` | owner | StreamingResponse файла; sets `Content-Disposition: attachment; filename="{archive_name}"` |

- **Body `filenames`** — `Optional[list[str]] = None`. `null` или пустой список
  означает «вся папка»; backend сам выбирает `file_items` где
  `folder_id == id AND deleted_at IS NULL AND trashed_at IS NULL`.
- ACL POST: viewer на src + проверка прав на каждый файл (re-use
  `batch_resolve_folder_permissions`); невалидные имена → 422.
  Лимит `MAX_ZIP_FILES=500` применяется и при auto-fill — превышение → 422
  `too_many_files` с подсказкой выбрать вручную / разбить на подпапки.
- Rate-limit POST: `RateLimiter(times=2, minutes=5)` per user.
- **In-flight:** ZIP-job берёт `bulk:inflight:{user_id}` только на время
  валидации + создания job-record (~100ms), затем сразу снимает после
  `enqueue_job()`. Параллельно ставит `async:job:{user_id}:zip:{job_id}`
  с `TTL = expires_at - now` (≈24h) — это **не** блокирует sync-ops
  (delete/move/upload). Лимит async-jobs: 3 одновременных zip-jobs на
  пользователя (если 4-й — 429 `too_many_async_jobs`).

### 2.4. ARQ-worker

`backend/app/worker/tasks/files.py`:

**Streaming-стратегия:** `zipfile.writestr()` буферизует весь файл в RAM —
для архивов >200 MB или отдельных файлов >500 MB ведёт к OOM воркера.
Используем **`tempfile.SpooledTemporaryFile(max_size=8*1024*1024)`**
(spill-to-disk выше 8 MB) для downstream-stream NC → temp → `zf.write()`.
`zf.write(temp_path, arcname=name)` стримит с диска кусками 64 KB
(внутренняя реализация stdlib).

```python
import tempfile, zipfile
from datetime import date

async def build_zip_archive(ctx, job_id: str) -> None:
    """Стримит файлы из NC в ZIP. Skip-on-missing.

    Use SpooledTemporaryFile per file → zf.write(temp, arcname).
    zipfile.write() handles chunked I/O internally (no full RAM buffering).
    force_zip64=True защищает от 4 GB ZIP-overhead.
    """
    # 1. UPDATE status='running', started_at=now()
    # 2. Открыть /data/file_zips/{job_id}.zip:
    zip_path = f"/data/file_zips/{job_id}.zip"
    with zipfile.ZipFile(zip_path, "w", zipfile.ZIP_DEFLATED, allowZip64=True) as zf:
        for filename in filenames:
            try:
                response, http_client = await nc.download_stream(...)
            except NextcloudError as e:
                error_files.append({"name": filename, "reason": "not_found" if e.status == 404 else "nc_error"})
                continue
            try:
                # SpooledTemporaryFile: in-RAM до 8 MB, спиллится на диск выше.
                with tempfile.SpooledTemporaryFile(max_size=8 * 1024 * 1024) as tmp:
                    async for chunk in response.aiter_bytes(chunk_size=64 * 1024):
                        tmp.write(chunk)
                    tmp.seek(0)
                    # Сохраняем во временный файл на диске для zf.write (нужен путь),
                    # либо используем ZipInfo + zf.open() для in-memory case.
                    # Простой путь: rollover() → name доступно только при spill.
                    # Production-reference: использовать zf.open(arcname, "w", force_zip64=True)
                    # + chunked tmp.read() → writer.write().
                    with zf.open(filename, "w", force_zip64=True) as writer:
                        while True:
                            chunk = tmp.read(64 * 1024)
                            if not chunk: break
                            writer.write(chunk)
            finally:
                await http_client.aclose()
    # 3. archive_name = f"{folder.name}-{date.today():%Y-%m-%d}.zip"
    # 4. Финальный статус:
    #    - len(error_files) == len(filenames): status='failed', os.unlink(zip_path).
    #    - len(error_files) > 0: status='done_with_errors'.
    #    - else: status='done'.
    # 5. UPDATE file_path, archive_name, size_bytes, completed_at, error_files.
    # 6. Снять async:job:{user_id}:zip:{job_id} ключ (или оставить до expires_at).
```

> **Замечание:** `zipfile` синхронный — внутри ARQ-task это OK
> (worker per-job). Если в будущем понадобится async — заменить на
> `stream-zip` (PyPI), но сейчас stdlib достаточно.

```ts
import { getCsrfToken, CSRF_HEADER } from '@/utils/csrf'
import { refreshAuth } from './index'

export function apiUploadWithProgress<T = unknown>(
  path: string,
  form: FormData,
  opts: UploadProgressOpts = {},
): Promise<T> {
  const doRequest = (): Promise<T> => new Promise((resolve, reject) => {
    const xhr = new XMLHttpRequest()
    xhr.open('POST', `${BASE_URL}${path}`)
    xhr.withCredentials = true
    const token = getCsrfToken()
    if (token) xhr.setRequestHeader(CSRF_HEADER, token)
    if (opts.idempotencyKey) xhr.setRequestHeader('Idempotency-Key', opts.idempotencyKey)
    xhr.upload.onprogress = (e) => {
      if (e.lengthComputable) opts.onProgress?.(e.loaded, e.total)
    }
    xhr.onload = () => {
      if (xhr.status >= 200 && xhr.status < 300) {
        try { resolve(JSON.parse(xhr.responseText) as T) }
        catch { resolve(xhr.responseText as unknown as T) }
      } else {
        const err: any = new Error(`HTTP ${xhr.status}`)
        err.status = xhr.status
        err.response = { status: xhr.status }
        reject(err)
      }
    }
    xhr.onerror = () => reject(new Error('Network error'))
    if (opts.signal) opts.signal.addEventListener('abort', () => xhr.abort())
    xhr.send(form)
  })
  // 401 → refresh → retry (один раз, как в apiUpload).
  return doRequest().catch(async (err: any) => {
    if (err?.status !== 401) throw err
    const ok = await refreshAuth()
    if (!ok) throw err
    return doRequest()
  })
}
```

#### 5.2.2. Логика per-file

**Зависимость:** Sprint 0 (§0.1.4) — `WebDAVClient.move(overwrite=...)`.

- `skip`: текущее M1 поведение → `nc.move(src, dst)` (default `overwrite=False`)
  → 412 → `name_conflict`.
- `overwrite` (**атомарно через WebDAV `Overwrite: T`**):
  ```python
  # Атомарный MOVE — RFC 4918 §9.9.4. NC поддерживает.
  # Никакого "delete + move" — race-free: между шагами никто не успеет
  # вклиниться.
  await nc.move(src, dst, overwrite=True)
  # NC возвращает 204 (overwritten) или 201 (created). Никаких 412.
  # БД: SELECT FOR UPDATE existing FileItem at dst → soft-delete его (deleted_at=now)
  #     UPDATE src FileItem.nc_path = dst, folder_id = target_folder_id
  # Audit: 'files.move_overwrite' с metadata.overwritten_file_id=...
  ```
- `rename` (цикл `move(overwrite=False)` пока не получим успех):
  ```python
  # split_extension контракт: только последний .ext (os.path.splitext-семантика).
  # "file.tar.gz" → ("file.tar", ".gz") → "file.tar (1).gz".
  # ".gitignore" (нет суффикса) → (".gitignore", "") → ".gitignore (1)".
  base, ext = os.path.splitext(name)
  for i in range(1, 100):
      new_name = f"{base} ({i}){ext}"
      try:
          await nc.move(src, f"{dst_folder}/{new_name}", overwrite=False)
          break
      except NextcloudError as e:
          if e.status != 412: raise
  else:
      # Fallback: UUID-suffix после 99 попыток.
      new_name = f"{base} ({uuid.uuid4().hex[:8]}){ext}"
      await nc.move(src, f"{dst_folder}/{new_name}", overwrite=False)
      logger.warning("files.rename_uuid_fallback", original=name, new=new_name)
  ```

### 6.2. БД-миграция

`040_file_items_trash.py`:
```python
op.add_column("file_items", sa.Column("trashed_at", TIMESTAMP(tz=True), nullable=True))
op.add_column("file_items", sa.Column("trashed_by", UUID, sa.ForeignKey("users.id", ondelete="SET NULL")))

```

> `trashed_at` отдельно от `deleted_at`: deleted_at = «удалён навсегда»,
> trashed_at = «в корзине». В корзине `deleted_at IS NULL`,
> `trashed_at IS NOT NULL`.

> **Unique-индекс:** новых уникальных индексов **не добавляем**. Существующий
> `idx_file_items_nc_path_active` (миграция 038, `unique WHERE deleted_at IS NULL`)
> обеспечивает уникальность. При перемещении файла в trash `nc_path`
> обновляется на trash-путь (`_trash/{user_id}/{job_id}/{name}`) — коллизий
> с активными файлами не возникает (разные nc_path). При restore коллизия
> с активным файлом → `UniqueViolation` от Postgres → ловим в backend и
> применяем `conflict_strategy` (default `rename`).
>
> **Альтернатива (откладывается в M3 как refactor):** заменить уникальность
> по `nc_path` на `(folder_id, lower(name)) WHERE deleted_at IS NULL AND trashed_at IS NULL`
> — семантически правильнее (file-id первичен, путь — производное), как у
> Dropbox/Google Drive. В M2 не делаем, чтобы не задеть M1-функциональность.

### 6.3. NC-структура
- При перемещении в корзину: `nc.move(src, f"_trash/{user_id}/{job_id}/{name}")`.
  - `job_id` = UUID — защита от коллизий (один пользователь может удалить
    два файла с одинаковыми именами из разных папок).
  - `_trash/` физически — `PortalFiles/_trash/...` (внутри NC_FILES_ROOT).
- При восстановлении: `nc.move(trash_path, original_path)`; если
  `original_folder_id` удалён → 422 `original_folder_gone`, пользователь
  выбирает другую папку.

### 6.4. Endpoints

| Метод | URL | Описание |
|---|---|---|
| GET | `/files/trash` | Список trashed файлов пользователя (пагинация). Без секций — плоский список с колонкой `original_folder_path` (или маркером «(папка удалена)»). Admin может передать `?user_id=...` для просмотра чужой корзины (API-only в M2, без UI). |
| POST | `/files/trash/restore` | Body `{file_item_ids: [...], target_folder_id?: UUID, conflict_strategy?: ConflictStrategy}` |
| POST | `/files/trash/purge` | Hard-delete конкретных файлов из корзины (или всех) |

**Логика restore:**
1. Если `target_folder_id` явно передан → используем его (требует `editor`).
2. Иначе для каждого `file_item_id`:
   - `original_folder_id IS NOT NULL` и папка живая → restore туда.
   - Иначе → 422 `original_folder_gone` со списком таких file_item_ids,
     frontend показывает обязательную модалку выбора целевой папки.
3. При коллизии имени (партial unique индекс по активным `nc_path`):
   - default `conflict_strategy = "rename"` (Google Drive-style, не теряем
     данные при restore).
   - переиспользует `os.path.splitext` + цикл из M2.5.

- **Изменения в существующих endpoints (behavior-change, см. ниже):**
  - `DELETE /files/file` → теперь moves в trash (вместо физ-удаления).
    Параметр `?hard=true` (admin) → старое поведение.
  - `POST /files/folders/{id}/bulk-delete` → moves в trash.
  - `DELETE /files/folders/{id}?hard=true` (admin) → cascade hard-delete
    всех trashed-файлов в этой папке (`SELECT FROM file_items WHERE
    original_folder_id = ? AND trashed_at IS NOT NULL` → `nc.delete` каждого
    trash_nc_path → DELETE rows). Без `?hard=true` папка попадает в trash сама.
- ACL для restore: владелец trashed-записи (`trashed_by == user.id`) или
  admin.
- ACL для GET `/files/trash`: видны только свои; admin видит чужие через
  `?user_id=...` (явный query-param, без `?all=true` в M2).

**Audit-event metadata:**
- При soft-delete (move в trash) — `audit.metadata.action = "trashed"`.
- При hard-delete (`?hard=true` или cron purge) — `audit.metadata.action = "purged"`.
- При restore — `audit.metadata.action = "restored"`, `metadata.original_folder_id`,
  `metadata.target_folder_id` (если restore в другую папку).

**Bump api-contracts.md:**
- Раздел `DELETE /files/file` помечается `behavior-change: soft-delete by default since v2.6`.
- Указать миграционный путь для интеграций: использовать `?hard=true`
  если нужно прежнее поведение.

## 7. M2.7. Bulk-операции на папках (рекурсивно) — L

### 7.1. Скоуп
- `POST /files/folders/bulk-delete`: массовое удаление папок (рекурсивно
  все вложенные файлы и подпапки).

  родительскую.
- ACL: `editor` на каждой папке + recursive проверка вложенных файлов
  (через CTE).

### 7.2. Backend

#### 7.2.1. ACL helper
```python
async def check_recursive_folder_acl(
    db, user, folder_ids: list[UUID], required_perm: str
) -> dict[UUID, bool]:
    """Возвращает {folder_id: True} только если у user есть required_perm
    на саму папку И на ВСЕ вложенные подпапки.
    Реализация через рекурсивный CTE по file_folders.parent_id +
    batch_resolve_folder_permissions для всего поддерева.
    """
```

#### 7.2.2. Endpoints
| Метод | URL | Body | Лимиты |
|---|---|---|---|
| POST | `/files/folders/bulk-delete` | `{folder_ids: [...]}` | ≤20 папок, rate `1/min` |
| POST | `/files/folders/bulk-move` | `{folder_ids: [...], target_parent_id?: UUID}` | ≤20 папок, rate `1/min` |

> `target_parent_id = null` → корневой уровень.

#### 7.2.3. Логика

**Move folder + recursive UPDATE `nc_path`:**

Транзакция (asyncpg / SQLAlchemy):
1. `BEGIN`
2. `SELECT FOR UPDATE` перемещаемой папки + всех потомков (через CTE) —
   блокировка от parallel move/delete.
3. Cycle-check: проверить, что `target_parent_id` не входит в descendants
   перемещаемой папки → 422 `cycle_detected` со списком `cycle_folder_ids`.
4. Атомарный WebDAV `MOVE` коллекции (`nc.move(src_collection, dst_collection,
   overwrite=False)`).
5. Recursive UPDATE `nc_path` всех потомков:
   ```sql
   WITH RECURSIVE descendants AS (
       -- Корень: сама перемещаемая папка с новым nc_path
       SELECT id, parent_id, name, $new_parent_path::text || '/' || name AS new_nc_path
       FROM file_folders
       WHERE id = $moved_folder_id

       UNION ALL

       -- Потомки: рекурсивно от уже найденных
       SELECT f.id, f.parent_id, f.name, d.new_nc_path || '/' || f.name
       FROM file_folders f
       JOIN descendants d ON f.parent_id = d.id
       WHERE f.deleted_at IS NULL
   )
   UPDATE file_folders SET nc_path = d.new_nc_path
   FROM descendants d
   WHERE file_folders.id = d.id;
   ```
6. Аналогично для `file_items` (JOIN file_folders по folder_id, обновить
   их `nc_path = folder.nc_path || '/' || item.name`).
7. UPDATE `parent_id` корня перемещаемой папки на `target_parent_id`.
8. `COMMIT`.

**Компенсация при сбое:**
- Если NC MOVE упал → ROLLBACK транзакции (БД не тронута).
- Если NC MOVE прошёл, но COMMIT упал (редкий случай — Postgres недоступен)
  → компенсирующий `nc.move(dst, src)` обратно. Если и это упало —
  `logger.error("files.move_compensation_failed", ...)` + alert
  (manual cleanup в `_trash/{admin}/orphans/`).

**Delete folder:**
- Рекурсивно soft-delete всех вложенных `file_folders` и `file_items`;
- В NC — MOVE всей коллекции в `_trash/{user_id}/{job_id}/{folder_name}/`
  (использует M2.6 инфраструктуру). При restore коллекции — обратный MOVE.

**In-flight:**
- `bulk:inflight:{user_id}`, TTL 300s (5 мин — recursive операции медленнее).
- Async-режим (M3): если recursive bulk на >100 файлов → ARQ-job +
  `async:job:{user_id}:folder_bulk:{job_id}`. В M2 — sync, до 20 папок.

| C12 | Retention от trashed_at | Restore сбрасывает `trashed_at = NULL`; повторное удаление = новый счётчик с нуля. См. §6.5. |

## 12. Что НЕ войдёт в M2 (явный out-of-scope)

- **Inline-rename файлов в таблице** (двойной клик на имя) — M3.

  отдельной модели.

- **Совместное редактирование вне Collabora** — out-of-scope портала.
- **WebSocket real-time updates** при изменениях другими пользователями —
  M3, требует sync-механизма.
- **Mobile app / responsive overhaul** — отдельный roadmap.
