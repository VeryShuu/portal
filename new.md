# Аудит портала глазами пользователя

Документ описывает наблюдения после прохождения типовых пользовательских сценариев (вход → главная → новости → поиск статьи → загрузка файла → фотогалерея → профиль). По каждому пункту указано:

- **Как сейчас** — текущее поведение/реализация
- **Чем плохо** — почему это проблема для пользователя или разработки
- **Как должно быть** — предлагаемое решение
- **Сложность** — оценка трудозатрат (S/M/L/XL)
- **Эффект** — что выиграет пользователь/проект

Шкала сложности:

- **S** — до 1 рабочего дня, изменения локальны
- **M** — 1–3 дня, затрагивает несколько модулей
- **L** — 1–2 недели, требует миграций/рефакторинга
- **XL** — больше 2 недель, затрагивает архитектуру

## 1. UX и навигация

### 1.2. Перегруженная главная

- **Как сейчас:** `HomePage.vue` (550 строк) рисует подряд: `portal-banner` → `HeroBlock` → секция «Featured (закреплённые)» → заголовок «Свежее» → grid из 4 новостей → правый столбец из виджетов (Сервисы, Фото, Недавние статьи, Закладки).
- **Чем плохо:** одновременно 3 точки фокуса (баннер + hero + featured news) часто несут одну и ту же информацию. Закреплённая новость и hero-блок визуально соревнуются. Пользователь не понимает «куда смотреть в первую очередь».
- **Как должно быть:** оставить **один основной фокус** — либо HeroBlock (брендинговый), либо Featured news. Виджеты сделать настраиваемыми через `users.preferences.home_widgets` (список ID + порядок), пользователь сам выбирает что видеть. Дефолтный набор — минимальный: новости + сервисы.
- **Сложность:** M
- **Эффект:** снижение когнитивной нагрузки, рост engagement по основной CTA.

### 1.3. 13 вкладок в админке без поиска

- **Как сейчас:** `AdminPage.vue` содержит 13 lazy-loaded табов (Users, UserAttributes, Links, Email, System, Keycloak, Branding, Modules, KB, Analytics, Audit, Monitoring, Photos).
- **Чем плохо:** найти настройку «лимит размера загружаемого файла» или «whitelist CIDR» — это перебор табов. Админ тратит секунды на поиск каждый раз.
- **Как должно быть:** глобальный поиск по настройкам внутри `/admin` (Ctrl+K). Индекс — JSON-карта `{label, description, tab, anchor}`, обновляется при добавлении настройки. Прыжок прямо к нужному полю с подсветкой.
- **Сложность:** M
- **Эффект:** −5–10 секунд на типичную админскую операцию.

## 2. Производительность (Frontend)

### 2.3. PhotosIndexPage — god-component 34 КБ

- **Как сейчас:** `pages/photos/PhotosIndexPage.vue` (34.69 КБ в одном файле).
- **Чем плохо:** долгая компиляция Vite в dev, большой initial chunk при первом открытии раздела, сложно поддерживать (любое изменение требует перечитать весь файл). Скорее всего, нет виртуального скролла — при 500+ фото в папке тормозит.
- **Как должно быть:** декомпозиция на `PhotosToolbar`, `PhotosTree`, `PhotosGrid` (виртуальный через `vue-virtual-scroller`), `PhotosUploader`, `PhotoLightbox` (уже есть). Логика в composable `usePhotos.ts`.
- **Сложность:** L
- **Эффект:** инициализация раздела −500 мс, плавный скролл при больших папках.

### 2.4. i18n грузится целиком — 74 КБ ru.json

- **Как сейчас:** `i18n/ru.json` 74 КБ, `en.json` 52 КБ — оба грузятся при старте.
- **Чем плохо:** ~125 КБ JSON парсится в JS-объект на каждом холодном входе, замедляет TTI. Большая часть строк (admin, photos, kb) не нужна на главной.
- **Как должно быть:** namespace-структура (`common`, `nav`, `home`, `news`, `kb`, `photos`, `admin`...). На старте грузится только `common`+`nav`+ namespace текущего раздела через `i18n.loadLocaleMessages('admin')` при заходе в `/admin`.
- **Сложность:** M (плюс миграция всех ключей)
- **Эффект:** −80 КБ initial bundle, парсинг −40 мс.

### 2.6. TanStack Query заявлен, но не используется

- **Как сейчас:** в `AGENTS.md` стек указывает «TanStack Query (Vue Query) + ofetch». В `HomePage.vue` — ручное `ref(true)` + `try/finally`.
- **Чем плохо:** теряются преимущества Query: dedup запросов между компонентами, фоновое обновление, оптимистичные апдейты, кэш. Каждое монтирование делает запрос заново.
- **Как должно быть:** обернуть API-клиенты в `useQuery`/`useMutation`. Кэш-ключи по `['news', filters]`, `['links']`, `['bookmarks']`. На главной и в `/news` запрос новостей разделится.
- **Сложность:** L (миграция всех страниц)
- **Эффект:** −30–50% сетевых запросов при навигации между страницами.

## 3. Внешний вид и дизайн

### 3.4. Дефолтные ionicons5 outline везде

- **Как сейчас:** `@vicons/ionicons5` outline-стиль во всём интерфейсе.
- **Чем плохо:** «бесплатный шаблон»-вид. Линии тонкие, на маленьких размерах теряются. Недостаточно акцентных иконок (нет filled-варианта для активного состояния).
- **Как должно быть:** определить design-rule: outline в навигации, filled в активном состоянии и в кнопках действия. Либо перейти на единый набор Lucide/Phosphor с постоянной шириной штриха.
- **Сложность:** M
- **Эффект:** более «фирменный» вид, лучше визуальная иерархия.

## 4. Функционал, которого не хватает

### 4.1. Уведомления — нет «прочитать всё» и группировки

- **Как сейчас:** `NotificationsDropdown.vue` показывает список событий, помечать прочитанными — поштучно.
- **Чем плохо:** при 30+ уведомлений за выходные жать каждое — пытка.
- **Как должно быть:** кнопка «Прочитать всё», группировка по дате (Сегодня / Вчера / Раньше), фильтр по типу (новости / упоминания / системные).
- **Сложность:** S (UI) + S (бэкенд: `POST /notifications/read-all`)
- **Эффект:** сильно улучшает повседневный UX.

### 4.2. Глобальный поиск без истории и фильтров

- **Как сейчас:** `GlobalSearch.vue` (Ctrl+K) — модалка с input + результаты.
- **Чем плохо:** нет «недавних запросов», нет быстрых фильтров «только KB / только файлы / только люди» прямо в дропдауне. Каждый раз набираешь заново.
- **Как должно быть:** под input — табы фильтров (`Все / KB / Новости / Файлы / Люди`), под ними — «Недавние запросы» из `localStorage`. ↓/↑ навигация, Enter — переход.
- **Сложность:** M
- **Эффект:** поиск становится главной точкой входа.

### 4.3. KB — нет TOC и якорей

- **Как сейчас:** статьи рендерятся целиком, длинная статья — простыня без оглавления. Заголовки `<h2>` без id.
- **Чем плохо:** на статье 5000+ слов невозможно ориентироваться. Нельзя поделиться ссылкой на конкретный раздел.
- **Как должно быть:** генерировать TOC справа sticky из markdown headings (плагин `markdown-it-anchor` + `markdown-it-toc-done-right`). Якоря `#heading-slug` в URL.
- **Сложность:** M
- **Эффект:** KB становится действительно базой знаний, а не списком статей.

### 4.4. Файлы — нет drag-n-drop и multi-select

- **Как сейчас:** загрузка через кнопку, действия над файлами — поштучно.
- **Чем плохо:** неудобно загружать 20 файлов (надо открыть диалог 20 раз?), нельзя удалить пачку.
- **Как должно быть:** drop-zone на всю страницу `FilesPage`, multi-select через Shift/Ctrl+click + bulk panel («Скачать», «Переместить», «Удалить»).
- **Сложность:** M
- **Эффект:** существенный рост качества файлового модуля.

### 4.6. Профиль — нет «коллег из моего отдела»

- **Как сейчас:** `ProfilePage` показывает свои данные, отдел из JWT (`department`).
- **Чем плохо:** атрибут есть, но «список коллег по отделу» нигде не отображается. Это очевидная функция корпоративного портала.
- **Как должно быть:** в профиле виджет «Коллеги из отдела X» (5–10 человек, кнопка «все»). Поиск по департаментам в `/users`.
- **Сложность:** S (есть данные, нужен endpoint `GET /users?department=X`)
- **Эффект:** социальная связность.

## 6. Архитектура (Frontend)

### 6.1. API-клиенты непоследовательны

- **Как сейчас:** `photos.ts` и `kb.ts` сгенерированы из openapi (`types.gen.d.ts`). `news.ts`, `links.ts`, `users.ts`, `files.ts` — написаны вручную с дублирующимися типами.
- **Чем плохо:** при изменении схемы API можно забыть обновить ручной клиент → runtime errors. Половина фронта типобезопасна, половина — нет.
- **Как должно быть:** **либо** генерировать всё через `openapi-typescript` (рекомендую), **либо** всё руками. Не половинчато.
- **Сложность:** M
- **Эффект:** меньше багов на стыке front/back.

### 6.2. Глобальный 401-handler через CustomEvent

- **Как сейчас:** в `api/index.ts` при 401 диспатчится событие `auth:expired`, обработчик в auth-store очищает user, делается редирект.
- **Чем плохо:** event-bus паттерн фрагилен: легко забыть подписаться, сложно отлаживать. Race-conditions неизбежны (тут уже есть `_redirectingOnExpiry` дебаунс — патч на симптом).
- **Как должно быть:** API-слой возвращает Result/Error, auth-guard в Vue Router ловит 401 централизованно. Один источник истины.
- **Сложность:** M
- **Эффект:** меньше «магии», легче тестировать.

### 6.3. Нет утилитарных CSS-классов

- **Как сейчас:** scoped CSS в каждом `.vue` + `tokens.css` + `admin-tabs.css` + `global.css`. Каждая страница изобретает grid/flex.
- **Чем плохо:** CSS дублируется, бандл растёт, согласованность отступов/радиусов на глаз.
- **Как должно быть:** UnoCSS или Tailwind в режиме «in-addition-to-Naive» с дизайн-токенами из `tokens.css`. Утилитарные `.flex .gap-4 .p-md` упрощают вёрстку.
- **Сложность:** L
- **Эффект:** −20–30% CSS-кода, единые отступы.

## 7. Производительность (Backend)

### 7.1. Каждое открытие страницы пишет в audit_log?

- **Как сейчас:** аудит партиционирован, batch-insert через ARQ — это правильно.
- **Чем плохо:** **надо проверить**, что просмотры страниц не пишутся в `audit_log`. Если да — таблица растёт линейно с трафиком, аналитика становится дороже.
- **Как должно быть:** просмотры → отдельная таблица `analytics_events` или Prometheus-counter. `audit_log` — только для write-операций и security-событий.
- **Сложность:** S (если уже разделено) или M (миграция)
- **Эффект:** медленный рост audit-таблицы, лучшая ретенция.

### 7.2. FTS на pg_trgm для typeahead на >50k записей

- **Как сейчас:** typeahead — `pg_trgm` similarity, основной поиск — hunspell_ru.
- **Чем плохо:** `pg_trgm` GIN-индекс работает, но при ~100k+ записей с widget-search отклик >300 мс — ощутимо в input.
- **Как должно быть:** мониторить latency, при росте объёма — подключить Meilisearch sidecar (10–20 МБ RAM, доли мс на typeahead). Альтернатива — кэширование топ-1000 entries в Redis.
- **Сложность:** L (Meilisearch) / M (Redis-кэш)
- **Эффект:** масштабируемость поиска до 1М+ записей.

### 7.3. SSR/streaming для первой отрисовки

- **Как сейчас:** SPA, белый экран до загрузки JS-бандла.
- **Чем плохо:** first paint 1–2 секунды на медленных машинах. Для интранета терпимо, но воспринимается как «медленно».
- **Как должно быть:** Nuxt с SSR первого экрана (главная, KB-статья, новость). Гидратация — после.
- **Сложность:** XL (миграция Vue SPA → Nuxt)
- **Эффект:** мгновенный first paint, лучше воспринимаемая скорость. **НЕ рекомендуется делать сейчас** — слишком дорого относительно эффекта.

# Аудит портала глазами редактора (контент-мейкера)

Документ описывает наблюдения после прохождения сценариев создания контента: создание новости с обложкой/галереей/вложениями → написание KB-статьи с медиа → загрузка фотоальбома → встраивание видео. Формат тот же: «как сейчас → чем плохо → как должно быть → сложность → эффект».

Ключевые файлы, которые анализировались:

- `frontend/src/pages/NewsFormPage.vue` (19 КБ — форма создания/редактирования новости)
- `frontend/src/pages/KbArticleFormPage.vue` (7 КБ — форма KB-статьи)
- `frontend/src/components/RichEditor.vue` (TipTap-редактор)
- `frontend/src/components/NewsCoverUpload.vue` (обложка)
- `frontend/src/components/NewsGalleryViewer.vue`, `NewsAttachmentsViewer.vue`
- `frontend/src/pages/photos/PhotosIndexPage.vue` (34 КБ — фотогалерея)
- `frontend/src/composables/usePhotoUpload.ts`

## 1. Создание новости — критические проблемы рабочего процесса

### 1.1. Галерея и вложения недоступны до первого сохранения

- **Как сейчас:** в `NewsFormPage.vue` секции «Галерея» и «Вложения» показывают предупреждение «Сначала сохраните черновик» (`news.form.saveFirst`), кнопки upload disabled при `!newsId`. Чтобы загрузить картинки в галерею, редактор обязан **сначала** заполнить заголовок и нажать «Сохранить черновик», получить ID, и только потом загружать.
- **Чем плохо:** ломает естественный workflow редактора — он сначала собирает все материалы (картинки лежат на рабочем столе), потом пишет текст. Получается «пишу заголовок → сохраняю черновик → загружаю → редактирую → сохраняю» вместо «всё сразу». Каждый раз режет flow.
- **Как должно быть:** при создании новой новости сразу делать `POST /news/draft` (без обязательных полей, только `author_id`) и получать `id`. Все аплоады работают с первого момента. Если пользователь уйдёт со страницы без подтверждения — черновик автоматически чистится через 24 часа cron-job или ARQ-таской (или помечается как `discarded`).
- **Сложность:** S (бэкенд: сделать title nullable у draft + cleanup-job)
- **Эффект:** редактор может загружать материалы параллельно с написанием текста.

### 1.2. Автосохранение только в edit-режиме черновика

- **Как сейчас:** `autoSaveTimer` срабатывает каждые 30 секунд, но **только** если `isEdit && newsId && status === 'draft'`. Новый текст пропадает при F5 до первого ручного сохранения. Опубликованная новость не автосохраняется при правке.
- **Чем плохо:** Главный страх редактора — потерять текст. F5, закрытая вкладка, упавший VPN — текст пропал. Опубликованную новость правишь час, не сохраняешь — улетает.
- **Как должно быть:** при создании сразу делается draft (см. 1.1) и автосохранение работает с момента ввода первой буквы. Дополнительно — **локальный backup в IndexedDB** ключом `draft-news-<id>` каждые 5 секунд, при возврате на форму предлагать «Восстановить несохранённые изменения от 14:23?». Для опубликованных новостей — отдельная ветка `pending_changes` (можно править без публикации).
- **Сложность:** M
- **Эффект:** ноль потерянных текстов.

### 1.3. Нет превью перед публикацией

- **Как сейчас:** редактор пишет в TipTap (markdown source), а как реально будет выглядеть — увидит только после публикации, перейдя на `/news/<id>`. Кнопки «Превью» в форме нет.
- **Чем плохо:** в WYSIWYG-редакторе и финальной странице разные стили (другая ширина, другие шрифты, другой рендер картинок с обложкой и фокальной точкой). Часть багов (битый markdown, неправильная вёрстка) ловится только после публикации → правка → публикация. Особенно критично для закреплённой новости на главной.
- **Как должно быть:** кнопка «Превью» рядом с «Опубликовать» — открывает модалку или новую вкладку `/news/<id>?preview=token`, где новость рендерится точно как в продакшене (с обложкой, галереей, всем). Токен короткоживущий, доступен только автору.
- **Сложность:** S
- **Эффект:** меньше «правок после публикации», уверенность в результате.

### 1.4. Cover, галерея, вложения — три разных UI на одной странице

- **Как сейчас:**
  - Cover — отдельный компонент `NewsCoverUpload.vue` (с focal point top/center/bottom)
  - Галерея — drag-n-drop сортировка через нативные `dragstart/dragover/drop` события
  - Вложения — простой список с кнопкой удаления
- **Чем плохо:** три разных UX для трёх типов медиа. Редактор учится трём паттернам. Drag-n-drop в галерее на нативном HTML5 API — без визуальной обратной связи (только класс `drag-over`), на тач-устройствах не работает.
- **Как должно быть:** общий компонент `MediaPicker` с табами «Обложка / Галерея / Файлы» и единым визуальным языком. Сортировка через `vuedraggable` (Sortable.js) — работает на тач-устройствах, есть placeholder, плавная анимация.
- **Сложность:** M
- **Эффект:** единый ментальный паттерн, нативный drag на мобильных.

### 1.5. Невозможно вставить картинку из галереи в тело новости

- **Как сейчас:** галерея новости — отдельный блок в нижней части страницы, рендерится в `NewsGalleryViewer` под текстом. В тело статьи через TipTap картинки **загружаются отдельно** (`apiUpload` в `kb/articles/.../media`).
- **Чем плохо:** редактор грузит одну и ту же картинку дважды: один раз в галерею (для слайдера), второй раз — в тело статьи. Дубль файлов в Nextcloud.
- **Как должно быть:** в TipTap toolbar — кнопка «Вставить из галереи новости», открывает модалку с миниатюрами уже загруженных в галерею файлов, клик → вставка `<img>` со ссылкой на тот же URL. Аналогично для KB-статей.
- **Сложность:** M
- **Эффект:** −50% дубликатов медиа, быстрее работа.

### 1.6. Нет шаблонов новостей

- **Как сейчас:** каждая новость пишется с нуля.
- **Чем плохо:** регулярные форматы (День рождения, Объявление о собрании, Релиз продукта, Опрос) набираются вручную каждый раз. Корпстиль уезжает: один HR пишет с эмодзи, другой — без, третий путает «Уважаемые коллеги» и «Привет всем».
- **Как должно быть:** Admin-таб «Шаблоны новостей»: набор готовых шаблонов с pre-filled `title`, `body`, `categories`. При создании — выпадающий «Создать из шаблона». Шаблоны хранятся в БД (`news_templates` table или JSONB в system settings).
- **Сложность:** M
- **Эффект:** консистентность контента, скорость для типовых форматов.

### 1.7. Поле «Опубликовано» редактируемое — это бомба

- **Как сейчас:** в форме два date-picker: `publish_at` (запланировать) и `published_at` (фактическая дата публикации). Оба редактируемые.
- **Чем плохо:** редактор может **перезаписать `published_at`** на любую дату — задним числом, в будущее, на 1970 год. Это ломает сортировку, ломает аналитику, ломает «Свежие новости». Феномен «вчерашняя новость попала наверх» именно отсюда.
- **Как должно быть:** `published_at` — read-only (показывается, но не редактируется). Если нужно «опубликовать задним числом» — отдельная галочка «Backdate» с подтверждением и записью в audit_log. Для штатного перепланирования есть `publish_at`.
- **Сложность:** S
- **Эффект:** целостность ленты новостей, аудит подмен.

### 1.8. Категории — `tag` mode без модерации

- **Как сейчас:** `<n-select multiple tag />` — пользователь может ввести **новую** категорию прямо в инпуте, она сохраняется. Список существующих подгружается через `fetchNewsCategories`.
- **Чем плохо:** разрастание категорий: «HR», «hr», «Эйчар», «Кадровое» — четыре категории про одно. Фильтрация по категориям становится бесполезной.
- **Как должно быть:** для всех — только выбор из списка. Создание новой категории — отдельная роль (admin/editor-lead) либо отдельный workflow «предложить категорию» с одобрением. `tag` mode выключить.
- **Сложность:** S
- **Эффект:** чистый таксономический слой, рабочая фильтрация.

### 1.9. Нет отслеживания статистики по новости в форме редактирования

- **Как сейчас:** просмотры/реакции/комментарии новости (если есть) видны только на странице самой новости.
- **Чем плохо:** редактор открывает форму «дополнить материал» и не понимает контекста — насколько публикация зашла, надо ли усилить.
- **Как должно быть:** в правом sidebar формы (когда `isEdit`) — мини-блок «Статистика»: просмотры, уникальные читатели, реакции, время чтения (медиана). Ссылка «Полная аналитика» в admin/analytics.
- **Сложность:** S
- **Эффект:** обратная связь редактору в момент работы.

## 2. RichEditor (TipTap) — узкие места

### 2.1. Toolbar выглядит как 2010 год

- **Как сейчас:** в `RichEditor.vue` кнопки toolbar — **символы** в `<b>B</b>`, `<i>I</i>`, `<s>S</s>`, `H2`, `H3`, `≡`, `1.`, `"`, `</>`, `⯇ ☰ ⯈`, эмодзи `🖼` и `▶`.
- **Чем плохо:** микс HTML-тегов как иконок + Unicode-стрелочек + эмодзи. На разных шрифтах рендерится по-разному (на Windows эмодзи — цветные, символы — моноширинные). Эстетически не соответствует остальному порталу с ionicons5. Aria-label есть, но визуально выглядит как «студенческий проект».
- **Как должно быть:** все кнопки — иконки из ionicons5 (`text-bold`, `text-italic`, `headings`, `list-outline`, `image-outline`, `videocam-outline`, `arrow-undo`, `arrow-redo`). Группировка через тонкие разделители, sticky toolbar при скролле.
- **Сложность:** S
- **Эффект:** визуальная согласованность.

### 2.2. Нет таблиц, разделителей, цитирования с автором, callout-блоков

- **Как сейчас:** базовый StarterKit + Image + Link + TextAlign + IframeEmbed. Нет `Table`, `HorizontalRule`, `Highlight`, `Callout` (info/warning/tip), `Details/summary`.
- **Чем плохо:** для KB-статей с инструкциями жизненно нужны таблицы и callout-блоки («Внимание!», «Совет»). Сейчас редактор выкручивается через `>` цитаты или скрин таблицы из Excel. Скриншоты таблицы — это deal-breaker для KB как живой документации.
- **Как должно быть:** добавить TipTap-расширения: `@tiptap/extension-table` (с UI для добавления колонок/строк), `@tiptap/extension-horizontal-rule`, кастомное `Callout` с типами `info/warning/tip/danger`, `Details` для сворачиваемых секций.
- **Сложность:** M
- **Эффект:** KB становится полноценной документацией.

### 2.3. Вставка ссылки — нет диалога

- **Как сейчас:** `Link` extension подключен, но в toolbar **нет кнопки** «Вставить ссылку». Сейчас, видимо, работает только через autolink (вставил URL — он подсветился).
- **Чем плохо:** редактор не может выделить текст «нажмите сюда» и сделать его ссылкой через UI. Через клавиатурный shortcut TipTap-link тоже без UI.
- **Как должно быть:** кнопка `[link]` в toolbar → модалка с полями `URL`, `Текст` (если ничего не выделено), `Открывать в новой вкладке`, `rel=nofollow` (для KB на внешние ресурсы). Кнопка-крестик «Удалить ссылку» если в выделении уже есть ссылка.
- **Сложность:** S
- **Эффект:** базовая редакторская функция работает.

### 2.4. Drag-n-drop / paste картинок работает только в KB

- **Как сейчас:** `uploadImage()` в `RichEditor.vue` использует `apiUpload('/kb/articles/${articleId}/media')`. Для новостей `articleId` не передаётся → drop/paste картинки **молча не работает**.
- **Чем плохо:** редактор перетаскивает картинку в тело новости — ничего не происходит, никакой ошибки. Загадочный баг, очень фрустрирует.
- **Как должно быть:** `RichEditor` принимает props `uploadEndpoint` (универсальный URL загрузки), parent передаёт `/kb/articles/.../media` или `/news/.../media`. На бэке — endpoint `POST /news/<id>/inline-media` для тела новости. Без endpoint — paste/drop отключён, но **с уведомлением** «Загрузка в тело новости доступна после первого сохранения».
- **Сложность:** S
- **Эффект:** работает paste/drop в новостях.

### 2.5. Вставка видео — только iframe URL

- **Как сейчас:** диалог «Вставить видео» принимает iframe-URL или embed-ссылку, парсится `src=""` через regex.
- **Чем плохо:** редактор берёт ссылку с YouTube/RuTube/VK Video в адресной строке (`https://youtube.com/watch?v=...`) — не работает. Нужна iframe-embed ссылка, которую надо отдельно копировать через «Поделиться → Встроить».
- **Как должно быть:** распознавать паттерны URL: youtube.com/watch, youtu.be, rutube.ru, vk.com/video, vk.ru/video — преобразовывать в embed-URL автоматически. Подсказка в плейсхолдере: «Вставьте ссылку на видео с YouTube, RuTube, ВК».
- **Сложность:** S
- **Эффект:** «вставил → работает», без копаний в настройках.

### 2.6. Markdown-источник недоступен

- **Как сейчас:** TipTap пишет в markdown через `tiptap-markdown`, источник доступен в `editor.storage.markdown.getMarkdown()`, но в UI его не видно.
- **Чем плохо:** опытному редактору быстрее правнуть markdown руками (особенно сложные таблицы, ссылки в списке). А ещё — диагностика «почему странно отображается» через просмотр исходника.
- **Как должно быть:** кнопка-переключатель в toolbar `[ </> ]` — переключение между WYSIWYG и `<n-input type="textarea">` с markdown. Изменения синхронизируются.
- **Сложность:** S
- **Эффект:** опытные редакторы быстрее, проще диагностика.

### 2.7. Нет character counter и чтения за минуту

- **Как сейчас:** ни длины статьи, ни оценки времени чтения.
- **Чем плохо:** редактор не понимает, не растянул ли новость на простыню в 3000 слов (никто не дочитает).
- **Как должно быть:** под редактором — мелким шрифтом «1240 символов · ~5 минут чтения». Цвет меняется на orange при >5000 символов.
- **Сложность:** S
- **Эффект:** редактор сам контролирует длину.

## 3. Фотогалерея с точки зрения того, кто загружает фото

### 3.1. Bulk-загрузка без явных границ

- **Как сейчас:** `usePhotoUpload.ts` — машина состояний. Очередь видна, прогресс есть.
- **Чем плохо:** **надо проверить**: что происходит при попытке загрузить 500 фото с DSLR (по 30 МБ RAW)? Streaming на бэкенде есть (`AsyncIterator[bytes]`), но фронт может попытаться запустить 500 параллельных запросов. Браузер падает или зависает.
- **Как должно быть:** в `usePhotoUpload` — ограничение concurrency=4 (как FTP-клиенты), очередь, retry с экспоненциальным backoff на 5xx. UI: «Загружено 23 из 500, текущая: IMG_4521.jpg, скорость 4.2 МБ/с, осталось ~3 мин». Пауза/возобновление.
- **Сложность:** M
- **Эффект:** реальная массовая загрузка фотоальбомов, а не «по 5 штук».

### 3.2. Нет EXIF-сортировки и автогруппировки по дате

- **Как сейчас:** загруженные фото идут в одну папку в порядке загрузки. Сортировка — ручная.
- **Чем плохо:** редактор корпоративного мероприятия загружает 200 фото, ему нужно отсортировать по времени съёмки (EXIF DateTimeOriginal), а не по времени upload. Сейчас приходится переименовывать.
- **Как должно быть:** на бэке при upload вытягивать `DateTimeOriginal` из EXIF в `photos.taken_at`. Сортировка в галерее — по `taken_at`. Опция «Группировать по дате» — автоматически создаёт подпапки «2026-04-15 — Конференция» по EXIF.
- **Сложность:** S (EXIF уже парсится для GPS-strip) + M (UI группировки)
- **Эффект:** правильный порядок 200 фото без ручной работы.

### 3.3. Нет редактора метаданных альбома

- **Как сейчас:** папка фото имеет имя и наследование прав. Описание, обложка, дата мероприятия — ?
- **Чем плохо:** альбом «Корпоратив 2026» — это название папки. Никаких баннеров, описаний, превью. На странице фотогалереи — просто список папок.
- **Как должно быть:** у папки добавить поля `description`, `cover_photo_id`, `event_date`. UI «Свойства альбома» — обложка, описание (markdown), дата. На главной странице фотогалереи — карточки с обложкой и подписью, как в Google Photos / Я.Диск.
- **Сложность:** M (миграция + UI)
- **Эффект:** фотогалерея выглядит как продукт, а не как FTP.

### 3.4. Нет встроенного crop/rotate перед публикацией

- **Как сейчас:** загруженное фото отображается как есть. Если кто-то снял вертикально, EXIF orientation на бэке учитывается? Если не учтён — фото лежит на боку.
- **Чем плохо:** редактор фотогалереи видит «лежащее на боку» фото и не может его повернуть в UI — нужно идти в Photoshop, экспортировать, заливать заново.
- **Как должно быть:** в lightbox — кнопки `Rotate ±90°` (вызывает backend job на пересоздание с новой ориентацией) и `Crop` (для обложки альбома). Обновляются и оригинал, и thumbnails.
- **Сложность:** M (бэкенд + фронт)
- **Эффект:** базовый ретуш без сторонних инструментов.

### 3.5. Watermark и копирайт-инфо

- **Как сейчас:** настроек watermark нет. EXIF GPS strip есть.
- **Чем плохо:** при публикации корпоративных фото автор/событие в EXIF не пишутся. Если фото утечёт — никакой attribution.
- **Как должно быть:** опция альбома «Добавлять watermark» (логотип компании + текст в углу), опция «Записывать author/copyright в EXIF». Watermark применяется к thumbnails (small/medium), оригинал чистый — для архива.
- **Сложность:** M
- **Эффект:** для PR/HR — возможность безопасной публикации без утечки.

## 4. KB-статьи

### 4.1. Нет «черновика» отдельного от опубликованной версии

- **Как сейчас:** KB использует optimistic locking через поле `version`. Опубликованная статья = единственная версия.
- **Чем плохо:** нельзя «переписать большую статью втихую и опубликовать когда готово». Любое изменение видят все сразу. В итоге работа над пере-структурированием статьи делается в Google Docs, копипастится потом одним движением.
- **Как должно быть:** для каждой опубликованной статьи — отдельная `working_copy` (поле `draft_body` рядом с `body`). Редактируется параллельно опубликованному, видна только редакторам, после готовности — `Publish` заменяет `body` атомарно с инкрементом `version`.
- **Сложность:** M (новое поле + workflow)
- **Эффект:** реальная редакторская работа над живой документацией.

### 4.2. Нет «история изменений» в UI для редактора

- **Как сейчас:** есть `KbVersionDiffModal.vue` — diff между версиями. Но как часто им пользуются?
- **Чем плохо:** редактор не видит на странице article «кто что менял за последний месяц». Только при ручном открытии диффа.
- **Как должно быть:** в sidebar статьи — вкладка «История» с таймлайном (кто, когда, что изменил, кнопка «Показать diff», «Откатить к этой версии»).
- **Сложность:** S (UI поверх существующего API)
- **Эффект:** прозрачность редактирования.

### 4.3. Нет соавторства / комментариев на полях

- **Как сейчас:** один редактор пишет, другой видит результат. Никаких inline-комментов, никаких suggested edits.
- **Чем плохо:** ревью KB-статьи делается через мессенджер («посмотри во второй абзац»). Несовместимо с серьёзной документацией.
- **Как должно быть:** на длинном horizon — Yjs/Liveblocks для real-time co-edit. На коротком — inline-комментарии (выделил текст → «оставить комментарий», бейдж в правом столбце, статус «решено/открыто»).
- **Сложность:** L (комментарии) / XL (real-time)
- **Эффект:** редактор больше не работает в одиночку.

## 5. Общие проблемы рабочего процесса

### 5.1. Нет «Мои черновики» / «Моя активность»

- **Как сейчас:** редактор начал писать новость, не дописал, ушёл. Чтобы вернуться, нужно зайти в `/news`, отфильтровать по `status=draft`, найти свою.
- **Чем плохо:** черновики растворяются в общем списке. Особенно если их много (хроническая беда контент-команд).
- **Как должно быть:** в шапке (или в профиле) — раздел «Мои материалы» с табами «Черновики», «На модерации», «Опубликованные», «Запланированные». Также — виджет на главной для редакторов.
- **Сложность:** S (frontend, API уже умеет фильтровать)
- **Эффект:** workflow контентщика наконец-то виден.

### 5.2. Workflow-модерации нет

- **Как сейчас:** в `news.status` — `draft / published`. Нет статусов `review / approved / rejected`.
- **Чем плохо:** в реальной редакции «джуниор пишет → лид одобряет → публикация». Сейчас джуниор сразу публикует или просит лида в чате открыть и нажать «Опубликовать».
- **Как должно быть:** добавить статусы `pending_review`, `approved`, `rejected` (с комментарием). Роль `editor_lead` или `manager`. Уведомление лиду «Новость на ревью». Аудит решений.
- **Сложность:** M
- **Эффект:** настоящий редакционный процесс.

### 5.3. Нет планировщика контента (календарный вид)

- **Как сейчас:** есть `publish_at` для отложенной публикации. Но план «что выходит на следующей неделе» — нет.
- **Чем плохо:** редактор не видит, что на четверг уже две новости запланированы и нельзя ставить третью. Контент-план ведут в Notion/Trello отдельно.
- **Как должно быть:** в `/admin` (или для роли editor) — таб «Календарь публикаций»: месяц / неделя, на ячейках — карточки запланированных новостей. Drag-n-drop для перепланирования. Пустые слоты — кнопка «Создать здесь».
- **Сложность:** L
- **Эффект:** контент-план живёт в портале, а не в Notion.

### 5.4. Нет push-уведомлений автору при действиях с его контентом

- **Как сейчас:** опубликовал новость, кто-то прокомментировал/отреагировал — узнаёшь только зайдя на страницу.
- **Чем плохо:** редактор не получает обратной связи в реальном времени. Engagement затухает.
- **Как должно быть:** уведомления (in-app + email) автору: «Ваша новость "X" получила 50 реакций», «Новый комментарий», «Статья KB упомянута в новости Y».
- **Сложность:** M (бэкенд: типы событий + правила) + S (UI уже есть)
- **Эффект:** редактор чувствует отдачу.

### 5.5. Нет быстрого «дублировать как новый»

- **Как сейчас:** для регулярных серий («Дайджест недели #34», «Релиз v1.X») каждый раз создаёшь с нуля или копипастишь из старой.
- **Чем плохо:** монотонно, ошибки при копировании структуры.
- **Как должно быть:** в меню новости — «Дублировать», создаёт черновик с теми же body/categories/cover, инкрементирует число в заголовке если есть.
- **Сложность:** S
- **Эффект:** −50% времени на серии.

### 5.6. SEO/Open Graph метаданные — нет?

- **Как сейчас:** новость публикуется → ссылка в Telegram/мессенджере раскрывается **как-то**. На основе чего: title? первого `<p>`? случайной картинки?
- **Чем плохо:** некрасивые превью в мессенджерах = меньше кликов. Даже на интранете в Telegram/корп-чате это важно.
- **Как должно быть:** в форме новости — секция «Превью для мессенджеров»: og:title, og:description (auto-fill из title и первых 200 символов), og:image (по умолчанию cover). Серверный рендер `<meta>` тегов на `/news/:id`.
- **Сложность:** M
- **Эффект:** профессиональный вид расшариваний.

# Аудит портала глазами системного администратора (DevOps / SRE)

Документ описывает наблюдения после прохождения сценариев инсталляции, эксплуатации и аварийного восстановления:

- первая установка через `setup.sh` на чистом сервере

Формат — тот же: «как сейчас → чем плохо → как должно быть → сложность → эффект».

Ключевые файлы, которые анализировались:

## 1. Первичная установка

### 1.1. `setup.sh` — bash-скрипт на Windows-friendly сервер

- **Как сейчас:** установка идёт через `setup.sh` (bash, `set -euo pipefail`). На корпоративных Windows-серверах нужен WSL/git-bash. На Linux-серверах — отлично, на Windows Server — танцы с бубном. AGENTS.md говорит, что среда выполнения — Windows CMD.
- **Чем плохо:** админ заказчика, который ставит портал на Windows Server 2019/2022 (типичная корпсреда), не может запустить bash-скрипт. Приходится вручную копировать команды или ставить WSL.
- **Как должно быть:** добавить параллельный `setup.ps1` (PowerShell 5.1+) с тем же UI. Либо переписать на Python (есть везде, где есть Docker Desktop). Документировать оба пути в README.
- **Сложность:** M
- **Эффект:** установка на Windows-сервер из коробки.

### 1.2. Нет preflight-проверок окружения

- **Как сейчас:** `setup.sh` сразу начинает спрашивать пароли. Если у админа нет docker / docker compose / openssl / достаточно памяти / свободных портов — узнает только при первом `docker compose up`.
- **Чем плохо:** при ошибке `port 443 already in use` админ откатывает всё и идёт разбираться. Нет early-fail.
- **Как должно быть:** в начале `setup.sh` функция `preflight()`:
  - `docker --version` ≥ 24.0
  - `docker compose version` (v2)
  - наличие `openssl`, `python3`, `curl`
  - свободные порты HTTP_PORT / HTTPS_PORT (через `ss -tln` или `netstat`)
  - доступная RAM ≥ 4 GB (рекомендуется 8 GB)
  - свободное место на диске ≥ 20 GB
  - права на работу с docker без sudo (или предупреждение)
  - выводить чек-лист с ✓/✗ перед началом
- **Сложность:** S
- **Эффект:** проблемы видны сразу, не после 20 минут конфигурирования.

### 1.3. SECRET_KEY и пароли невозможно прочитать после установки

- **Как сейчас:** при `gen_or_ask` пароль генерируется и пишется в `.env`. Админ его никогда не видит — он залогирован в файл (`chmod 600`), но не показан на экране, не отправлен в безопасный канал.
- **Чем плохо:** для disaster-recovery нужен POSTGRES_PASSWORD (восстановить БД из дампа на новой машине). Если `.env` потерян — пароль не восстановить. Бэкап `.env` лежит рядом → утечёт вместе с диском.
- **Как должно быть:** в конце установки **обязательный** экран «Сохраните в менеджер паролей»: список секретов один раз. Опционально — экспорт в зашифрованный архив (`age` / `gpg`) с master-passphrase, выводить QR-код для bitwarden/keepass.
- **Сложность:** S
- **Эффект:** реальный disaster-recovery возможен.

### 1.4. Нет интеграции с внешним secret-store

- **Как сейчас:** все секреты в `.env` файле + `system_data/secrets/*.json`. Файлы в git ignore, но на диске лежат plain-text.
- **Чем плохо:** в средах с compliance (PCI/банки/гос) нельзя хранить секреты в plain-text. Нужен HashiCorp Vault / AWS SM / Azure KV / docker secrets.
- **Как должно быть:** опциональная интеграция через `docker compose secrets` (стандарт) или env-переменные с префиксом `*_FILE` (читать значение из файла). Документировать паттерн внедрения Vault.
- **Сложность:** M
- **Эффект:** проходимость в strict-compliance средах.

### 1.5. TLS-сертификат не запрашивается на установке

- **Как сейчас:** `system_data/certs/portal.crt` и `portal.key` нужно положить вручную, иначе nginx не стартует. В `docs/deploy.md` упоминается self-signed для dev.
- **Чем плохо:** новый админ запускает `setup.sh` → жмёт «Production» → контейнер nginx не стартует → ошибка непонятная. Опытный знает, неопытный паникует.
- **Как должно быть:** в `setup.sh` секция «TLS-сертификат» с тремя опциями:
  1. **Let's Encrypt** (если есть публичный DNS) — встроенный certbot-контейнер
  2. **Использовать существующие** — путь к `crt` и `key`
  3. **Self-signed** для тестов — генерируется автоматически с CN=hostname
  Опция (3) — default для staging, опция (1)/(2) — для production.
- **Сложность:** M
- **Эффект:** zero-touch deploy для большинства случаев.

### 1.6. Setup.sh не проверяет конфликт пользователей

- **Как сейчас:** `gen_or_ask` создаёт пароль, но скрипт не проверяет, нет ли уже запущенных контейнеров portal-* от прошлой установки на этой же машине.
- **Чем плохо:** на одной машине нельзя поставить два независимых инстанса portal (например, prod + sandbox) — `container_name` коллидируют.
- **Как должно быть:** добавить переменную `COMPOSE_PROJECT_NAME=portal-${INSTANCE}` и убрать жёсткие `container_name:` из docker-compose.yml. Тогда можно `setup.sh --instance staging` и не конфликтовать.
- **Сложность:** S
- **Эффект:** возможность multiple deployments.

## 2. Бэкапы и DR

### 2.1. Бэкап только PostgreSQL — недостаточно

- **Как сейчас:** профиль `backup` запускает `pg-backup` контейнер, который раз в сутки делает `pg_dump` и хранит N дней (`BACKUP_RETAIN_DAYS=14`).
- **Чем плохо:** **`upload_data/`** (фото, аватары, KB-вложения, news media) **не бэкапится**. После DR данные БД будут, а файлы — нет. Это полу-бэкап. Также не бэкапится `system_data/` (settings, certs, secrets, branding).
- **Как должно быть:** `pg-backup` контейнер расширить до полноценного backup-runner: PostgreSQL дамп + `tar.gz` всех `upload_data/` и `system_data/settings|secrets|branding` с одной retention-политикой. Опционально — синхронизация в S3/MinIO/rsync.
- **Сложность:** S
- **Эффект:** реальный полный бэкап, а не частичный.

### 2.2. Бэкапы лежат на той же машине

- **Как сейчас:** `./base_data/pg-backups` — локальный volume.
- **Чем плохо:** при поломке диска/удалении сервера/ransomware → бэкапы умирают вместе с продакшеном. 3-2-1 правило не выполняется.
- **Как должно быть:** в `pg-backup` добавить опциональные параметры `BACKUP_S3_BUCKET`, `BACKUP_RSYNC_TARGET`, `BACKUP_GPG_RECIPIENT`. После создания дампа — шифровать (`gpg`) + отправлять во внешнее хранилище. Документировать минимум один off-site target.
- **Сложность:** M
- **Эффект:** соответствие 3-2-1, ransomware-resilience.

### 2.3. Restore не задокументирован end-to-end

- **Как сейчас:** в `docs/deploy.md` описан backup — упоминается `pg_dump`. Restore-сценарий («пришёл новый сервер, есть бэкап от вчера, надо поднять портал») — отдельной runbook-инструкции нет.
- **Чем плохо:** во время инцидента админ читает вики по диагонали, путает порядок шагов (восстановить БД → накатить миграции → или наоборот?). Время восстановления растёт.
- **Как должно быть:** `docs/restore.md` с пошаговым runbook + bash-скрипт `scripts/restore.sh`, который:
  1. Принимает путь к дампу
  2. Останавливает backend/worker (или новая чистая инсталляция)
  3. Заливает дамп через `pg_restore`
  4. Восстанавливает upload_data из tar-архива
  5. Запускает миграции (на случай новой версии кода)
  6. Стартует сервисы
  Регулярные drill-runs на staging (раз в квартал).
- **Сложность:** M
- **Эффект:** RTO с «несколько часов» падает до 30–60 минут.

### 2.4. Нет point-in-time recovery (PITR)

- **Как сейчас:** только daily `pg_dump`. Если падение в 18:00, последний бэкап был в 02:00 → потеряно 16 часов работы.
- **Чем плохо:** RPO = 24 часа в худшем случае. Для корпоративного портала допустимо, для серьёзных — нет.
- **Как должно быть:** включить WAL-archiving в PostgreSQL, `pg-backup` сервис расширить базовыми бэкапами через `pg_basebackup` + поток WAL в S3. PITR через `pgBackRest` (production-grade tool).
- **Сложность:** L
- **Эффект:** RPO падает до минут, при сбое восстановление до момента T-1.

### 2.5. Бэкап хранит пароль БД в env

- **Как сейчас:** `pg-backup` контейнер получает `PGPASSWORD: ${POSTGRES_PASSWORD}` через environment.
- **Чем плохо:** `docker inspect portal-pg-backup` показывает пароль в env. Любой root на хосте видит пароль БД через docker.
- **Как должно быть:** `.pgpass` файл с правами 600, монтируется как secret. `docker compose secrets` или secret через `tmpfs`.
- **Сложность:** S
- **Эффект:** меньше surface для эскалации.

## 3. Мониторинг и наблюдаемость

### 3.1. Prometheus есть, Grafana — нет

- **Как сейчас:** `prometheus-fastapi-instrumentator` подключен (`PROMETHEUS_METRICS_ENABLED=true`), `/metrics` endpoint работает. Внешнего Prometheus сервера нет, дашбордов нет.
- **Чем плохо:** метрики собираются в backend, но никем не скрейпятся. Дашборд `RPS / latency / error rate` не существует. SLO не отслеживаются.
- **Как должно быть:** опциональный профиль `monitoring`: контейнеры `prometheus`, `grafana`, готовые дашборды (FastAPI, PostgreSQL exporter, Redis exporter, Nginx exporter, node-exporter). Дашборды коммитятся в репозиторий как JSON/YAML, провижинятся через grafana provisioning.
- **Сложность:** M
- **Эффект:** observability из коробки, не требует отдельной команды.

### 3.2. Логи только в stdout / json-file driver

- **Как сейчас:** `x-logging` в docker-compose: `json-file`, max 50MB × 5 файлов на сервис, всего ~250MB на сервис.
- **Чем плохо:** на проде с 50 RPS это 1–2 дня логов. Поиск через `grep` по 5 файлам, нет аггрегации, нет alerting'а.
- **Как должно быть:** опциональный профиль `logging`: Loki + Promtail (легковесная замена ELK). Подключение к Grafana из 3.1. Запросы LogQL по trace_id/user_id/severity.
- **Сложность:** M
- **Эффект:** централизованные логи, поиск, корреляция с метриками.

### 3.3. Sentry — опционален, но без скаффолдинга

- **Как сейчас:** `SENTRY_DSN` в env. Если пусто — выключено. Self-hosted Sentry не идёт в комплекте.
- **Чем плохо:** клиенты, которые не хотят отправлять данные в облачный Sentry, оказываются без error tracking.
- **Как должно быть:** документировать рецепт self-hosted GlitchTip (легче Sentry, совместим API) или opt-in профиль с docker compose файлом.
- **Сложность:** S (документация) / M (готовый профиль)
- **Эффект:** error tracking в air-gapped средах.

### 3.4. Healthchecks есть, но нет watchdog

- **Как сейчас:** healthcheck в каждом контейнере. `restart: unless-stopped`. Healthcheck `unhealthy` сам по себе не перезапускает контейнер.
- **Чем плохо:** контейнер с unhealthy состоянием продолжает работать. Внешнего автохилера нет.
- **Как должно быть:** добавить `autoheal` контейнер (`willfarrell/autoheal`) — перезапускает контейнеры с label `autoheal=true` при unhealthy. Альтернатива — Kubernetes (но это XL миграция).
- **Сложность:** S
- **Эффект:** auto-recovery при подвисании worker'а или подвисшем connection pool.

### 3.5. Нет alerting'а

- **Как сейчас:** даже если Prometheus подключить, alert-правил нет. Никто не узнает о problem'е до жалоб пользователей.
- **Чем плохо:** «нашёл, что портал лежит уже 3 часа» — типовой нарратив инцидента.
- **Как должно быть:** в комплекте — `alerting/rules.yml` с базовыми SLO-алертами:
  - error_rate > 1% за 5 минут → warning
  - p95 latency > 1s за 5 минут → warning
  - postgres connections > 80% → critical
  - disk usage > 85% → warning
  - any container restart loop → critical
  Алерты идут в Alertmanager → email/Telegram/Mattermost.
- **Сложность:** M
- **Эффект:** проактивная реакция на инциденты.

### 3.6. Нет request tracing

- **Как сейчас:** structlog пишет JSON, но без correlation-id (trace_id, span_id).
- **Чем плохо:** при инциденте «у пользователя X странная ошибка» нельзя отфильтровать все логи одного запроса (front → backend → worker → DB).
- **Как должно быть:** middleware для генерации `X-Request-Id` (если клиент не прислал), пропихивание через все логи и в ответ. Опционально — OpenTelemetry с экспортом в Tempo/Jaeger (часть профиля monitoring).
- **Сложность:** S (request-id) / M (OTEL)
- **Эффект:** диагностика инцидентов в десятки раз быстрее.

## 4. Безопасность инфраструктуры

### 4.1. Все контейнеры запускаются от root внутри

- **Как сейчас:** в `docker-compose.yml` — `security_opt: no-new-privileges`, но `user:` не установлен. Скорее всего, образы приложения запускаются под root внутри контейнера.
- **Чем плохо:** при RCE/escape → root на контейнере → лишняя поверхность атаки. Best practice — non-root user.
- **Как должно быть:** в Dockerfile `USER 1000:1000` после копирования файлов. В docker-compose `user: "1000:1000"` для backend/worker. Volume mount permissions выставлять через init-job или `setup.sh`.
- **Сложность:** M (надо проверять каждый mount + миграции)
- **Эффект:** усиление defence-in-depth.

### 4.2. Нет regular vulnerability scanning образов

- **Как сейчас:** в `build.yml` GitHub Actions — собирает образы. Trivy/Grype нет в pipeline.
- **Чем плохо:** уязвимости в base-образах (python:3.12-slim, postgres:16, nginx:1.27-alpine) копятся, никто не уведомляется. CVE на 9.0+ может пройти незамеченным.
- **Как должно быть:** в CI добавить `trivy image` шаг с `--severity HIGH,CRITICAL --exit-code 1`. Раз в неделю — scheduled rebuild с алертом на новые CVE.
- **Сложность:** S
- **Эффект:** security hygiene.

### 4.3. Нет SBOM

- **Как сейчас:** список зависимостей зашит в образах, но не публикуется отдельно.
- **Чем плохо:** при появлении 0-day (типа log4shell) надо вручную проверять «было/не было» у каждой версии.
- **Как должно быть:** в CI — `syft` для генерации SBOM (CycloneDX/SPDX), сохранение как артефакт релиза. При CVE — автоматическая проверка через `grype` против всех опубликованных SBOM.
- **Сложность:** S
- **Эффект:** прозрачность зависимостей, быстрая реакция на CVE.

### 4.4. Внутренняя docker-сеть `internal`, но нет mTLS

- **Как сейчас:** есть две сети: `internal` (без выхода в интернет) и `external`. Backend слушает HTTP plain внутри сети.
- **Чем плохо:** в multi-tenant хосте/k8s любой соседний под может слушать трафик. Для однохостового deploy — приемлемо.
- **Как должно быть:** для однохостового — оставить как есть. Для k8s/swarm — обязательный mTLS через service mesh (Linkerd / Istio) или хотя бы certs внутри. Либо явно задокументировать «требуется trusted host».
- **Сложность:** L (mesh) / S (документ)
- **Эффект:** соответствие zero-trust.

### 4.5. Postgres slot для replication не настроен

- **Как сейчас:** один инстанс postgres, без replica.
- **Чем плохо:** падение postgres = downtime. Чтобы перейти на read-replica для аналитики или standby для failover — надо переустанавливать кастомный Dockerfile.
- **Как должно быть:** базовый `wal_level = replica`, `max_replication_slots = 5`, `archive_mode = on` в `postgres/postgresql.conf`. Готовый рецепт добавления standby в `docs/ha.md`.
- **Сложность:** M
- **Эффект:** возможность HA без переустановки.

### 4.6. Нет ограничений на nginx — DoS via slowloris

- **Как сейчас:** `client_body_timeout`, `client_header_timeout`, лимиты на body size — надо проверить в `nginx.conf`. Rate limit на API есть на уровне FastAPI.
- **Чем плохо:** если nginx без timeout'ов → slowloris. На интранете маловероятно, но из VPN — возможно.
- **Как должно быть:** в `nginx.conf` явно: `client_body_timeout 10s; client_header_timeout 10s; send_timeout 10s; keepalive_timeout 65; large_client_header_buffers 4 8k;`. `limit_req_zone` на уровень nginx как fallback к FastAPI rate limit.
- **Сложность:** S
- **Эффект:** baseline DoS-устойчивость.

## 5. Обновления и миграции

### 5.1. Нет blue-green / rolling update

- **Как сейчас:** `docker compose up -d --build` — останавливает контейнеры, стартует новые. Downtime = время рестарта (~30 сек на backend).
- **Чем плохо:** во время обновления — портал недоступен. Пользователи видят 502. На больших организациях это видно.
- **Как должно быть:** для backend с Nginx upstream'ами — два инстанса, обновление по одному. Альтернатива — один инстанс, но уведомление пользователей через nginx fallback page «Обновление, ~30 сек». Самое простое — выкатывать в нерабочее время.
- **Сложность:** M (blue-green) / S (fallback page)
- **Эффект:** ноль видимого downtime.

### 5.2. Миграции запускаются всегда — риск некорректной DDL

- **Как сейчас:** контейнер `migrations` стартует перед backend, выполняет `alembic upgrade head` через `migrate.sh`. Запускается **на каждый `docker compose up`**.
- **Чем плохо:** если миграция тяжёлая (CREATE INDEX на таблице 50М записей без CONCURRENTLY) — старт зависает на минуты/часы. Нет dry-run перед применением.
- **Как должно быть:**
  - `alembic upgrade head --sql > /tmp/migration.sql` для inspect перед применением
  - в `migrate.sh` — alert при detection долгих DDL (через `lock_timeout`/`statement_timeout`)
  - в админке — runbook «как делать heavy миграции вручную»
  - флаг `SKIP_MIGRATIONS=true` для безопасных рестартов
- **Сложность:** S
- **Эффект:** контроль над тяжёлыми миграциями.

### 5.3. Нет автоматического backup перед update

- **Как сейчас:** обновление = `docker compose pull && docker compose up -d --build`. Бэкап не делается автоматически.
- **Чем плохо:** обновление зашло криво → сложно откатить (миграции уже применились). Админ забыл сделать бэкап → данные могут пострадать.
- **Как должно быть:** в `setup.sh` пункт «Обновить до новой версии» который:
  1. Делает on-demand pg_dump + tar `upload_data` → `./.snapshots/before-upgrade-<timestamp>/`
  2. Pull новых образов
  3. Останавливает старые
  4. Запускает новые
  5. Если health-check 5 минут не зелёный — автоматический rollback (восстановить snapshot, откатить compose).
- **Сложность:** M
- **Эффект:** safe upgrades.

### 5.4. Нет версионирования портала

- **Как сейчас:** `IMAGE_TAG:-latest` — всё latest. Нет понятия «portal v1.5.2». В UI/API «версия» неизвестна.
- **Чем плохо:** support-инциденты «у нас не работает X» — невозможно понять, какая версия установлена.
- **Как должно быть:** `IMAGE_TAG` — semver из git tag. В footer портала / в `/admin/system` отображать версию + commit hash + дату сборки. В `/api/v1/version` endpoint для скриптов.
- **Сложность:** S
- **Эффект:** диагностируемость, контроль зависимостей.

### 5.5. Нет canary release для тяжёлых модулей

- **Как сейчас:** обновление выкатывается всем сразу.
- **Чем плохо:** баг в новом релизе → у всех 300 пользователей.
- **Как должно быть:** feature flags (например, через `LaunchDarkly OSS` / `Unleash`), включение нового функционала на роль/группу. Для портала такого размера — overkill, но в `users.preferences` можно сделать `experiments: ["new_kb_editor"]`.
- **Сложность:** L
- **Эффект:** safe rollout новых фич.

## 6. Производительность и масштабирование

### 6.1. Backend = 1 инстанс с CPU 2.0/RAM 2g

- **Как сейчас:** один контейнер `portal-backend`, `cpus: 2.0`, `memory: 2g`. Указано `deploy.resources` — но в `docker compose` без swarm это ignored hint.
- **Чем плохо:** на одной машине с 16 CPU backend может занять только 2 — ресурсы простаивают. Лимиты не применяются на не-swarm.
- **Как должно быть:** для одной машины — убрать `deploy.resources` или использовать `mem_limit` / `cpus` (compose-level, работают). Для масштабирования — несколько backend-инстансов за nginx upstream (`backend1`, `backend2`, `backend3`).
- **Сложность:** S (limits) / M (scaling)
- **Эффект:** реальное использование железа.

### 6.2. Worker не масштабируется горизонтально

- **Как сейчас:** один контейнер `portal-worker`. ARQ умеет несколько воркеров, но docker-compose настроен на один.
- **Чем плохо:** при пике (массовая загрузка фото с генерацией thumbnails) — очередь растёт, пользователи ждут.
- **Как должно быть:** `docker compose up --scale worker=3`. В compose можно добавить параметризацию `WORKER_REPLICAS`. ARQ-задачи уже идемпотентны (использовать `_job_id` для дедупликации).
- **Сложность:** S
- **Эффект:** масштабирование под пики.

### 6.3. Pgbouncer отсутствует

- **Как сейчас:** backend → postgres напрямую, async pool из SQLAlchemy.
- **Чем плохо:** при `--scale backend=3` × `pool_size=20` = 60 connections. PostgreSQL default `max_connections=100` — близко к лимиту. При нескольких workers — переполнение.
- **Как должно быть:** добавить `pgbouncer` контейнер (transaction pooling) между backend и postgres. SQLAlchemy → pgbouncer:6432 → postgres:5432. Backend pool_size снижается до 5–10.
- **Сложность:** S
- **Эффект:** возможность горизонтального масштабирования backend.

### 6.4. Redis maxmemory 256mb — мало для production

- **Как сейчас:** `--maxmemory 256mb --maxmemory-policy allkeys-lru`. Redis хранит сессии + ARQ + кэш ACL + idempotency-keys + photos cache.
- **Чем плохо:** на 300 активных пользователей с 24h-сессиями + кэшем — 256MB заполнятся. LRU начнёт выселять активные сессии → пользователей выкидывает.
- **Как должно быть:** параметризовать через env `REDIS_MAXMEMORY`, default 1gb для prod. Раздельно — кэш в db=1, сессии в db=0 с `noeviction` policy для сессий (важно сохранять).
- **Сложность:** S
- **Эффект:** стабильность сессий.

### 6.5. Нет CDN/edge cache для статики

- **Как сейчас:** frontend (Vue SPA bundle) отдаётся nginx с `expires` (надо проверить). Аватары, миниатюры фото — через backend / nginx.
- **Чем плохо:** на 300 одновременных пользователях каждое открытие главной = ~50 запросов к статике. Nginx справится, но грузит backend mounts.
- **Как должно быть:** проверить и настроить `expires 1y; immutable` для bundle (имена с хэшем), `expires 1d` для аватаров, ETag для thumbnails. Опциональный CDN-варnish/cloudflare для крупных деплоев.
- **Сложность:** S
- **Эффект:** ускорение загрузки, разгрузка backend.

## 7. Документация и runbook'и

### 7.1. Нет runbook'а «что делать когда упал X»

- **Как сейчас:** есть `docs/deploy.md` (установка), `docs/adr.md` (решения). Operations runbook — отсутствует.
- **Чем плохо:** в 3 ночи админ должен сам диагностировать «почему портал не отвечает». Каждый раз заново.
- **Как должно быть:** `docs/runbook.md` с типовыми инцидентами:
  - **Backend health=down:** проверить логи / проверить redis ping / проверить postgres / restart backend / эскалация
  - **Postgres недоступен:** disk full? max_connections? — алгоритм
  - **Worker не обрабатывает очередь:** длина очереди в Redis / ARQ heartbeat / restart worker
  - **Высокий CPU на backend:** топ slow queries / pg_stat_activity / N+1 в логах
  - **Nextcloud unreachable:** проверки → fallback degradation
- **Сложность:** M (написать) / постоянная (поддерживать)
- **Эффект:** снижение MTTR.

### 7.2. Нет архитектурной диаграммы

- **Как сейчас:** в AGENTS.md описание стека текстом. В docs/adr ADR'ы. Полной диаграммы «кто с кем общается, какие порты, какие зависимости» нет.
- **Чем плохо:** новый админ месяц въезжает, читая Compose-файлы.
- **Как должно быть:** `docs/architecture.md` с Mermaid диаграммами:
  - Контейнеры и сети
  - Поток запроса (browser → nginx → backend → postgres/redis/nextcloud)
  - Поток фоновых задач (backend → ARQ queue → worker → side-effects)
  - Поток аутентификации (Keycloak OIDC + локальный)
- **Сложность:** S
- **Эффект:** onboarding в часы вместо недель.

### 7.3. Нет capacity planning гайда

- **Как сейчас:** нигде не указано «300 пользователей = 4 GB RAM, 50К новостей = 20 GB диск».
- **Чем плохо:** админ не знает, какое железо заказывать. «Поставлю на VM 2 CPU 4 GB» → через 6 месяцев OOM.
- **Как должно быть:** `docs/capacity.md` с эмпирическими цифрами по компонентам, формула: «N пользователей × M контента → CPU/RAM/Disk».
- **Сложность:** S (если есть нагрузочные тесты — а они есть в `load/`)
- **Эффект:** правильный sizing с первого раза.

## 8. CI/CD и release-процесс

### 8.1. CI запускает тесты, но не проверяет миграции

- **Как сейчас:** `ci.yml` — lint + test + alembic migrate (по AGENTS.md).
- **Чем плохо:** «alembic migrate» проверяет только up. Down (откат) не проверяется. Reverse-compat между v1.5 и v1.6 миграциями не верифицируется.
- **Как должно быть:** добавить шаги:
  - `alembic upgrade head && alembic downgrade -1 && alembic upgrade head` — sanity check downgrade
  - regression test «новый код работает на старой схеме» (для zero-downtime deploys)
- **Сложность:** S
- **Эффект:** safe rollback миграций.

### 8.2. Нет smoke-test после деплоя

- **Как сейчас:** после деплоя — `docker compose ps` показывает «running». Healthcheck зелёный — значит окей.
- **Чем плохо:** healthcheck = `/ready` (DB+Redis+NC). Не проверяет, что login работает, что главная отдаётся, что API отвечает.
- **Как должно быть:** post-deploy smoke-test: bash-скрипт `scripts/smoke.sh` который делает 10–15 базовых запросов (login → fetch news → fetch KB → upload tiny file → cleanup). Запуск автоматически после `compose up`.
- **Сложность:** S (есть `load/smoke.js`, можно адаптировать)
- **Эффект:** уверенность, что деплой реально рабочий.

### 8.3. Нет rollback-команды

- **Как сейчас:** для отката надо вручную: `git checkout <prev-tag>`, `docker compose up -d --build`, восстановить миграции вручную.
- **Чем плохо:** в инциденте — паника, ошибки.
- **Как должно быть:** `setup.sh` пункт «Откатиться к предыдущей версии». Хранить tag предыдущего успешного деплоя в `.last_known_good`. Откат = checkout + alembic downgrade + restore upload (если бэкап есть, см. 5.3) + compose up.
- **Сложность:** M
- **Эффект:** rollback за минуты, а не часы.
