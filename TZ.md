# ТЗ. Развитие модуля «База знаний»

Документ собирает все идеи улучшений модуля «База знаний» портала, обсуждённые в рамках review. Структура: backend → frontend → дизайн-язык (Obsidian-style) → клавиатурные сценарии → эксплуатация → приоритеты. Каждый пункт описан с точки зрения цели, ожидаемого эффекта и (где это уместно) подсказок по реализации.

Базовая документация модуля: `./docs/knowledge-base.md`.

## 1. Backend

### 1.1. Производительность и масштабируемость

#### 1.1.1. Стриминг экспорта ZIP / vault
- **Что не так.** `./backend/app/api/kb/export_import.py` собирает архив целиком в память (`io.BytesIO`) — при vault на тысячи статей это OOM воркера и латентность «холодного» ответа.
- **Цель.** Отдавать архив потоком, не материализуя его целиком.
- **Реализация.**
  - Перейти на `StreamingResponse` поверх асинхронного генератора, который пишет в `zipfile.ZipFile(stream, mode='w', allowZip64=True)`, где `stream` — обёртка, отдающая чанки в `Response`.
  - Альтернатива: писать во временный файл (`tempfile.SpooledTemporaryFile(max_size=…)`) → `FileResponse` + фоновая очистка через `BackgroundTask`.
- **Эффект.** Память воркера ограничена константой; экспорт vault на 5-10 ГБ перестаёт ронять процесс; первый байт уходит клиенту быстрее (better TTFB).

#### 1.1.2. Фоновый экспорт PDF/DOCX
- **Что не так.** Playwright/Chromium холодный старт — секунды; синхронный эндпойнт держит соединение и упирается в таймауты ingress/nginx на крупных статьях.
- **Цель.** Снять долгие задачи с request-response цикла.
- **Реализация.**
  - Job-очередь: Arq (если уже есть Redis) / RQ / Celery.
  - Эндпойнт `POST /kb/articles/{id}/export/pdf` возвращает `202 Accepted` + `Location: /kb/jobs/{job_id}`.
  - `GET /kb/jobs/{job_id}` — статус (`pending|running|done|failed`) и URL результата.
  - Готовый файл сохранять во временный кэш (`{kb_export_cache}/{job_id}.pdf`, TTL 1 час), отдавать через `X-Accel-Redirect`.
- **Эффект.** UI получает явный прогресс, отсутствуют таймауты, можно масштабировать воркер экспорта отдельно от API.

#### 1.1.3. Прогрев и переиспользование Chromium
- **Цель.** Убрать стоимость холодного старта браузера на каждый PDF.
- **Реализация.**
  - Долгоживущий `playwright.async_api.Browser` инстанс per-worker, поднимаемый при старте через FastAPI `lifespan`.
  - На каждый запрос — новый `BrowserContext`, чтобы изолировать cookies/localStorage.
- **Эффект.** Время PDF падает с 3-5 сек до 0.5-1 сек на средней статье.

#### 1.1.4. Полнотекстовый поиск: ранжирование и сниппеты
- **Что не так.** Есть `body_tsvector` (russian_hunspell) и GIN, но в выдаче `/kb/articles?q=` нет ни упорядочивания по релевантности, ни сниппетов.
- **Цель.** Сделать поиск полезным «из коробки».
- **Реализация.**
  - `ORDER BY ts_rank_cd(body_tsvector, plainto_tsquery('russian_hunspell', :q)) DESC`.
  - Добавить поле `snippet` в схему ответа, вычислять через `ts_headline('russian_hunspell', body, plainto_tsquery(...), 'StartSel=<mark>,StopSel=</mark>,MaxFragments=2,MaxWords=20,MinWords=5')`.
  - На фронте — рендер `snippet` с HTML-санитайзером (только `<mark>`).
- **Эффект.** Поиск из «каталога» становится поисковиком. Пользователь видит контекст, кликов мимо радикально меньше.

#### 1.1.5. Устранение N+1 в `/kb/sections`
- **Цель.** Гарантировать один SQL-запрос на загрузку дерева.
- **Реализация.**
  - Проверить, что `created_by`, `permissions` грузятся через `selectinload`/`joinedload`, а не лениво при сериализации.
  - Добавить трассировку SQLAlchemy (`echo`) в тесте, ассертить количество запросов на типовое дерево.
- **Эффект.** Стабильное время ответа независимо от глубины дерева.

#### 1.1.6. Closure-table / `ltree` для иерархии разделов
- **Цель.** Ускорить рекурсивные операции (резолв ACL, breadcrumbs, инвалидация поддерева).
- **Реализация.**
  - Вариант A: PostgreSQL `ltree` с GiST-индексом, хранить путь `it.directum.…`.
  - Вариант B: closure-table `kb_section_closure(ancestor_id, descendant_id, depth)` поверх существующего `parent_id`. Триггеры на INSERT/UPDATE/DELETE поддерживают согласованность.
- **Эффект.** Резолв ACL и breadcrumbs — O(глубины) или O(1) запрос вместо рекурсивного CTE. Особенно заметно на больших vault и при batch-операциях.

### 1.2. ACL и кэш

#### 1.2.1. Negative caching
- **Что не так.** При массовых запросах «чужих» ресурсов каждый раз cache-miss → CTE → результат «нет доступа», не кэшируется.
- **Реализация.** Хранить sentinel-значение (например, строка `__deny__`) с тем же TTL, что и положительные результаты. Резолвер сначала проверяет sentinel, потом обычное значение.
- **Эффект.** Уменьшение DB-нагрузки при сканировании списков, защита от accidental DoS «обходом по id».

#### 1.2.2. Версионирование кэша вместо сканирования ключей
- **Что не так.** `invalidate_section_cache` обходит поддерево CTE-запросом и удаляет ключи Redis — это два дорогих действия (CTE + множественные `DEL`/`SCAN`).
- **Реализация.**
  - Хранить bump-счётчик `kb_acl_ver:section:{id}` (INCR при изменении). Ключ кэша включает версию: `kb_acl:{user}:section:{id}:v{N}` — старые записи никогда не запрашиваются и протухают по TTL.
  - Инвалидация поддерева — один `INCR` на корне и один CTE-запрос на детях (или, при closure-table, без него).
- **Эффект.** O(1) инвалидация, отсутствие гонок «удалил перед записью».

#### 1.2.3. Обратный индекс для bulk-инвалидации
- **Альтернатива п. 1.2.2.** Поддерживать `SET kb_acl_idx:section:{id}` со списком актуальных cache-ключей; инвалидация — `SUNION` + `DEL`.
- **Эффект.** Полностью убирает `SCAN`/`KEYS`, который сейчас остаётся опасным паттерном.

### 1.3. Версионирование и хранение

#### 1.3.1. Дельта-хранение версий
- **Что не так.** Каждое автосохранение пишет полный body в `kb_article_versions` — БД быстро раздувается, особенно при длинных статьях.
- **Реализация.**
  - Хранить snapshot раз в N версий (например, 10) или раз в M минут, между snapshot’ами — дельты (`diff-match-patch` / `xdelta`).
  - Restore: найти ближайший snapshot ≤ N, применить дельты вперёд.
- **Эффект.** Объём `kb_article_versions` падает в 5-10 раз. Затраты CPU на restore — миллисекунды.

#### 1.3.2. Политика истории (GC)
- **Реализация.** Конфиг: «хранить все версии за последние N дней + последние K версий + помеченные `pinned`». Фоновая задача чистит остальное.
- **Эффект.** Контролируемый рост, поддерживаемая БД.

#### 1.3.3. Раздельное хранение draft-автосейва и публикуемых снимков
- **Что не так.** Сейчас и `PUT /draft`, и `PUT /articles/{id}` плодят записи в одной таблице — «полезные» и «технические» версии смешаны.
- **Реализация.** Для черновика — отдельная одиночная запись `kb_article_pending_draft(article_id, body, version, author_id, updated_at)` с UPSERT. В историю попадают только публикации/именованные снимки.
- **Эффект.** История перестаёт быть «шумной»; UI «История версий» сразу становится понятным.

### 1.4. Файлы и медиа

#### 1.4.1. Антивирусная проверка вложений
- **Реализация.** ClamAV-демон, очередь сканирования. Загруженный файл попадает в карантин (отдельный путь), доступен скачиванию только после `clean`. На стороне UI — статус «Проверяется…».
- **Эффект.** Снижение рисков при обмене файлами между подразделениями.

#### 1.4.2. Дедупликация по SHA-256
- **Реализация.** Хранить файлы по хешу (`{kb_files_dir}/{sha256[:2]}/{sha256}`), `kb_article_files` ссылается на хеш. Удаление файла → decrement refcount, физическое удаление только при 0.
- **Эффект.** Экономия места при копировании статей, vault-импортах, дубликатах скриншотов.

#### 1.4.3. EXIF-strip и автоматический ресайз медиа
- **Реализация.** При загрузке инлайн-картинки: убрать EXIF (`Pillow`), сгенерировать 1-3 размера (`@1x`, `@2x`, может быть thumbnail), сохранить `.webp`. Отдавать через `<picture>` с `srcset`.
- **Эффект.** Меньше трафика, защита от слива геолокации, корректное отображение на retina и мобильных.

#### 1.4.4. Storage backend abstraction (S3/MinIO)
- **Реализация.** Адаптер `FileStorage` с локальной и S3-реализациями. Раздача S3 — pre-signed URL или прокси через nginx.
- **Эффект.** Возможность горизонтально масштабировать API без NFS, бэкап через стандартный S3-tooling.

### 1.5. Поиск

#### 1.5.1. Индексация вложений (PDF/DOCX/XLSX)
- **Реализация.** Apache Tika / `textract` / `pdfminer.six` извлекают текст при загрузке. Текст пишется в отдельную колонку/таблицу `kb_article_files.indexed_text` + GIN. Поиск объединяет матчи по статье и по файлам.
- **Эффект.** «Найти PDF с упоминанием X» работает.

#### 1.5.2. Fuzzy-поиск и подсказки
- **Реализация.** `pg_trgm` индекс на `title` для опечаток (`title %> :q`); либо ввести Meilisearch/Typesense как отдельный сервис — фасеты, опечатки, синонимы из коробки.
- **Эффект.** Поиск прощает опечатки; user не теряется, если не помнит точное название.

#### 1.5.3. Семантический поиск (pgvector)
- **Реализация.** Эмбеддинги статей (e.g. bge-m3, multilingual-e5) хранить в `kb_article_embeddings(vector(1024))`. `ivfflat`/`hnsw` индекс. Эндпойнт «Похожие статьи», RAG-Q&A.
- **Эффект.** Запросы естественным языком; рекомендации связанных статей.

### 1.6. Импорт / экспорт

#### 1.6.1. Двусторонняя синхронизация с Git
- **Реализация.** Конфигурируемый remote (GitLab/Gitea). Pull — `git fetch` + diff → импорт. Push — экспорт vault → коммит. Конфликты разрешаются через стандартный merge.
- **Эффект.** Backup, code-review для документации, возможность писать в VS Code/Obsidian локально.

#### 1.6.2. Прогресс импорта (SSE/WebSocket)
- **Реализация.** Импорт — job, статус публикуется в Redis pub/sub, фронт подписан через SSE. Показ прогресс-бара и текущего файла.
- **Эффект.** Импорт vault на сотни статей перестаёт быть «чёрным ящиком».

### 1.7. Прочее

#### 1.7.1. Idempotency-Key для всех POST
- **Цель.** Защита от дубликатов при двойных кликах / повторных запросах.
- **Реализация.** Middleware: при наличии заголовка `Idempotency-Key` хранит `(method, path, user_id, key) → response` в Redis с TTL 24 часа.
- **Эффект.** Дубликаты комментариев, suggestions, feedback исчезают как класс.

#### 1.7.2. Outbox-таблица и публикация событий во внешнюю шину
- **Реализация.** На каждое изменение пишем запись в `kb_events_outbox` в той же транзакции. Отдельный воркер выгребает и публикует в Kafka/NATS. Гарантия at-least-once.
- **Эффект.** Интеграции (Slack-нотификации, поисковая реиндексация, аналитика) без связности с API.

#### 1.7.3. Rate-limit на тяжёлые операции
- **Реализация.** `slowapi` / Redis token bucket per-user на: PDF/DOCX экспорт, vault-экспорт/импорт, поиск с длинным `q`, diff больших версий.
- **Эффект.** Один пользователь не кладёт сервис, аналитика «кто-злоупотребляет».

## 2. Frontend

### 2.1. Редактор

#### 2.1.1. Slash-меню (`/` → выбор блока)
- **Что даёт.** Команды редактора не через тулбар, а через клавиатуру. Все возможности «обнаруживаются» одной клавишей.
- **Реализация.** Расширение TipTap `@tiptap/suggestion`. Список команд: heading 1-3, list, todo, table, callout, details, image, iframe, code, divider.
- **Эффект.** Время создания статьи −20-30% на типовых кейсах; рост доли структурного контента.

#### 2.1.2. Шаблоны статей
- **Шаблоны.** Runbook, Postmortem, ADR, How-to, Onboarding, Release notes.
- **Реализация.** `kb_templates(id, name, body, created_by)` + модалка «Новая статья из шаблона». Шаблоны хранят body уже отсанитайзенный.
- **Эффект.** Единый стиль документации; авторам легче «начать»; новички видят ожидаемый формат.

#### 2.1.3. Автогенерация TOC с подсветкой активного раздела
- **Реализация.** Парсинг heading из rendered body → sticky-панель справа. `IntersectionObserver` подсвечивает активный пункт. Anchor-ссылки `#h-{slug}` для шеринга на конкретный шаг.
- **Эффект.** Длинные runbook’и читаются «по диагонали»; ссылки на пункты вместо «смотри раздел 4.2».

#### 2.1.4. Side-by-side diff внутри редактора
- **Реализация.** Заменить `KbVersionDiffModal` на встроенную панель: левая колонка — выбранная версия (readonly), правая — текущий редактор. Скролл синхронизирован.
- **Эффект.** Review предложений правок становится одним окном вместо «открыл-закрыл-вспомнил».

#### 2.1.5. Совместное редактирование (Y.js + presence)
- **Реализация.**
  - `@hocuspocus/server` (Node, отдельный сервис) + `@hocuspocus/provider` на фронте.
  - TipTap `Collaboration` + `CollaborationCursor` extensions.
  - Аутентификация через JWT портала.
  - Снимки в `kb_article_versions` по дебаунсу (например, раз в 5 минут или по `published`).
- **Эффект.** Исчезает 409-конфликт; парная работа реальна; рост вовлечённости в writing-culture.

#### 2.1.6. Явный статус автосохранения
- **Реализация.** В шапке редактора — индикатор: «Сохранено · 2 сек назад / Сохраняется… / Ошибка — повторить». Класс на иконке.
- **Эффект.** Снижение тревожности, меньше тикетов «у меня пропал черновик».

#### 2.1.7. Drag-and-drop файлов + paste картинок
- **Реализация.** TipTap `Drop` handler + `paste` handler с проверкой типа. Загрузка через существующий `useEditorImageUpload`. Прогресс-плейсхолдер в месте вставки.
- **Эффект.** Скриншоты вставляются за 1 секунду вместо 15. Инструкции становятся «с картинками».

#### 2.1.8. Mentions (`@user`) и wiki-links (`[[Статья]]`) с backlinks
- **Реализация.**
  - TipTap `Mention` для пользователей (data — Keycloak search).
  - Свой extension для `[[…]]` с автодополнением по статьям.
  - Бэкенд: при сохранении парсит ссылки, поддерживает таблицу `kb_article_links(source_id, target_id)`.
  - В UI статьи — блок «На эту статью ссылаются: …».
- **Эффект.** База превращается из набора файлов в граф знаний. Старые статьи живы за счёт backlinks. Mentions шлют нотификацию ответственному.

### 2.2. Навигация и список

#### 2.2.1. Виртуализация дерева разделов
- **Реализация.** `vue-virtual-scroller` или `@tanstack/vue-virtual` поверх «уплощённого» представления дерева (массив `{depth, section}`).
- **Эффект.** Поддержка тысяч узлов без лагов.

#### 2.2.2. Сохранённые фильтры / saved views
- **Реализация.** `kb_views(user_id, name, filters_json)`. В тулбаре — выпадашка «Мои черновики / Без владельца / Stale > 180 дней / Ожидают review».
- **Эффект.** Рутинные сценарии контент-гигиены становятся реальными.

#### 2.2.3. Графовый вид связей
- **Реализация.** Cytoscape.js / d3-force. Источник — `kb_article_links` + теги. Кластеры по разделам, размер узла = `view_count`.
- **Эффект.** Карта знаний домена; видны «острова» (на которые никто не ссылается).

#### 2.2.4. Канонические URL со slug
- **Реализация.** `kb_articles.slug` (генерация при создании, ручное редактирование). Роут `/kb/a/:slug-:id`. Старый `/kb/articles/:id` редиректит.
- **Эффект.** Читаемые ссылки в чатах, лучше закладки.

### 2.3. Производительность фронта

#### 2.3.1. Виртуализация длинных списков (статьи, комментарии).
#### 2.3.2. Skeleton-loaders вместо спиннеров (perceived performance −30-40%).
#### 2.3.3. Prefetch при hover на ссылку статьи (`queryClient.prefetchQuery`) — мгновенный переход.
#### 2.3.4. Code-splitting тяжёлых модулей (PDF preview, diff, импорт). `defineAsyncComponent`.

### 2.4. A11y и i18n

#### 2.4.1. Полноценный a11y-аудит
- ARIA для дерева (`role="tree"`, `aria-expanded`, `aria-level`).
- Focus-traps в модалках.
- Видимый focus-ring (соответствие WCAG 2.4.7).
- Скрин-ридер тестирование (NVDA/VoiceOver) на ключевых сценариях.

#### 2.4.2. Английская локаль для смешанных команд (i18n уже подключён).

### 2.5. Поиск UI

#### 2.5.1. Унификация с глобальным `Ctrl+K`

## 3. Дизайн-язык: сближение с Obsidian / Notion / Linear

### 3.0. Master/detail компоновка (three-pane + full reading) ⭐

> Решает озвученную боль: «нажал на статью — открылась отдельная страница, чтобы выйти, нужна стрелка Назад». Цель — единый интерфейс в стиле Obsidian / Notion / Gmail, где дерево и список всегда видимы, а статья переключается в правой панели.

#### 3.0.1. Целевая компоновка

Three-pane layout с переключателем «full reading»:

1. **Левая колонка — дерево разделов** (как сейчас, но persistent на всех `/kb/*` страницах).
2. **Средняя колонка — список статей** выбранного раздела (то, что сейчас на `/kb`).
3. **Правая колонка — тело статьи** (то, что сейчас на `/kb/articles/{id}`).
4. **Full reading toggle** (`Ctrl+\` или кнопка) — сворачивает левые колонки, статья на всю ширину для комфортного чтения.

#### 3.0.2. Почему именно так

- **Решает основную боль навигации.** Возврат к списку — не отдельное действие, список всегда виден.
- **Знакомый паттерн.** Obsidian, Notion, Gmail, Apple Mail, Outlook, Linear, Slack — все построены так. Нулевая кривая обучения.
- **Не ломает URL.** Существующие маршруты `/kb` и `/kb/articles/{id}` остаются работоспособными, bookmark’и и шеринг ссылок не страдают.
- **Технически малоинвазивно.** Это в первую очередь общий layout-компонент и адаптивная сетка; сами страницы и эндпойнты не переписываются.

#### 3.0.3. Адаптивная стратегия

Комфортная ширина чтения — 60-75 символов, ≈ 600-720px.

| Ширина окна | Сайдбар портала | Дерево | Список | Тело статьи |
|---|---|---|---|---|
| ≥ 1920px | 240px | 240px | 320px | ≈ 1120px |
| 1440px | 240px | 220px | 280px | ≈ 700px |
| 1366px | 240px | 200px | 260px | ≈ 666px (комфортно) |
| 1280px | 64px (свёрнут) | 200px | 260px | ≈ 756px |
| 1100-1280px | 64px | 200px | overlay при выборе статьи | ≈ 836px |
| < 1100px | drawer | drawer | drawer | full-width |

- **≥ 1280px** — все три колонки одновременно.
- **1100-1280px** — дерево + статья всегда, список вызывается по кнопке «← К списку» / автоматически скрывается при выборе статьи (паттерн Mail.app).
- **< 1100px** — мобильный режим: дерево и список как drawer’ы поверх контента, поведение близко к текущему.

#### 3.0.4. Реализация

- **Layout-компонент `KbLayout.vue`.**
  - Три слота: `tree`, `list`, `detail`.
  - Внутри — resizable splitters между панелями.
  - Логика свёртывания на основе `useBreakpoints`.
- **Nested-роуты вместо отдельных страниц.**
  - Родительский роут `/kb` рендерит `KbLayout` + `KbSectionTree` + `KbArticleList`.
  - Дочерний роут `/kb/articles/:id` рендерит детальную колонку поверх (через `<router-view>` в слоте `detail`).
  - На `/kb` без вложенного роута — детальная колонка показывает **empty state**: иллюстрация + «Выберите статью из списка или создайте новую».
- **Состояние URL.**
  - Раздел в query: `?section={id}` (синхронизировано с `selectedSection` из `useKbSections`).
  - Статья в path: `/kb/articles/{id}` (без изменений).
  - Открытие статьи в новой вкладке (Ctrl+Click) работает «из коробки» — открывается тот же layout с выбранной статьей.
- **Состояние в `localStorage`** (расширить существующий механизм):
  - `kb.layout.tree-width`, `kb.layout.list-width` — ширины панелей.
  - `kb.layout.full-reading` — режим чтения.
  - Существующие ключи `kb.section-tree.expanded`, `kb.section-tree.selected` остаются.
- **Хоткеи** (см. раздел 4):
  - `Esc` в детали → закрыть статью, фокус на её строку в списке.
  - `↑ / ↓` в списке → следующая / предыдущая статья (как в почте).
  - `Ctrl+\` → свернуть/развернуть боковые панели.
  - `j / k` (vim-style, опционально) — то же, что `↑ / ↓`.

#### 3.0.5. Что нужно доработать в существующих компонентах

- **Шапка статьи (`KbArticleHeader`).** Сейчас тулбар проектировался на полную ширину страницы. В three-pane колонка статьи ≈ 700-1100px — часть кнопок надо утопить в kebab/контекст-меню, чтобы не было переноса. Приоритет видимых действий: «Редактировать», «Поделиться», остальное — в меню.
- **Хлебные крошки статьи.** Сейчас они в шапке статьи и дублируют то, что видно в дереве. В three-pane это излишне — можно убрать или оставить компактными (`Раздел / Подраздел`).
- **Кнопки массовых действий статьи** (экспорт PDF/DOCX/MD, история, права) → в верхний kebab «⋯» правой колонки.
- **Список статей.** Должен поддерживать клавиатурную навигацию (`tabindex`, `aria-selected`), подсвечивать **текущую открытую статью** (а не только при наведении).
- **Модалки** (управление правами, история, импорт) — рендерить через `Teleport` в корень, чтобы они не зависели от родительской колонки и работали корректно поверх overlay-списка.

#### 3.0.6. Подводные камни

- **Печать.** Print CSS должен скрывать левые колонки и full-width рендерить только статью.
- **Глубокие модалки на средних экранах.** При overlay-списке (1100-1280px) одновременно может быть открыт overlay-список + модалка прав. Z-index должен быть упорядочен: список < модалки.
- **Длинные тулбары статьи.** Перед миграцией — провести ревизию кнопок (см. п. 3.0.5).
- **Перенос фокуса при переключении статьи.** При навигации `↑/↓` фокус должен оставаться на списке (для продолжения нажатий), но `aria-live` должен анонсировать смену контента.
- **Прокрутка тела статьи.** При смене статьи скролл правой колонки нужно сбрасывать в верх.

#### 3.0.7. Опциональное расширение: tabbed editing (как в Obsidian)

Несколько статей открыты во вкладках внутри правой колонки. **Не рекомендуется делать сразу** — высокая сложность (состояние вкладок, drag, перезагрузка), а в сценарии KB обычно работают с одной статьёй. Можно вернуться, когда three-pane стабилизируется и появится явный запрос.

#### 3.0.8. Минимальный поэтапный план (если делать инкрементально)

Если полный three-pane сейчас слишком крупная задача, можно идти ступенями:

1. **Этап 1 — persistent sidebar (Вариант 1).**
   - Дерево разделов остаётся на странице статьи как левая колонка (через общий layout).
   - Empty state на `/kb` («Выберите статью»).
   - `Esc` на статье → возврат к списку с тем же разделом.
   - Подсветка текущей статьи в дереве (если её раздел открыт).
   - **Эффект:** снимает 70% дискомфорта при ~30% усилий.
2. **Этап 2 — three-pane.**
   - Добавляется persistent список статей между деревом и статьёй.
   - Резизаблы, адаптив, клавиатурная навигация.
3. **Этап 3 — full reading toggle, `Ctrl+\`, прочие хоткеи (`↑/↓`, `Esc`).**

#### 3.0.9. Эффект

- Переключение между статьями — мгновенное (нет route-transition + cold render).
- Контекст («где я в дереве», «какие ещё статьи в этом разделе») сохраняется всегда.
- Чтение статьи остаётся комфортным благодаря full-reading toggle.
- Соответствие ожиданиям пользователей, привыкших к Obsidian/Notion/почтовым клиентам.

- Генерация типов `npm run gen:types` — обязательный шаг pre-commit.

### 5.4. Property-based тесты
- `hypothesis` для `sanitize_markdown` и `clean_title` — реальная атакующая поверхность.

### 5.5. E2E на совместное редактирование и 409
- Сейчас не покрыто. Playwright-сценарий: два контекста, одновременная правка, проверка конфликта/мерджа.

## 6. Приоритизация

### 6.0. Флагманская UX-инициатива

- **Master/detail three-pane + full reading** (3.0). Решает основную боль навигации, приводит UX к стандарту Obsidian/Notion/Gmail. Рекомендуется как первая крупная UI-задача; пункты 6.1 ниже либо встроятся в неё, либо станут более ценными после её внедрения.

### 6.1. Топ-5 «быстрых побед» (UI)

1. **Хлебные крошки + description раздела над списком** (3.3.1, 3.3.2). Контекст не теряется.
2. **Свернуть панель разделов + resizable splitter** (3.1.2, 3.1.3). Мгновенно удобнее на разных экранах.
3. **Снизить вес активного состояния + иконки папок** (3.2.1, 3.2.2). Общий вид «как у взрослых».
4. **Фильтр-поиск по дереву разделов** (3.2.8). Критично при росте базы.
5. **Quick switcher `Ctrl+O`** (раздел 4). Самый сильный одиночный хоткей.

### 6.2. Топ-5 «быстрых побед» (общие)

1. **`Ctrl+K` Spotlight + подсветка совпадений** (1.1.4 + 2.5.1, 2.5.2).
2. **Slash-меню и шаблоны статей** (2.1.1, 2.1.2).
3. **Явный статус автосохранения + DnD/paste файлов** (2.1.6, 2.1.7).
4. **Effective permissions viewer** (2.6.2).
5. **Дашборд статьи + stale-detector** (2.7).

### 6.3. Топ-3 «инфраструктурных» (требуют большего вложения, но снимают целые классы проблем)

1. **Совместное редактирование (Y.js / Hocuspocus)** (2.1.5).
2. **Фоновый экспорт + прогрев Chromium** (1.1.2, 1.1.3).
3. **Closure-table / `ltree` + версионирование кэша ACL** (1.1.6, 1.2.2).

### 6.4. Стратегические инициативы (требуют отдельного дизайна)

- **Двусторонний sync с Git** (1.6.1).
- **Семантический поиск pgvector + Q&A** (1.5.3).
- **Граф знаний с backlinks и UI-визуализацией** (2.1.8, 2.2.3).

## 7. План внедрения (рекомендуемый порядок)

Раздел задаёт практический порядок работ: что делать в какой последовательности, чтобы не переделывать сделанное и получать максимум видимого эффекта в каждой итерации. Опирается на разделы 1-6.

**Базовый принцип.** Сначала — компоновка (3.0), потому что она множит ценность остальных UI-улучшений и снимает основную пользовательскую боль. Параллельно — backend-улучшения, которые не зависят от UI и могут идти отдельным треком.

### 7.1. UX-трек

#### Итерация A. Persistent sidebar (Этап 1 из 3.0.8) + сопутствующие визуальные правки

**Цель.** Снять основную боль навигации («чтобы выйти из статьи — стрелка Назад») и подготовить почву для three-pane. Минимум риска, максимум видимости.

**Состав.**
- **3.0 / Этап 1.** Persistent дерево разделов как layout для всех `/kb/*`. Empty state на `/kb`. `Esc` на статье → возврат к списку с сохранённым разделом. Подсветка текущей открытой статьи в дереве/списке.
- **3.1.4.** Убрать H1 «База знаний» с подзаголовком — освобождает вертикаль.
- **3.3.1.** Breadcrumbs над списком — компенсирует уход H1, даёт контекст.
- **3.3.2.** Description раздела под breadcrumbs — оживляет «мёртвое» поле.
- **3.2.2.** Снизить визуальный вес активного состояния в дереве (полупрозрачная подложка + полоса слева вместо красной заливки).
- **3.2.1.** Иконки папки/документа в дереве.
- **3.3.6.** Skeleton-loader при загрузке списка и дерева.

**Эффект итерации.** Persistent навигация, чистая шапка, современная подача активного раздела, нет «пустых экранов» при загрузке. Это уже визуально другой продукт.

**Что НЕ начинать до этого.** Slug-URL (2.2.4), sticky TOC (3.4.2), properties panel (3.4.3), side-by-side diff (2.1.4), унификация поиска (2.5.1) — лучше делать поверх стабильного layout.

#### Итерация B. Three-pane (Этап 2 из 3.0.8)

**Цель.** Полноценный single-screen интерфейс в стиле Obsidian/Gmail.

**Состав.**
- **3.0 / Этап 2.** Persistent список статей между деревом и статьёй. Resizable splitters. Адаптив (≥1280 / 1100-1280 / <1100). Клавиатурная навигация по списку (`↑ / ↓`, `Esc`).
- **3.0.5.** Ревизия `KbArticleHeader`: длинные кнопки в kebab; breadcrumbs статьи — компактные или убрать; модалки через `Teleport`.
- **3.1.2.** Свернуть/развернуть панель разделов (`Ctrl+\`).
- **3.1.3.** Resizable splitter ширины колонок (`localStorage`).
- **3.1.1.** Убрать карточку вокруг дерева — flat-стиль.
- **2.3.3.** Prefetch при hover на ссылку статьи (полностью оправдан, когда переключения частые).
- **3.3.7.** Empty state в пустом разделе с CTA.
- **3.3.8.** Сохранение режима «таблица/сетка» в `localStorage`.

**Эффект итерации.** Переключение между статьями — мгновенное, контекст сохранён, удобно на широких и средних экранах. Главный паттерн «инструмента, в котором живут» закрыт.

#### Итерация C. Full reading + хоткеи (Этап 3 из 3.0.8)

**Цель.** Завершить UX-эквивалент Obsidian/Notion.

**Состав.**
- **3.0 / Этап 3.** `Ctrl+\` — full reading toggle. `↑ / ↓ / Esc` — окончательная клавиатурная навигация.
- **3.4.1.** Reading mode (`Ctrl+E`): центрированная колонка 70ch, увеличенный leading.
- **Раздел 4.** Реализация полноценной таблицы хоткеев. Базовая часть: `Ctrl+O` quick switcher, `Ctrl+N` новая статья, `Ctrl+S` сохранить.

**Эффект итерации.** Опытный пользователь работает с клавиатуры, чтение длинных runbook’ов перестаёт быть утомительным.

#### Итерация D. Дерево — улучшения интерактивности

**Цель.** Дерево перестаёт быть «списком», становится полноценным навигатором.

**Состав.**
- **3.2.8.** Фильтр-поиск по дереву (filter as you type).
- **3.2.3.** Hover-кнопки `+` и `⋮`.
- **3.2.4.** Контекстное меню по правой кнопке мыши.
- **3.2.5.** Drag-and-drop переноса разделов.
- **3.2.6.** `F2` и пункт «Переименовать» в контекстном меню.
- **3.2.7.** Бейдж счётчика статей (требует поля в API — `article_count`).
- **2.2.1.** Виртуализация дерева (при `> 500` узлов).

#### Итерация E. Список статей и просмотр статьи

**Состав.**
- **3.3.3.** Сортировка кликом по колонкам.
- **3.3.4.** Inline-теги в строке статьи.
- **3.3.5.** Превью статьи (требует поля `preview` в API).
- **3.3.9.** Группировка списка (тег / автор / месяц).
- **3.4.2.** Sticky TOC справа.
- **3.4.3.** Боковая панель свойств статьи.
- **3.4.5.** Прогресс-бар чтения.
- **2.5.1, 2.5.2, 2.5.3.** Унификация с глобальным `Ctrl+K`, подсветка совпадений, фасеты.

#### Итерация F. Редактор

**Состав.**
- **2.1.6.** Явный статус автосохранения.
- **2.1.7.** Drag-and-drop / paste картинок.
- **2.1.1.** Slash-меню.
- **2.1.2.** Шаблоны статей.
- **2.1.3.** Автогенерация TOC.
- **2.1.4.** Side-by-side diff.
- **2.1.8.** Mentions + wiki-links + backlinks (требует backend-поддержки таблицы `kb_article_links`).

#### Итерация G. Большие фичи (по отдельным проектам)

- **2.1.5.** Совместное редактирование (Y.js / Hocuspocus). Отдельный проект — новый сервис, аутентификация, миграция флоу автосохранения.
- **2.7.1.** Дашборд статьи (просмотры, helpful-ratio, глубина чтения).
- **2.7.2.** Stale-detector + еженедельный дайджест.
- **2.6.1, 2.6.2, 2.6.3.** Bulk-ACL, Effective permissions viewer, шаблоны ACL.

### 7.2. Backend-трек (можно вести параллельно UX-треку)

Эти пункты не зависят от компоновки, дают эффект самостоятельно и могут идти отдельным треком, не конкурируя за код фронта.

#### Итерация α. «Дешёвые» backend-улучшения с заметным эффектом
- **1.1.4.** FTS ранжирование + `ts_headline` сниппеты. Делает поиск действительно полезным; на фронте подцепится тривиально в любой момент.
- **1.7.1.** Idempotency-Key middleware. Снимает класс багов «двойной клик → дубль».
- **1.1.5.** Устранение N+1 в `/kb/sections`. Профилактика и стабильное время ответа.
- **1.3.2.** Политика истории (GC). Контроль роста БД.

#### Итерация β. Файлы и медиа
- **1.4.3.** EXIF-strip и ресайз медиа.
- **1.4.2.** Дедупликация по SHA-256.
- **1.4.1.** Антивирусная проверка (ClamAV).

#### Итерация γ. ACL и кэш
- **1.2.1.** Negative caching.
- **1.2.2.** Версионирование кэша (или 1.2.3 как альтернатива).
- **1.1.6.** Closure-table / `ltree` для иерархии — самая крупная из «инфраструктурных» задач, требует миграции; делать, когда упрётся производительность.

#### Итерация δ. Тяжёлый экспорт

#### Итерация ζ. Стратегические backend-инициативы

### 7.3. Качество и эксплуатация (сквозной трек)

Эти задачи лучше внедрять не отдельной итерацией, а **по мере** работы над соответствующими функциями:
- **5.1.** Метрики Prometheus добавляются вместе с соответствующим кодом (FTS, экспорт, ACL).
- **5.2.** Трейсинг OpenTelemetry — после стабилизации основных эндпойнтов.
- **5.3.** Контрактные тесты OpenAPI ↔ frontend — в CI как только появится первое расхождение.
- **5.4.** Property-based тесты на sanitize_markdown / clean_title — отдельная мини-итерация (несколько часов).
- **5.5.** E2E на 409 / co-editing — обязательно вместе с 2.1.5.

### 7.5. Что делать прямо сейчас

Конкретная следующая задача (по согласованию):

1. **Итерация A (UX-трек).** Persistent sidebar + сопутствующие визуальные правки. Снимает основную боль навигации, не требует инфраструктурных изменений.
2. **Параллельно — Итерация α (backend).** Если есть свободные руки на бэкенде: FTS-сниппеты + Idempotency-Key + N+1. Эти три задачи независимы между собой и от UX-трека.
