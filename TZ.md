# ТЗ: доработка блока «База знаний» (Knowledge Base)

Документ собран по результатам код-ревью. Безопасность вне scope. Каждая задача содержит:
- **Проблема** — что сейчас не так и где.
- **Последствия** — что увидит пользователь/что произойдёт в проде.
- **Риски, если не делать** — насколько критично игнорировать.
- **Решение** — что сделать конкретно.
- **Сложность** — оценка трудозатрат (S ≈ 0.5–1 день, M ≈ 1–3 дня, L ≈ 3–5+ дней).
- **Готовность** — критерии приёмки.

Приоритеты: **P1** — обязательны к ближайшему релизу, **P2** — в течение спринта, **P3** — техдолг.

> Все задачи блока **P1** выполнены (см. историю в `./docs/knowledge-base.md` и `./kb-ref.md`).

## P2. Важные улучшения

### P2-1. Bulk-импорт тегов вместо `flush()` в цикле

- **Проблема.** `./backend/app/api/kb/export_import.py:182-192`: на каждое создание тега и каждую связку `KbArticleTag` идёт `flush()` → отдельный round-trip к БД.
- **Последствия.** Импорт архива с большим количеством статей × тегов выполняется в разы дольше необходимого; растёт нагрузка на БД и время удержания транзакции.
- **Риски, если не делать.** Тайм-ауты при импорте крупных Obsidian-вольтов, повышенная вероятность deadlock из-за длинных транзакций.
- **Решение.**
  1. Собрать уникальные slug'ов тегов, одним SELECT получить существующие.
  2. Bulk-insert недостающих (`session.execute(insert(KbTag).values(...))`).
  3. Bulk-insert связок `KbArticleTag` через `insert(...).on_conflict_do_nothing()`.
- **Сложность.** **S–M** (день).
- **Готовность.** Импорт N статей с тегами укладывается в O(1) запросов на тег-таблицу вместо O(N).

### P2-2. Slug-проверка раздела в рамках parent, а не глобально

- **Проблема.** `./backend/app/api/kb/sections.py:92-95` ищет `KbSection.slug == slug` без учёта `parent_id`, хотя БД-ограничение уникальности — пара `(parent_id, slug)` (`./backend/app/models/kb.py:29`).
- **Последствия.** При создании раздела с slug, который уже встречается в другой ветке, бэкенд начнёт добавлять суффиксы (`-2`, `-3`), хотя коллизии на самом деле нет. URL получаются некрасивыми и нестабильными.
- **Риски, если не делать.** Постоянное «загрязнение» URL и slug'ов, путаница у пользователей, проблемы с миграцией ссылок.
- **Решение.** Добавить в `where`: `KbSection.parent_id == parent_id`.
- **Сложность.** **S** (час + тест).
- **Готовность.** Раздел `docs/api` и `tutorials/api` создаются с одинаковым slug `api`.

### P2-3. Неатомарность review suggestions

- **Проблема.** `./backend/app/api/kb/suggestions.py:142-156`: commit статуса → внешний вызов `notify_suggestion_reviewed` → второй commit. Если нотификация падает, статус уже сохранён, а API вернёт 500.
- **Последствия.** Suggestion в БД помечен как accepted/rejected, но клиент видит ошибку и может повторно нажать кнопку → двойные нотификации, рассинхрон UI.
- **Риски, если не делать.** Поток жалоб «нажал accept, вылетела ошибка, а на самом деле всё применилось». Сложно дебажить, рушит доверие к функции suggestions.
- **Решение.**
  1. Постановку нотификации в очередь (outbox) делать внутри той же транзакции.
  2. Либо использовать существующий `email_outbox`-паттерн — записать событие в таблицу, отправлять воркером.
- **Сложность.** **M** (день).
- **Готовность.** Падение нотификации не приводит к 500 на API; событие гарантированно доставляется ровно один раз.

### P2-4. Валидация пустого тела статьи перед submit

- **Проблема.** `./frontend/src/pages/KbArticleFormPage.vue:278-283` проверяет только `title`. Поле body помечено как required, но отправка пустого тела возможна.
- **Последствия.** Создаются пустые статьи или приходит ошибка бэка с непонятным текстом.
- **Риски, если не делать.** Замусоренная БЗ, плохой UX.
- **Решение.** Добавить проверку `form.value.body.trim()`, локализованное сообщение, фокус на редактор.
- **Сложность.** **S** (час).
- **Готовность.** Submit с пустым body показывает warning и не отправляет запрос.

### P2-5. Бесшумное подавление ошибок загрузки вложений

- **Проблема.** `./frontend/src/components/KbAttachmentsPanel.vue:102-111`: `catch { files.value = [] }`.
- **Последствия.** При сбое сети/прав пользователь видит «нет вложений», хотя файлы есть. Может решить, что они удалены, и начать загружать заново.
- **Риски, если не делать.** Дубли файлов, ложные баг-репорты, потеря доверия.
- **Решение.** Показать toast `parseApiError(err, t)`, оставить предыдущий список (не затирать на ошибку).
- **Сложность.** **S** (час).
- **Готовность.** При 500/403 виден toast, список не сбрасывается.

### P2-6. Вынос дубликата `findSection`

- **Проблема.** Функция обхода дерева секций объявлена дважды: в `./frontend/src/pages/KbListPage.vue` (`findSection`) и в `./frontend/src/composables/useKbSections.ts` (`findSectionRecursive`).
- **Последствия.** При изменении логики одна копия отстаёт.
- **Риски, если не делать.** Скрытые расхождения поведения, рост cognitive load.
- **Решение.** Экспортировать `findSectionRecursive` из композабла, удалить локальную копию.
- **Сложность.** **S** (полчаса).
- **Готовность.** Локальная копия удалена, тесты зелёные.

## P3. Техдолг и улучшения качества

### P3-1. Композитный индекс под `list_articles`

- **Проблема.** `./backend/app/api/kb/articles.py:65-79` фильтрует по `deleted_at`, `status`, `created_by` и сортирует по `updated_at DESC`. В `./backend/app/models/kb.py:73-80` подходящего композитного индекса нет.
- **Последствия.** На больших объёмах (десятки тысяч статей) запросы list делают seq scan + сортировку в памяти. Растёт latency, P95 деградирует.
- **Риски, если не делать.** Не критично при текущих объёмах, но при росте БЗ страница списка начнёт тормозить.
- **Решение.** Миграция Alembic, добавить индекс вида `(deleted_at, status, updated_at DESC)` и при необходимости отдельный по `created_by`. Прогнать `EXPLAIN ANALYZE`.
- **Сложность.** **S** (день с подбором индекса).
- **Готовность.** `EXPLAIN` запроса list_articles показывает index scan; миграция в репозитории.

### P3-2. Общий assembler для DTO «entity + permission + users»

- **Проблема.** Паттерн «загрузить сущность → проверить права → собрать map пользователей → построить public schema» повторяется в `./backend/app/api/kb/articles.py:263-270, 400-404, 479-481`, `./backend/app/api/kb/versions.py:110-113, 185-187`, `./backend/app/api/kb/comments.py:56-61`, `./backend/app/api/kb/suggestions.py`.
- **Последствия.** Любое изменение формата ответа (например, добавление поля в `UserRef`) — это правка в 5+ местах.
- **Риски, если не делать.** Накапливающийся дублирующий код, расхождения форматов между ручками.
- **Решение.** Вынести общий хелпер `build_users_map(db, user_ids) -> dict[int, UserRef]` и DTO-сборщики по типам.
- **Сложность.** **M** (1–2 дня).
- **Готовность.** Дубли удалены; тесты на DTO зелёные.

### P3-3. Единый helper для recursive CTE по дереву секций

- **Проблема.** Recursive CTE (descendants/ancestors) повторяется минимум в 7 местах: `./backend/app/api/kb/articles.py:82-92`, `./backend/app/api/kb/sections.py:171-180, 196-205`, `./backend/app/api/kb/_common.py:33-43`, `./backend/app/api/kb/_frontmatter.py:63-74`, `./backend/app/services/kb_acl/invalidation.py:36-45`, `./backend/app/services/kb_acl/batch.py:122-136`.
- **Последствия.** При изменении схемы дерева правки разъезжаются по модулям; разные места могут трактовать дерево по-разному.
- **Риски, если не делать.** Источник тонких багов при будущих доработках (например, добавление soft-delete для секций).
- **Решение.** Вынести `kb_sections_subtree_cte(root_ids)` и `kb_sections_ancestors_cte(node_id)` в `./backend/app/services/kb_acl/_common.py` или отдельный `kb_tree.py`.
- **Сложность.** **M** (1–2 дня).
- **Готовность.** Все 7 мест переведены на helper; тесты зелёные.

### P3-4. Дедуп PDF/DOCX access-check в export_import

- **Проблема.** `./backend/app/api/kb/export_import.py:359-367` и `:418-426` — почти идентичные блоки проверки доступа к статье перед экспортом.

- **Риски, если не делать.** Возможен дрейф: фикс в PDF забудут перенести в DOCX.
- **Решение.** Вынести `_load_article_for_export(db, user, article_id)` → общий хелпер.
- **Сложность.** **S** (час).
- **Готовность.** Дубль удалён.

### P3-5. Очистка неиспользуемых зависимостей и широких `except`

- **Проблема.**
  - `./backend/app/api/kb/permissions.py:398-400` — неиспользуемые `user`, `redis` в сигнатуре `search_kb_users`.
  - `./backend/app/api/kb/export_import.py:336-337` — широкий `except Exception` глушит всё в строку отчёта.
- **Последствия.** Шум в сигнатурах, сложнее диагностировать импорты.
- **Риски, если не делать.** Замедляет дебаг при инцидентах.
- **Решение.** Убрать лишние deps; разделить «ожидаемые» ошибки парсинга от системных, логировать stacktrace.
- **Сложность.** **S** (час).
- **Готовность.** Линт чист; логи содержат traceback на системных ошибках импорта.

### P3-6. Добор тестов на API permissions/tags/attachments

- **Проблема.** В backend-тестах отсутствует/слабо покрыт:
  - `./backend/app/api/kb/permissions.py` (sections/articles permissions, inherit toggle, `/users/search`).
  - `./backend/app/api/kb/tags.py`.
  - `./backend/app/api/kb/attachments.py` на уровне unit (только частично через integration media).
- **Последствия.** Регрессии в ACL-эндпоинтах поймать не на чем; критичная для бизнес-логики область.
- **Риски, если не делать.** Регресс в правах доступа = инциденты безопасности и потеря доверия.
- **Решение.** Добавить unit-тесты:
  - inherit on/off для статьи и секции;
  - search_kb_users с фильтрами и пагинацией;
  - CRUD по тегам;
  - upload/delete вложений, граничные случаи (большой файл, неверный тип).
- **Сложность.** **M** (2–3 дня).
- **Готовность.** Покрытие соответствующих модулей не ниже 80%.

### P3-7. Снизить долю мокающих unit-тестов

- **Проблема.** В `./backend/tests/unit/test_kb_articles.py`, `test_kb_export_import.py`, `test_kb_versions.py` много `db.execute.side_effect`-цепочек. Тесты «верят» в порядок SQL, а не проверяют поведение.
- **Последствия.** Регрессии в реальных условиях фильтрации/сортировки могут пройти.
- **Риски, если не делать.** Ложное чувство покрытия.
- **Решение.** Постепенно переносить такие тесты на интеграционный уровень (с реальной test-DB через alembic + factories).
- **Сложность.** **L** (растягивается на несколько спринтов).
- **Готовность.** Доля моков `db.execute` снижена; критичные сценарии покрыты интеграционно.

### P3-8. Пагинация комментариев и версий

- **Проблема.** `./frontend/src/queries/kb.ts:48-64`: хардкод `limit: 50`. UI не подгружает остальное.
- **Последствия.** На активно обсуждаемых статьях старые комментарии/версии невидимы.
- **Риски, если не делать.** Потеря контекста обсуждения; вопросы от пользователей «куда делись наши версии».
- **Решение.** Реализовать «Показать ещё» через `useInfiniteQuery` или классическую пагинацию; убрать хардкод.
- **Сложность.** **M** (день на каждый таб).
- **Готовность.** При >50 комментариях/версиях все доступны через UI.

### P3-9. Вынос Markdown-экспорта в API-клиент

- **Проблема.** `./frontend/src/pages/KbArticlePage.vue:210-214` использует `window.open('/api/v1/kb/articles/.../export/md')` напрямую, в отличие от PDF/DOCX.
- **Последствия.** Любая смена базы API/префикса = правка в компоненте.
- **Риски, если не делать.** Дрейф конвенций, скрытая связность UI с бэком.
- **Решение.** Добавить `exportArticleMd(id)` в `./frontend/src/api/kb.ts` по аналогии с PDF/DOCX.
- **Сложность.** **S** (час).
- **Готовность.** Прямой URL из компонента удалён.

### P3-10. Сброс header при переходе между статьями

- **Проблема.** `./frontend/src/pages/KbArticlePage.vue`: `clearHeader` вызывается только в `onBeforeUnmount`. При навигации между статьями (router-reuse) виден старый заголовок до загрузки новой статьи.
- **Последствия.** Мерцание/визуальная неаккуратность.
- **Риски, если не делать.** Мелкий UX-дефект.
- **Решение.** В watcher по `articleId` сначала чистить header (или показывать skeleton-заголовок) до прихода данных.
- **Сложность.** **S** (час).
- **Готовность.** При навигации заголовок не «прилипает» от прошлой статьи.
