## 2. Backend (Python 3.12 / FastAPI / SQLAlchemy 2.x async / Alembic / Redis / arq)

### 2.1 Архитектура

#### 2.1.1 API-модуль использует приватные внутренности другого API
- **Файл**: `./backend/app/api/bootstrap.py:14-29`
- **Актуально**: подтверждено — импортирует `_load_settings`, `_find_file`, `_photos_out`, `PhotosModuleSettings` из модулей `branding` и `modules`.
- **Сложность**: средняя; **Критичность**: средняя.

> **Для менеджера.** Файл `bootstrap.py` (агрегатор первой загрузки страницы) напрямую лезет во «внутренности» других файлов, которые не предназначены для внешнего использования. Это нормально работает сейчас, но стоит разработчику переименовать или изменить эти функции — `bootstrap.py` сломается без очевидной причины. Риск: при рефакторинге фич брендинга или модулей легко пропустить это место и получить ошибку уже в production.

#### 2.1.2 Смешение API/бизнес-логики/файловой I/O в одном модуле
- **Файлы**: `./backend/app/api/news.py` (912 строк), `./backend/app/api/photos/folders.py` (523), `./backend/app/api/photos/photos.py` (617), `./backend/app/api/feedback.py` (526), `./backend/app/api/users.py` (516)
- **Актуально**: подтверждено — LOC и структура без изменений.
- **Сложность**: высокая; **Критичность**: высокая.

> **Для менеджера.** Один файл одновременно принимает HTTP-запрос, проверяет права, выполняет бизнес-логику, работает с базой данных и сохраняет файлы. Это как если бы кассир на кассе сам же вёл бухгалтерию и делал инвентаризацию. Последствия: добавление любой новой функции в эти модули становится дорогим (разработчик рискует случайно сломать соседнюю логику); тестировать отдельные сценарии невозможно без запуска всего стека. Прямо сейчас это самый значимый источник дорогостоящих регрессий.

#### 2.1.3 Nextcloud: глобальный singleton с изменяемым состоянием
- **Файл**: `./backend/app/services/nextcloud/service.py:64-88`
- **Актуально**: подтверждено — глобальная переменная `_service`, инициализируется при первом вызове.
- **Сложность**: средняя; **Критичность**: средняя.

> **Для менеджера.** Соединение с Nextcloud создаётся один раз для всего приложения и больше не обновляется. Если настройки Nextcloud изменить в admin-панели, новые параметры применятся только после перезапуска сервера. Кроме того, если во время параллельной работы нескольких запросов возникнет проблема — потенциально всё «зависнет» на одном клиенте. Риск невысокий при малой нагрузке, но вырастает при масштабировании.

### 2.2 Код-проблемы

#### 2.2.1 God-handlers: `update_folder` и `bulk_action`
- **Файлы**:
  - `./backend/app/api/photos/folders.py:204-430` (`update_folder`, ~227 строк)
  - `./backend/app/api/photos/photos.py:401-514` (`bulk_action`, ~114 строк)
- **Актуально**: подтверждено — функции не изменились. (`auth.callback` декомпозирован и из этого пункта исключён.)
- **Сложность**: средняя; **Критичность**: высокая.

> **Для менеджера.** Каждая из этих функций делает слишком много всего за один раз: проверяет права, меняет базу данных, перемещает файлы, уведомляет другие системы. Функция `update_folder` занимает 227 строк кода — для сравнения, средняя «хорошая» функция умещается в 20–40 строк. Это ведёт к тому, что при добавлении даже небольшого изменения в логику фотоальбомов разработчик вынужден держать в голове весь огромный контекст и рискует сломать один из нескольких параллельных сценариев.

#### 2.2.2 Частые `commit` внутри цикла загрузки фото
- **Файл**: `./backend/app/api/photos/photos.py:546-617` (`upload_photos`)
- **Актуально**: подтверждено — `await db.commit()` вызывается на каждый файл внутри цикла.
- **Сложность**: средняя; **Критичность**: средняя.

> **Для менеджера.** При загрузке 20 фотографий сервер делает 20 отдельных «записей» в базу данных вместо одной. Это как 20 раз открывать и закрывать дверь вместо того, чтобы занести все коробки за один поход. Последствия: загрузка большого количества фото заметно медленнее, чем могла бы быть; при частичном сбое (например, сломалась сеть на 10-м файле) состояние базы остаётся непоследовательным — часть записей сохранена, часть нет.

### 2.4 Костыли и временные решения

#### 2.4.1 Маркеры review-патчей `P0-/P1-` в продовом коде
- **Файлы**: `./backend/app/api/auth.py`, `./backend/app/api/news.py`, `./backend/app/services/news.py`, `./backend/app/api/users.py`
- **Актуально**: подтверждено — в коде присутствуют комментарии `P0-3`, `P1-16`, `P1-20`, `P0-7`, `P0-1`, `P0-2`, `P1-19`, `P1-18`, `P0-4`, `P0-5`, `P0-11`.
- **Сложность**: низкая; **Критичность**: средняя.

> **Для менеджера.** В коде есть пометки вида «P0-3», «P1-16» и т.п. — следы «пожарных» исправлений прошлых периодов. Проблема в том, что их смысл хранится только в комментариях внутри кода, а не в системе задач. Со временем становится непонятно: это исправление ещё актуально? Его можно удалить? Можно ли поменять этот код? Риск — при рефакторинге разработчик не понимает, что удаление этого комментария означает потерю важного контекста. Исправление простое: завести тикет на каждую метку в трекере задач.

#### 2.4.2 Ручные `COMMIT` в Alembic-миграциях для concurrent index
- **Файлы**: `./backend/migrations/versions/022_fk_indexes.py:19`, `./backend/migrations/versions/024_trgm_indexes.py:19`
- **Актуально**: не проверялось по коду (низкий приоритет), но исправления не вносились.
- **Сложность**: средняя; **Критичность**: средняя.

> **Для менеджера.** Часть инструкций обновления базы данных содержит ручные команды подтверждения транзакции (`COMMIT`) — специфический приём, который работает только при определённых условиях запуска. Если процедура запуска миграций когда-либо изменится (например, появится новый CI/CD pipeline или другой способ деплоя), эти миграции могут завершиться с ошибкой или частично выполниться. На данный момент не критично, но создаёт хрупкость процесса обновления базы.

## 3. Frontend (Vue 3 / TS / Vite / Pinia / Tanstack Query / Naive UI / TipTap)

### 3.1 Архитектура

#### 3.1.1 Дублирование data-layer: Pinia store с query-хуками внутри (files)
- **Файлы**: `./frontend/src/stores/files.ts`, `./frontend/src/queries/files.ts`
- **Актуально**: `stores/files.ts` импортирует и вызывает хуки из `queries/files.ts` — это допустимый промежуточный паттерн, однако store одновременно хранит и UI-состояние (`selectedFolderId`), и server-state через query. Ситуация стабильнее, чем была с `links` (удалён), но не соответствует целевой архитектуре.
- **Сложность**: средняя; **Критичность**: средняя.

> **Для менеджера.** Данные о файлах и папках хранятся сразу в двух местах — в «хранилище состояния» (store) и в «кеше данных с сервера» (query). Это как вести одну и ту же таблицу в Excel и в базе данных одновременно, синхронизируя их вручную. Риск: при добавлении новой функции разработчик может обновить данные в одном месте и забыть про другое, что приведёт к несоответствиям на экране.

#### 3.1.2 Страницы перегружены оркестрацией API и инвалидацией кеша
- **Файлы**: `./frontend/src/pages/NewsFormPage.vue:333-560`, `./frontend/src/pages/KbArticlePage.vue:266-384`, `./frontend/src/pages/photos/PhotosIndexPage.vue:417-804`
- **Актуально**: подтверждено — 20 вызовов `queryClient.invalidateQueries` непосредственно в страничных компонентах.
- **Сложность**: средняя; **Критичность**: высокая.

> **Для менеджера.** Страницы (компоненты интерфейса) напрямую управляют загрузкой данных и обновлением кеша. Это нарушение разделения ответственности: страница должна только «показывать данные», а не «знать, как получить данные и когда их обновить». В результате добавление любой новой кнопки или действия на странице требует также ручного обновления логики кеширования — это легко пропустить и получить устаревшие данные на экране.

#### 3.1.3 UI side-effects внутри API-слоя (скачивание файлов)
- **Файл**: `./frontend/src/api/kb.ts:185-211`
- **Актуально**: подтверждено — 4 вызова `document.createElement('a')` в API-функциях `exportArticlePdf`, `exportArticleDocx`, `exportSectionZip`.
- **Сложность**: низкая; **Критичность**: средняя.

> **Для менеджера.** Функции, которые отвечают за «общение с сервером» (API-слой), также выполняют действия с интерфейсом пользователя — создают невидимые кнопки в браузере и имитируют их нажатие для скачивания файлов. Это нарушение архитектурного принципа «каждый модуль делает одно». Последствия: такой код нельзя протестировать автоматически; при переходе, например, на мобильное приложение или десктоп-клиент, эта логика скачивания просто не сработает.

#### 3.1.4 Router: один guard делает auth/role/module-gate
- **Файл**: `./frontend/src/router.ts:187-233`
- **Описание**: разные домены гард-логики (авторизация, роли, проверка включённых модулей) переплетены в одном блоке; есть ветви `fail-open` (пропускают при неизвестных условиях).
- **Сложность**: средняя; **Критичность**: средняя.

> **Для менеджера.** Проверка доступа к страницам устроена как один большой «страж», который одновременно проверяет: вошёл ли пользователь в систему, есть ли у него нужная роль, и включён ли соответствующий модуль. Когда такой монолитный код содержит ошибку — её трудно найти и изолировать. Опасный момент: некоторые ветви кода «пропускают по умолчанию» при неожиданных условиях, что теоретически может открыть доступ к страницам, которые должны быть закрыты.

### 3.3 Лучшие практики

#### 3.3.1 ESLint глобально отключает `no-explicit-any`
- **Файл**: `./frontend/eslint.config.js:49,82,137`
- **Актуально**: подтверждено — `"@typescript-eslint/no-explicit-any": "off"` в трёх блоках конфига.
- **Сложность**: средняя; **Критичность**: средняя.

> **Для менеджера.** TypeScript — язык с проверкой типов, который помогает предотвращать ошибки до запуска кода. Тип `any` означает «не проверять этот элемент». Правило, которое должно запрещать неограниченное использование `any`, отключено глобально. Это как отключить антивирус «потому что он мешает». Последствие: ошибки типизации в frontend-коде не обнаруживаются автоматически — только вручную или в production.

#### 3.3.2 Объекты как часть Tanstack Query keys
- **Файл**: `./frontend/src/queries/keys.ts:3-5`
- **Описание**: ключи кеша включают объекты `params ?? {}`; разный порядок полей объекта даёт разные ключи → cache miss при эквивалентных запросах.

### 4.1 Docker Compose

#### 4.1.1 ⚠️ Staging Redis ACL: путь к файлу не существует (НЕ ИСПРАВЛЕНО)
- **Файл**: `./docker-compose.staging.yml:26`
- **Актуально**: **ПОДТВЕРЖДЕНО — проблема остаётся.** В staging-файле:
  ```yaml
  command: redis-server --aclfile /etc/redis/redis.acl --maxmemory 128mb --maxmemory-policy allkeys-lru
  ```
  Базовый `entrypoint` (который генерирует ACL в `/tmp/redis.acl`) **обходится** через `command:`. Файл `/etc/redis/redis.acl` не существует — Redis на staging не запустится с правильными настройками доступа. **Этот пункт был ошибочно помечен как РЕШЕНО в предыдущей версии документа.**
- **Сложность**: низкая; **Критичность**: высокая.

> **Для менеджера.** На staging-окружении (тестовый стенд, максимально приближённый к production) Redis (база данных для кеша и очередей) настроен неправильно: он ссылается на файл прав доступа, которого не существует. При запуске staging-окружения Redis либо не стартует, либо запускается без аутентификации. Это означает, что тестирование на staging проходит в условиях, принципиально отличающихся от production — часть ошибок просто не будет обнаружена. Исправление занимает примерно час работы.

В результате команда думает, что контейнеры ограничены, хотя на самом деле они могут потребить всю память сервера. Риск: при нагрузочном сценарии один контейнер может «съесть» ресурсы и повалить остальные.
